# Auth mechanisms: how verified identity and attributes reach authorization

Date: 2026-10-12. Method: primary sources (RFCs, specs, vendor docs, repo READMEs) fetched live on this date; registry and GitHub numbers from `npm view`, the npm downloads API and `gh api` the same day.

Question: which mechanisms do people actually use to authenticate callers and hand verified attributes (claims) to a policy layer, so that an ABAC/filter policy library over attributes plus tool arguments can stay auth-agnostic and an auth layer can be separate?

**Confidence legend.** HIGH = two or more independent primary sources read (several pages from one vendor count as one source; a vendor's own `LICENSE` file is an independent source for the license claim only). MEDIUM = one primary source read in full or in the relevant part. LOW = recalled or inferred, not verified in this run (flagged "I believe this, but I could not verify it from this research").

**Tag legend.** `agent:approved` = a mechanism the attribute-extraction layer should support, or a component worth reusing or copying the pattern from. `agent:blocked` = do not build on this as the embedded layer (wrong problem, wrong packaging, or prohibited), with the reason given.

---

## 1. Headline findings

1. Every mechanism reduces to the same shape: **credential in, (authentication proof) -> normalized principal + attribute bag out.** The policy-evaluation stage needs only that bag plus per-call context (tool name, args, resource). In Cedar, OPA, Istio, agentgateway, Hasura and Google IAM the policy stage receives already-verified attributes; several of these products also authenticate, but in a separate, earlier stage (Istio `RequestAuthentication` before `AuthorizationPolicy`; agentgateway `jwtAuth` before `mcpAuthorization`; Hasura JWT/webhook before permission rules; Envoy `jwt_authn` before `ext_authz`). Cedar leaves identity entirely to the application. That staged separation is the design to copy.
2. Two delivery styles exist: **claims-in-token** (JWT: attributes ride in the credential, verified locally via JWKS) and **claims-by-lookup** (opaque token -> RFC 7662 introspection; cookie -> session store; Hasura auth webhook; API key -> record). Both end in the same bag; they differ in freshness and revocation latency.
3. **The MCP spec fixes the HTTP side and leaves stdio to the environment.** Streamable HTTP: `Authorization: Bearer` on every request, audience-validated, no token passthrough. stdio: "SHOULD NOT follow this specification, and instead retrieve credentials from the environment" (2025-11-25 and 2026-07-28 text, identical). So a stdio server has identity only at launch.
4. **2026-07-28 makes MCP stateless** (no `initialize`, no `Mcp-Session-Id`, per-request `_meta`). Identity therefore must be re-derived per request from the header; there is no session to cache it on. Step-up and elicitation move to the multi-round-trip pattern (`input_required`).
5. **Federated/delegated auth for AI connectors is converging on three things:** (a) OAuth with CIMD client registration (DCR deprecated in 2026-07-28), (b) enterprise-managed authorization = ID-JAG (RFC 8693 exchange at the IdP, RFC 7523 jwt-bearer at the resource AS; MCP `ext-auth` extension is "Stable"), (c) a credential vault/broker that injects per-user upstream credentials so the agent and model never hold them.
6. **Credential brokers and API-key gateways answer a different question from "who is calling me".** Every broker surveyed (Nango, Composio, Arcade, Pipedream Connect, Apideck, Merge Agent Handler, Paragon) keys stored upstream credentials by an identifier the *application* supplies (`connectionId` + `tags`, `user_id`, `external_user_id`, consumer id). The identifier is a lookup key chosen by an already-authenticated caller, not proof of identity; Nango states that you must persist the connection-id-to-user mapping yourself. A policy layer must therefore take the principal from its own inbound authentication and treat the broker key as a derived resource attribute. Only brokers that proxy and inject at egress, or run the tool themselves and return only its output (Nango proxy and MCP sessions, Composio `proxyExecute`, Pipedream Connect proxy, WorkOS Pipes Relay, Infisical Agent Vault, Zuplo MCP gateway, Arcade tool execution, Claude vaults), keep the credential out of the agent; Auth0 Token Vault returns the provider token to the application, and WorkOS Pipes does so unless Relay is used. None is an in-process library: the nearest are self-hosted services (section 2.3.1).
7. **Build vs integrate:** integrate `jose` (or `oauth4webapi`) for crypto/JWKS, the MCP SDK's `AuthInfo` / `requireBearerAuth` as the HTTP-transport seam, and OPA/Cedar/agentgateway as policy references. **Build** a thin, dependency-light attribute-extraction layer: credential adapters -> claim mapping -> normalized `IPrincipal` with provenance and expiry. No existing library covers "adapter interface + claim normalization + stdio-env source + per-request refresh" together (see section 7).

### 2.3.1 Credential brokers and API-key gateways

Two families share this table. **Brokers** store a user's or tenant's *upstream* credentials (OAuth tokens, API keys) and, in some products, inject them at egress. **API-key gateways** authenticate *inbound* callers by opaque key and map the key to a consumer record. Metrics are from 2026-10-12 (`gh api`, `npm view`, npm downloads API); licenses are from the repository `LICENSE` file, not the GitHub badge.

**Capabilities.** "Caller / tenant" = how the product learns who the end user is. "Egress" = does the product perform the upstream call with the credential so the agent never holds it.

**How a broker sits beside a separate ABAC policy layer.** (1) Authenticate the caller first (I1-I8); the principal comes from that credential. (2) Resolve the broker key from the principal through the application's own mapping (Nango makes this explicit; Composio, Arcade and Pipedream take the id on trust from the calling backend). (3) Put `credential.kind` (`shared` or `per-user`), `broker` and `broker_key` in the attribute bag so policy can say "this call would use the org-wide Salesforce connection". (4) Evaluate policy on tool name and arguments *before* the broker call. Brokers' own gates are coarser and sometimes bypassable (Nango's `nango_proxy` ignores toolset allow/deny; Composio's proxy is limited to the connected account's domain; Agent Vault filters by host). (5) Prefer egress injection (B1, B2, B4, B9 Relay, B11, G12, F6) over token vending (B8, B9 default) when the agent should never hold the credential.

## 3. Per-mechanism notes

**JWT bearer (I1).** Validate in this order: signature against the issuer's JWKS, `iss` against an allowlist, `aud` against this resource, `exp`/`nbf`, then read claims. The MCP spec additionally requires the token to have been issued for this server (RFC 8707 audience binding) and references RFC 9068 for the audience claim. Envoy's anti-spoofing rule (strip the claim-header names from inbound requests before populating them) applies to any layer that forwards claims as headers. Provides everything the IdP put in the token; nothing about state changes after issuance.

**Introspection (I2).** Use for opaque tokens or when immediate revocation matters. The response is `active` plus optional registered claims and arbitrary service members, so the bag is IdP-defined. The calling resource must itself be authenticated to the endpoint. Cache never past `exp`; the trade is staleness vs load.

**Webhook resolver (I7).** The cleanest abstraction for a pluggable auth layer: input = request headers (and optionally the operation), output = `{ role, ...string variables }` or deny, plus a TTL hint. Hasura's contract is deliberately closed-world (all values strings), which keeps policy expressions simple.

**mTLS (I4) and SPIFFE (I9).** Identity is the certificate subject or SPIFFE ID. Envoy and Istio surface it as `source.principal`. RFC 8705 adds certificate-bound tokens: the resource compares `cnf.x5t#S256` to the presented cert hash and returns 401 `invalid_token` on mismatch. SPIFFE docs recommend X.509-SVIDs over JWT-SVIDs because bearer JWTs can be replayed; JWT-SVID exists for L7 hops.

**OAuth 2.1 for MCP (I8).** Server MUST implement RFC 9728 PRM (`authorization_servers`), serve a `WWW-Authenticate: Bearer resource_metadata=...` on 401, validate audience, and accept the token on every HTTP request (not per session). 2026-07-28 adds: RFC 9207 `iss` check on the authorization response, CIMD preferred and DCR deprecated, credentials bound to the issuing AS, and a refined scope-challenge rule (servers SHOULD put all scopes for the current operation in one challenge; clients take the union with prior scopes). Insufficient scope = 403 `insufficient_scope` with `scope=` and `resource_metadata`.

**Cloud workload identity (I10) and K8s tokens (I11).** These authenticate machines to clouds. For an agent platform their role is as *upstream credential sources* (the gateway exchanges its own workload identity for cloud access) rather than the end-user identity policy decides on. GCP's CEL mapping + attribute condition is the most explicit published example of "normalize then reject".

**Token exchange (F1) and delegation.** Policy should receive both subject and actor when delegation applies: for an agent acting for a user, subject = user, actor = agent/client, and RFC 8693 says to consider only the top-level claims and the current actor when authorizing. An ABAC attribute bag therefore needs at least `subject.*` and `actor.*` namespaces.

**ID-JAG / Enterprise-Managed Authorization (F3, F4).** Replaces the consent screen with an IdP-signed assertion evaluated against admin policy. The IdP sees token issuance only; MCP traffic and tool arguments remain invisible to it, so fine-grained policy still lives at the gateway. Claude's implementation: the connector's AS must list the jwt-bearer grant in `grant_types_supported` and keep a per-tenant issuer allowlist.

**Anthropic connector auth (F5) and vaults (F6).** Two separate designs. Connectors (claude.ai, Desktop, mobile, Cowork, Claude Code) authenticate *to the MCP server* with per-user OAuth, an org-wide static header (beta, not user-identifying), or EMA. Managed Agents inject *upstream* credentials per session from a vault keyed by end user, and the egress-substitution trick keeps secrets out of the sandbox. No document called "connector gateway" was found; the design is spread across these pages.

**Credential brokers (F7).** All three key credentials by an app-supplied stable user id, run the consent flow, store and refresh tokens, and keep tokens out of the model. They answer "get a per-user upstream token"; none answer "who is calling me".

**Claim mapping (T1).** The three real designs: Hasura (JSONPath into the token, defaults, string-only variables), GCP (CEL over the assertion, flat `attribute.*`, hard cap 50, reject condition), Kong (named claim + required values, AND/OR semantics). Common core: *paths in, flat attributes out, explicit reject rule, defaults for missing claims.*

**Revocation (T5).** There is no universal push channel. Practical stack: short access-token TTL + introspection where freshness matters + a `jti`/subject denylist + CAEP events where the IdP supports them (CAEP 1.0 is a Standards Track spec from the OpenID Shared Signals WG, 29 Aug 2025). **No maintained Node/TypeScript CAEP receiver exists** (**MEDIUM confidence**: npm searches `caep`, `shared signals framework receiver`, `security event token SET receiver`, `ssf receiver openid`, `continuous access evaluation protocol`, a GitHub repository search and a GitHub code search for `caep session-revoked` (both returned nothing or errored), two web searches, and a DuckDuckGo query restricted to `site:github.com` that stood in for the failed GitHub provider, all run 2026-10-12). What exists: `@sgnl-ai/secevent` 1.0.1 (MIT, SET/CAEP/SSF builder and parser with `parser.verify` and JWKS URL support; 8 weekly downloads, published 2025-08-15, repo SGNL-ai/secevent-js has 0 stars though pushed 2026-10-12) and `@sgnl-ai/set-transmitter` 1.0.0 (MIT, HTTP transmitter, 8 weekly downloads), plus `@atlasauth/pca-signals` 0.4.1 (MIT, created 2026-10-08, 601 weekly downloads, SET build/verify for the PCA agent-authorization project, 0 stars). None implements a stream-configuration endpoint with a push or poll receiver. The GitHub-restricted web search surfaced receivers and transmitters only in other languages or as toys: `SGNL-ai/caep.dev` (Go, MIT, 19 stars, pushed 2026-07-27), `idfoundry/ssfgo` (Go), `mjovanc/sigshare` (Rust), `iamsahil826-a11y/openid-ssf-receiver` (Python, MIT, 0 stars), `duo-labs/sharedsignals` (BSD-3-Clause, 26 stars, last push 2025-03-07) and `ErKiran/ssf-caep` (a mock Node transmitter, 0 stars); stars and dates are from `gh api`. A receiver is therefore a small build on `jose` (verify the SET JWT, check `iss`/`aud`, read `events`) plus an HTTP endpoint, not an install.

## 4. Lifecycle: where attributes exist and when they can change

| Point | Source of identity | Mutable? | Notes |
|---|---|---|---|
| Process startup / config | Env vars, config files, launch-time secrets, workload identity (SPIFFE/K8s/cloud) | Fixed for process life unless re-read | **stdio MCP servers get identity here only.** The spec says stdio should "retrieve credentials from the environment". TS SDK: `ctx.http` is `undefined` on stdio |
| Per connection | TLS handshake (mTLS cert, SPIFFE SVID), WebSocket `connection_init` (Hasura authenticates there and holds until expiry) | New connection = re-auth | Not a unit in MCP 2026-07-28: protocol sessions removed |
| Per request | `Authorization: Bearer` (MCP: "MUST be included in every HTTP request"), headers to webhook, cookies | Every request | In 2026-07-28 stateless MCP there is no `Mcp-Session-Id` and no `initialize`; each request carries protocol version and client info in `_meta`, plus required `Mcp-Method`/`Mcp-Name` headers. Identity must be derived from the header each time (cache by token hash within TTL) |
| Mid-flight | Step-up: 403 `insufficient_scope` -> re-authorize with union of scopes -> retry (clients should cap retries). Elicitation / sampling / roots moved to Multi Round-Trip Requests (`input_required` result + client retry with `inputResponses`); `notifications/elicitation/complete` removed | Attributes can grow | A server needing the outcome of an out-of-band interaction learns it on retry of the original request, correlating via its own `requestState` |
| Before response | Output filtering by attributes (field redaction, row filters); MCP `cacheScope: public|private` and `ttlMs` on list results (2026-07-28) control shared caching | n/a | Per-user lists must be `private`; `tools/list` no longer varies per connection, so per-user tool visibility needs the private cache scope or per-request evaluation |
| Long-running | Token expiry (`expiresAt` required by TS SDK gate), refresh, vault re-resolution, CAEP | Yes | Claude refreshes 5 min before expiry or on 401; vault credentials re-resolved periodically |

Consequence for the layer: attributes must carry `issuedAt`, `expiresAt`, `source`, and `refreshable`, because a stdio process holds a *static* principal while an HTTP process gets a fresh one per request.

## 5. Reference input shapes (what policy engines consume)

- **Envoy `ext_authz` / OPA:** `source`, `destination` (with `principal`, `labels`, `certificate`), `request.http{method,path,headers(lowercased),body}`, `context_extensions` (string map), `metadata_context` (dynamic metadata), optional `tls_session.sni`; OPA adds `parsed_path`, `parsed_body`.
- **Cedar:** `principal`, `action`, `resource` (entity refs) + `context` record + entities (attributes, parents).
- **agentgateway CEL:** variables `jwt.*` (claims) and `mcp.tool.name` (tool), expressions return boolean.
- **Istio:** `request.auth.principal`, `request.auth.claims[k]`, `source.principal`.
- **GCP IAM:** `principal://...subject/<google.subject>` and `principalSet://...attribute.<name>/<value>` / group.

A neutral target that maps onto all of these: `{ principal: { id, type, attributes, claims }, actor?: {...}, credential: { kind, issuer, audience, scopes, expiresAt, bound? }, request: { tool, args, resource }, context: { transport, ... } }`. (Design suggestion, not from a source.)

## 7. Build vs integrate verdict for an attribute-extraction layer

| Concern | Verdict | Choice | Rationale (one sentence) |
|---|---|---|---|
| JWT verify, JWKS fetch/cache, JWS/JWE | **Integrate** | `jose` | 154M weekly downloads, MIT, runtime-agnostic, actively maintained; never hand-roll signature checks. |
| Introspection, token exchange client, DPoP | **Integrate** | `oauth4webapi` | Small, spec-faithful, same maintainer as `jose`. |
| HTTP-transport seam for MCP | **Integrate** | `@modelcontextprotocol/sdk` `requireBearerAuth` / `verifyAccessToken` / `AuthInfo.extra` | It is the host contract; plug the layer in as the verifier and put normalized attributes in `extra`. |
| Policy engine | **Reuse existing repo policy library** (ABAC); Cedar/OPA/CEL as reference | none new | The layer must only emit a principal+attribute bag; Cedar PARC and agentgateway CEL show the shape. |
| Credential adapters (bearer-JWT, introspection, API key, cookie, mTLS-from-proxy-header, webhook, env/stdio, SPIFFE JWT-SVID) | **Build** | thin adapter interface `(request|env) -> IRawCredential -> IPrincipal` | No JS library unifies these; each adapter is tens of lines over `jose`/`fetch`. |
| Claim mapping / normalization | **Build** | declarative map (JSON path in, flat attributes out, defaults, reject condition), modeled on Hasura `claims_map` + GCP attribute condition | Closest prior art is embedded in products, not extractable; the design is small and well specified. |
| Actor/subject and shared-vs-per-user provenance | **Build** | `subject`, `actor`, `credential.kind` fields | RFC 8693 `act` semantics and Claude's static-header caveat both require policy to know which identity it is judging. |
| Caching with TTL and revocation hooks | **Build (small)** | keyed by token hash, bounded by `exp`, invalidation callback for denylist/CAEP | Rules are simple (RFC 7662 `exp` bound; Envoy/Kong patterns); no suitable Node lib found. |
| CAEP / SSF receiver | **Build (small)** | verify the SET with `jose` (`issuer`, `audience`, `algorithms`), then call the cache invalidation hook | No maintained Node receiver exists; the only libraries (`@sgnl-ai/secevent`, `@atlasauth/pca-signals`) have single-digit to low-hundreds weekly downloads and no receiver endpoint. |
| API-key inbound | **Build as an adapter over a key store** | record lookup returning owner, org, scopes, with a `shared` flag | Unkey's verify response (permissions, rate limits, identity) is the best model; Unkey is a service under AGPLv3, and AWS states API keys must not be used for authentication or authorization. |
| Web-framework wiring (Fastify, NestJS, Hono, tRPC) | **Build thin adapters** | Fastify `decorateRequest('principal', null)` + `onRequest` hook that replies early on failure; NestJS authentication guard then policy guard reading handler metadata | Both frameworks document exactly this attach-then-check chain (P9), so the layer needs only a framework-neutral `extract()`. |
| Per-user upstream credentials | **Integrate behind a seam; no product to embed** | `IUpstreamCredentialProvider` with adapters: Infisical Agent Vault (self-hosted, MIT in practice, egress injection), Nango (ELv2 service) or Composio/Pipedream/WorkOS Relay (hosted), HashiCorp Vault/OpenBao for dynamic secrets, Claude vaults when on Managed Agents | Every surveyed broker is a hosted service or a separately deployed daemon (section 2.3.1), none is an in-process library; the broker key is app-supplied, so the seam maps an authenticated principal to a broker key and never accepts one from the caller, and never passes the inbound token through (F9). |
| Authorization server (issuing tokens) | **Do not build** | external IdP, or `workers-oauth-provider` if on Workers | Out of scope for an extraction layer; MCP says the AS is out of the server's scope. |
| Whole-gateway and proxy products (agentgateway, ContextForge, Docker gateway, Kong, Tyk, Gravitee, Pomerium, Istio, Zuplo, LiteLLM) | **Blocked as the embedded layer** | reference only | Separate daemons or hosted services; integrate only as bring-your-own-gateway deployments, and copy their claim-forwarding contracts (Kong consumer headers, Pomerium `X-Pomerium-Jwt-Assertion`, Envoy anti-spoof rule). |

**Recommendation.** Ship the layer as pure TypeScript (`platform:shared`-compatible core, with Node-only adapters for env/stdio), depending only on `jose`. Its contract is `extract(input) -> Promise<IPrincipal | AuthFailure>` where `IPrincipal` has `{ subject, actor?, attributes (flat string/string[]), credential{kind, issuer, audience, scopes, issuedAt, expiresAt, shared:boolean}, provenance }`. Register adapters per transport: stdio = env adapter evaluated once at launch (static, `expiresAt` absent); Streamable HTTP = bearer/introspection/webhook adapters evaluated per request, cached by token hash within `exp`. Keep policy auth-agnostic by giving it only `IPrincipal.attributes` plus tool name/args. Track the ID-JAG draft and CAEP as the two moving standards.
