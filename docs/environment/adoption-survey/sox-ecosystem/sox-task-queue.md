## Current state

The package is a SQLite-backed durable task queue with no environment variable dependencies. All configuration is passed programmatically via `TaskQueueConfig` and `SchedulerConfig` interfaces.

**Environment variables:** None read. No `process.env.*` calls in flagged files.

**Writes:**
- `config.dbPath` (required, caller-provided string) — SQLite database file; may be relative, absolute, or in-memory (`:memory:`).
  - Located at task-queue.ts line 197: `this.db = new Database(this.config.dbPath)`
  - Scheduler resolves dbPath via duck-typing at scheduler.ts:60–68.
- `<dbPath>-wal` — WAL write-ahead log (auto-generated by SQLite when PRAGMA journal_mode = WAL is set, schema.ts:4).
- `<dbPath>-shm` — WAL shared-memory index file (auto-generated by SQLite for coordination across connections).

**Config:** All configuration passed to `SqliteTaskQueue` or `createTaskQueue()` via `TaskQueueConfig` (task-queue.ts:25):
- `dbPath: string` (required) — database file path.
- `heartbeatTimeoutMs?: number` (default 30_000) — lease duration before task requeue (task-queue.ts:426).
- `reaperIntervalMs?: number` (default 5_000) — interval between lease-expiry reaper ticks (task-queue.ts:255).
- `dequeueBatchSize?: number` (default 10) — tasks to claim per dequeue() call (task-queue.ts:424).
- `maxQueueDepth?: number` (default 0, unlimited) — hard limit on live tasks (task-queue.ts:342).
- `defaultMaxRetries?: number` (default 3) — max retries if task enqueue does not override (task-queue.ts:362).
- `defaultTtlMs?: number | null` (default null) — default task TTL (task-queue.ts:365).
- `autoRequeueExpired?: boolean` (default true) — auto-reaper on open() (task-queue.ts:203).
- `onDead?: (task: Task) => void` — optional dead-letter callback (task-queue.ts:329).

Scheduler config likewise includes `dbPath` (explicit or via queue reference), `tickIntervalMs`, `autoStart`, `defaultPriority`, `defaultMaxRetries`.

**Logging:** Warnings and errors to console.warn/console.error (stdout/stderr). Messages include:
- Scheduler entry warnings: disabled expired cron (scheduler.ts:158), enqueue failures (scheduler.ts:198).
- Reaper tick errors: logged but loop continues (task-queue.ts:260).
- Dead-letter callback errors: logged but do not propagate (task-queue.ts:335).

No structured logging; no persisted log files.

## Logging audit

**Summary:** The package logs warnings and errors to console (stdout/stderr) but does not persist log files.

- **has_logging:** true — warns on scheduler entry failures (scheduler.ts:158, 198), reaper issues (task-queue.ts:260, 305–307), dead-letter callback errors (task-queue.ts:335).
- **logger:** console (console.warn, console.error) — plaintext, unstructured.
- **persists_log_files:** false — all output is transient (stdout/stderr only).
- **log_destination:** stdout/stderr only.
- **structured:** false — plaintext messages, no JSON/structured format.
- **error_handling:** robust — errors in reaper ticks, dead-letter callbacks, and scheduler tick operations are caught (try/catch) and logged; they do not halt execution.
- **maps_to_env_logs:** true — adopting @adhd/environment would allow routing logs to `env.paths.logs` (kind: `logs`, share: `per-instance`) with a wrapper around console.warn/console.error. This is valuable for multi-instance deployments where each worker/scheduler instance writes to a separate log file.

**Recommendation:** Integrate a simple log-routing layer (pino or custom wrapper) that routes console output to both stdout and `env.paths.logs/<instance>.log`. This requires minimal adoption effort and is valuable for production observability.
