## Acceptance (Gherkin)
In-memory MCP transport and a stub upstream defined inside the test through the fake `IProcessLauncher`; `mcp-json` runs on a temp file. No spawned process.

```gherkin
Feature: Wrap an unmodified MCP server - mcp-json and serve

  Background:
    Given a stub upstream with tools notes_add, notes_clear and notes_archive that logs every tools/call it receives
    And notes.yaml (writer may call notes_add with tag forced to "policy"; notes_archive is ask) and attributes {"role":"writer"}

  @S7.1 @happy
  Scenario: mcp-json init wraps the entry once and keeps a backup
    Given an .mcp.json with one server "notes" run as node with the stub's path
    When "mcp-json init --spec notes.yaml" runs
    Then exit code is 0 and the entry's command is "adhd-policy" with first argument "serve" and the original command carried as "bin:..."  # D-10
    And a backup "<file>.adhd-policy.bak" exists
    When "init" runs a second time
    Then the file is byte-identical to after the first run

  @S7.1 @happy
  Scenario: Undo restores the original byte for byte
    Given a wrapped .mcp.json
    When "mcp-json --undo" runs
    Then the file equals the original byte for byte  # D-10

  @S7.2 @happy
  Scenario: The allowed call reaches the upstream with the forced value
    Given a client connected to "serve bin:... --spec notes.yaml --adhd-attributes <writer>"
    When it lists tools
    Then notes_add, notes_clear and notes_archive appear under the upstream names  # D-08
    When it calls notes_add with text "hello" and tag "mine"
    Then the call succeeds and the upstream log has exactly one entry {"name":"notes_add","args":{"text":"hello","tag":"policy"}}

  @S7.2 @negative
  Scenario: Denied and ask calls are refused and never reach the upstream
    When the client calls notes_clear (no permission) and notes_archive (ask, nobody to answer)
    Then each result has isError true and mentions permission_denied  # D-08, D-15
    And the upstream log still has only the one allowed entry

  @S7.3 @edge
  Scenario: With no policy and no attributes the built-in default applies and says so
    Given no spec argument and no workspace-policy.yaml above the working directory
    When the client calls any tool
    Then the call is refused and the upstream log is empty
    And stderr announces "policy: built-in" once  # D-10, D-12
```
