Real CLI form (D-03, for T18 to reconcile): the derived command takes ONE `--input '<json>'` flag (or `@file`) holding the operation input, e.g. `check --input '{"tool":"files.read","args":{...},"attributes":{...}}'`. The demo's `--tool`, `--args`, `--attributes` (and `narrow --parent`, `--request`) do not exist; `check --tool x` is `invalid_argument` exit 2 ("Unknown option: --tool. Available: --input"), which @S2.9 asserts. Commands answer with or without the `policy` namespace prefix.

Observed: a refusal's reason text reads `denied by permission project:2` / `no permission allows files.read` / `tool "billing.refund" requires approval (matched project:3)`; the decision (effect `ask`, denial code, matched ids) is also in the error body's `details.decision`, which is what @S2.2 / @S2.6 assert (the word "ask" is not in the reason sentence itself, only in `details.decision.effect`). The policy source is announced once per distinct source as `policy: <path>` on stderr. The apigen logger writes its own JSON record straight to fd 2 (not capturable in process); it is NOT stdout, so "no decision is printed" holds for a real consumer. Stdout holds exactly the operation's JSON result.
