# Capability-vertical — architectural critique

**Verdict:** A clean map of ten capabilities onto ten packages, undone by one rule — "no shared domain layer" — that forces the two entities every capability actually touches (Task/Plan, Session/Attempt) to be either duplicated nine times or smuggled in as an unacknowledged dependency, reproducing the hand-mirrored-wire-types bug this rebuild already knows about.

## 1. Improvements — packages to split/merge/add/remove, boundaries to move, what each buys

- **Merge `budget` (5) and `planning` (6).** They disagree about the same numbers by construction: `planning` estimates cost against a cache-hit assumption, `budget` enforces against observed spend. The named failure — planner assumes 90% cache-hit while nothing ever requests caching — is exactly what happens when the estimator and the enforcer are different packages with no shared ledger. One package, two entry points (estimate-at-plan-time, enforce-at-run-time), one cost model. Buys: a single number that can't drift from itself.

- **Split `plans` (1) into a small transactional store plus logic**, and make `exclusivity` (8) a *client* of that store rather than a sibling with its own storage. Detailed in §4 — this is the load-bearing fix in the whole review. Buys: the one invariant the brief calls out as mandatory (claim and plan-state commit together) becomes possible to enforce in code instead of by convention.

- **Demote `surface` (10) from a tenth vertical to a composition root.** "One definition, many transports" is not a capability with its own model and storage — it's a re-exposition of the other nine. As a peer package it either becomes a thin shim depending on all nine others (fine, but that's an entrypoint, not a vertical — the repo's own convention already has a tier for exactly this: `entrypoint/`, not `packages/`) or the other nine grow ad hoc CLI/MCP/HTTP mounting code themselves and `surface` is aspirational. Given "plugins load by name at runtime, zero static importers" is already the stated target, `surface` should be the dynamic-mount host, explicitly named and treated as such, not counted as one of ten equal boxes.

- **Give `routing` (3) an internal plugin seam, because the vertical boundary alone doesn't buy substitutability.** Provider-neutrality's entire job is "swap the provider without touching anything else." Fusing routing's storage (session/provider-affinity state) with its capability surface, as the "own it end to end" rule requires, means adding a provider touches the same package as the wire protocol. The proposal never states whether a new provider is a subdirectory inside `routing` or a new capability — undefined, and it will drift the first time someone adds provider #3 under deadline. Buys: an explicit adapter interface inside `routing` so "add a provider" has one obvious answer.

- **Add a durable-ledger primitive beneath, not inside, `autonomy` (2).** The concrete existing failure — the only durable record of what happened is an unlocked, last-writer-wins JSON file that can't be recomputed — is a storage/durability requirement, not a supervision strategy. Folding it into "autonomy" means every other capability that needs to durably record an observation (budget's real costs, gating's verdicts, steering's suspend state, exclusivity's claims) either writes through the recovery package — a backwards dependency, nine verticals leaning on the tenth — or reinvents unlocked-JSON nine more times. This durable-write primitive is the second-strongest case, after §4, that "no shared layer" is the wrong absolute.

## 2. Primary risks and shortcomings

- **Structural enforcement over convention (worst-served factor) — capability 8.** An `exclusivity` package with storage separate from `plans`'s storage cannot structurally enforce a claim against a plan. It can only publish an event or set a flag `plans` may or may not honor — which is the exact failure already named in the brief ("an assignment field no scheduler reads"). The vertical boundary reproduces the disease it's diagnosing.

- **Cost-boundedness — capabilities 5 & 6.** Covered in §1: split ownership of the cost model is how the 90%-cache-hit bug happened, and the proposed structure keeps the split.

- **Substitutability — capability 3.** The vertical boundary is the wrong grain for substitutability here; the real seam (per-provider adapter) is one level *inside* `routing`, and the proposal doesn't acknowledge that a capability-sized package and a provider-sized swap unit are different things.

- **Recoverability — capability 2.** The durability requirement (single-writer, lockable, recomputable journal) doesn't map cleanly onto "supervision and healing," and the design has no other place to put it. Named risk, not yet a failure in this structure, but there is no obvious owner.

- **Verifiability, indirectly.** Nine of nine sampled backlog items described code that had since changed — a symptom of no boundary being anyone's job to re-verify when its neighbor changes. `gating` (9) is the capability nominally responsible for verifying outcomes, but it has no jurisdiction over composition→routing handoffs like the already-observed "composition produces tool grants the runtime discards" — that bug sits exactly on a seam neither package owns, and capability-vertical multiplies the number of such seams by not naming who owns them.

## 3. What fails first

The `exclusivity`/`plans` split (capability 8 / capability 1) fails first, and it fails silently, under the exact condition this rebuild exists to survive: crash-and-recover over a long unattended run. As soon as claim-write and plan-state-write are not the same transaction, a crash between them — which sustained unattended operation will eventually hit, that's what capability 2 is *for* — leaves the two stores in inconsistent states: claimed-but-plan-shows-unclaimed, or the reverse. Recovery then has to reconcile two independently durable, independently versioned stores from after-the-fact inspection alone. It will not show up in tests, because it's a race between crash timing and two separate commits, not a logic bug. It will show up days or weeks into an unattended run as duplicate work (two attempts against one task) or orphaned claims (a task permanently marked in-flight after the plan moved past it) — and by the design's own contract there is no shared code path that could have refused the second write.

Second-order and slower-burning: with no shared domain layer, there is no single declaration of what a `TaskId` is or what a valid state transition looks like. Every package that references a task — composition attaching prompts, budget attaching spend, gating attaching verdicts, steering attaching suspend state — independently treats "task reference" as an opaque string with no shared validity check. Combined with capability 1's own requirement that plans be "diffable, re-runnable" (i.e. edited and replanned while running), stale references accumulate quietly: attempt records pointing at a task version a later diff superseded. Nothing in the structure catches this because no package's boundary is responsible for it.

## 4. The atomicity problem

The invariant has to live somewhere; "no shared domain layer" doesn't remove the requirement, it just forces a choice among three placements, and only one of them is honest:

1. **Nowhere** — each package writes its own store and reconciles "eventually." This is what capability-vertical as stated implies, and it's what fails first (§3): unrecoverable divergence, patched only by an out-of-band reconciler that is itself a new shared component the design claims not to have, plus a whole new failure class (reconciler bugs) on top.
2. **Inside `plans`** — `exclusivity` becomes a thin logic-only client of `plans`'s storage, with claims as a column/table in the plan store rather than a separate store of its own. This is the correct placement, but it means capability 8 quietly does *not* get the "own your storage end to end" promise every other capability gets — an unacknowledged, asymmetric exception baked into a design that claims symmetry.
3. **In an explicit shared store** — a small `plan-store` module both `plans` and `exclusivity` depend on, doing the claim-write and the plan-state-write in one transaction. This is placement 2 made honest: it names the dependency instead of hiding it inside one capability's box.

**My answer is (3), and its cost is small and specific: one shared transactional store package — not a general "domain layer" spanning all ten capabilities, just the Task/Plan/Attempt/claim aggregate that capabilities 1, 2, 6, 7, 8, and 9 all actually touch.** That costs the design its cleanest claim ("one feature, one package, zero shared layer") but buys back the one invariant the brief states as mandatory. The same reasoning applies to the budget/planning cost ledger in §1 — which means "no shared layer" was never really true of this system; the honest version of this structure has one shared layer underneath, and the capability packages sit above it.

## 5. The single worst thing about this design

The "no shared domain layer" rule, taken literally, guarantees that the failure already sitting in production — one subsystem hand-mirroring another's wire types, invisible until a runtime parse failure — gets manufactured again internally, once for every entity more than one capability touches (Task/Plan across six capabilities, cost data across two), and the design has no seam left to fix it in without breaking its own founding rule. A structure whose central claim is "no shared layer" should not require a shared layer to satisfy its own stated invariant (§4) — that contradiction is the design, not an edge case in it.
