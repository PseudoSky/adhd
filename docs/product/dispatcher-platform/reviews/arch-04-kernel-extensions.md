# Kernel + extensions — architectural critique

**Verdict:** The store/loop split is right, but the design puts three non-negotiable capabilities — cost enforcement, unattended supervision, evidence-gating — behind the exact same "optional, manifest-selected" mechanism it uses for genuinely optional concerns like transports and providers, which reproduces this system's own root disease (structural enforcement by convention) one layer up.

## 1. Improvements

**Belongs in the kernel, currently listed as extension:**

- **Budget/cost gate (capability 5).** The brief is explicit: caps must *block*, not warn — an enforced primitive. An "enforced primitive" that ships as an optional extension is a contradiction: a manifest that omits `budget` produces a fully bootable system with unbounded spend, and nothing in `kernel/loop` notices. The kernel loop needs a mandatory pre-dispatch cost-check hook point — not a cost policy implementation, just an unconditional call site the loop cannot skip. Policy (what counts, what the caps are, per task/session/agent/global) can live in an extension behind that hook. The *existence of the check* cannot.
- **Supervision liveness contract (capability 2).** Unattended recovery is one of three headline goals of the whole rebuild, yet `supervisor` and `healers` sit in `extensions/` next to `composition` and `guard-*`. A manifest that boots without a supervisor loaded is indistinguishable, from the loop's perspective, from one that has one — the loop has no way to know supervision is absent, because nothing in the kernel requires it. Given that runtime-loaded extensions have *already twice* been misread as "not in use" from static reading alone, making the flagship capability itself an easily-omitted extension is the worst possible place to apply that pattern. The kernel loop should own a heartbeat/liveness primitive that a cycle cannot advance without touching — supervisor policy (what "stuck" means, how to heal) is extension; the fact that *something* is watching is kernel-enforced.
- **Evidence verdict type (capability 9).** "Guards verify outcomes, dry-run default" is described as structural. If `guard-*` are pure extensions called as opaque functions, the kernel cannot distinguish "guard ran and passed" from "guard didn't run" (extension absent, no-op, silently swallowed exception). The kernel needs to own the verdict *type* (ran / passed / failed / absent) even though guard *implementations* are extensions — otherwise dry-run-by-default degrades to dry-run-if-someone-remembered-to-wire-a-guard.

**Belongs in extensions, currently ambiguous:**

- **Session lifecycle.** The established defect today is that HITL/injection/streaming work but are unreachable because the planner fires session-less tasks. The proposed structure never places "session" on either side of the kernel/extension line. If session is not a named kernel concept (owned by `kernel/store` alongside the work graph), every extension that needs one — HITL, transport-*, provider swap-mid-conversation (capability 3) — has no guaranteed primitive to attach to, and this exact defect reproduces verbatim in the rebuild.
- **Prompt composition + caching (capability 4) vs. planner packing (capability 6).** The current system's cost-boundedness bug — planner assumes a 90% cache-hit rate the system never requests — is a coupling failure between two components. In this proposal those two components sit on opposite sides of the extension boundary (`composition` extension owns caching behavior; packing/planning logic is unplaced, presumably kernel-adjacent). Nothing in the design names a contract forcing planning's cost assumptions to read composition's *actual* caching state rather than an assumed constant. Boundary fix: `kernel/contracts` must expose a queryable caching-capability fact (is content-hash caching active, what's its real hit behavior) that any planning logic is required to read rather than hardcode.

## 2. Primary risks and shortcomings

- **Capability 5 (cost enforced primitive) — badly served.** As above: optional-by-manifest is structurally identical to "warn," not "block," at the level that matters (does the system run at all without it).
- **Capability 2 (unattended execution recovers) — badly served.** The single differentiator against the sox parity benchmark is placed in the part of the architecture explicitly designed to be omittable.
- **Capability 7 (HITL steering) — unaddressed.** No kernel-level session concept means the "unreachable because session-less" defect has no structural fix in this proposal, only a relocation.
- **Quality factor: Structural enforcement over convention — actively undermined.** This is the named root cause of the current system's failures (assignment field no scheduler reads, advisory-prose policies, human-closed integration loop). "Extension selected by manifest" is convention wearing an architecture-diagram costume: whether the capability runs depends on whether someone remembered to list it, exactly like the failures being fled from.
- **Quality factor: Recoverability — partially served, underspecified.** Good: store is kernel and described as "constrained," which is the right place for structural exclusivity (capability 8) and durable plans (capability 1). Missing: no statement that the store — not an extension — owns the durable record of guard output, real token counts, and attempt history (today's unlocked, unrecoverable JSON file). If that record-keeping is left to whichever extension happens to run last, the exact defect recurs under a new name.

## 3. What fails first

Manifest drift between the environment an extension was developed/tested in and the one actually deployed for a long unattended run. A minimal kernel loop plus optional supervisor/healers/budget means the loop itself has no opinion about what "safe to run unattended" requires — it will happily execute cycles with a manifest that's missing the budget gate or the healer, because nothing kernel-side asserts a minimum required extension set for `--unattended` mode. Given the established fact that manifest-driven composition has *already* fooled readers twice, the first multi-day unattended run is the most likely place this bites: it dies (or worse, silently overspends / wedges on stuck work) not because any single extension is buggy, but because the *set* loaded for that run was never validated against what unattended mode structurally requires. Second-order failure, close behind: a guard extension that no-ops under some error path, producing a false "evidence gated" record because the kernel has no verdict type to reject a silent pass.

## 4. The forever-API problem

`kernel/contracts` becomes the one surface every extension depends on, and for a solo developer it will ossify the moment two or three structurally different extensions exist (a provider, a transport, a guard) — the shape validated by only one kind of consumer (say, providers, built first because that's capability 3's focus) will fit that consumer and nothing else, and the mismatch won't surface until the second differently-shaped extension is written against it, by which point N existing extensions need rewriting to match any contract change. Manage it by: (a) writing at least three structurally different extensions — one provider, one transport, one guard — before treating the contracts shape as stable, specifically because a single-consumer-validated API is not validated; (b) semver-ing the contracts package itself from the first commit, independent of the product version, so a breaking change is a deliberate, visible major bump rather than a silent shift that stale extensions load against unnoticed. Getting the boundary wrong on the first attempt costs one full rewrite pass across every extension written against it — for a solo developer with no coordination cost, that's not organizationally expensive, but it is exactly the place where the "no second pair of eyes" gap has no backstop: nothing catches an early wrong contract decision except building enough divergent extensions to feel the seam crack, and the design as described (kernel first, extensions after) delays that discovery to the point where the most extensions already exist against it.

## 5. Observability of composition

Given runtime-loaded extensions have already twice been wrongly assessed as "not in use" by readers who counted static imports instead of reading the deployment config, this design must ship a live, kernel-owned introspection surface — not documentation, not the manifest file itself — that answers "what is actually running right now" from the running process, because the manifest on disk and the loaded set in a live process can diverge (partial load failure, hot-reload, a manifest edited after boot). Concretely:

- `hosts/runner` — the only component with ground truth, because it performs the loading — must populate a kernel-held registry as each extension actually loads (not as configured to load), including version/identity per extension and any load failures, not just successes.
- That registry must be exposed as one of the platform's own operations (capability 10: one definition, many transports) — queryable via the same CLI/MCP/HTTP surface as everything else — so both a human and the planner itself can ask it. This matters concretely for capability 6: cost-aware planning that assumes caching behavior must be able to query whether the composition extension providing that caching is actually loaded, rather than assuming it, which is precisely how today's 90%-hit-rate planning bug happened.
- Ownership is `hosts/runner`'s alone. An extension cannot be trusted to self-report (if the broken thing is the extension, it can't reliably say so), and `kernel/loop` should treat "extension self-reports as loaded" as untrusted input, consuming only the runner's registry.

## 6. The single worst thing about this design

It uses one mechanism — "optional extension, selected by manifest" — for two categories of thing that must not be treated alike: genuinely optional seams (which provider, which transport, which composition strategy) and non-negotiable preconditions for the product's own stated goals (cost caps that block, supervision that recovers, guards that gate). Collapsing that distinction means the architecture cannot, by inspection of its own directory structure, tell you whether a given deployment is safe to run unattended — which is the same failure mode named as the root cause of the current system's problems (data recorded and honored by nothing), reproduced at the composition layer instead of the data layer.
