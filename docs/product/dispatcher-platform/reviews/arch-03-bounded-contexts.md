# Bounded contexts by data ownership — architectural critique

**Verdict:** Directionally correct — data ownership kills the "advisory field nothing reads" disease — but the design specifies *who may write which table* and stays silent on *what must be atomic together*, and the two places that silence is most expensive (claim/dispatch exclusivity, and cost calibration) are exactly the places the brief's own evidence says the current system already failed.

## 1. Improvements — contexts to split/merge/add/remove, boundaries to move, what each buys

**Split `agents` into `agents` (static, versioned definitions) and leave sessions/transcripts either inside `execution` or explicitly execution-owned.** A definition (model-tier preference, tool bindings, prompt version pin) has a config lifecycle — created rarely, read often, diffed like software. A session/transcript has a runtime lifecycle that is 1:1 with an execution cycle: it opens when execution dispatches, it closes/suspends when the cycle ends or HITL interrupts it (capability 7). Bundling both under one context hides that coupling. Fix: either fold session/transcript ownership into `execution` (cycles *are* the session boundary), or keep `agents` but make the contract explicit — sessions are written only by execution's dispatch operation, never independently. As written, nothing stops a future planner from creating "session-less" dispatch again, which is the exact defect already on record ("planner fires session-less tasks while HITL/streaming need a session"). Renaming the tables doesn't fix that; only a mandatory call path does.

**Add a `prompts` context (or a clearly carved sub-boundary), currently missing.** Capability 4 — "prompts as versioned software — reusable components, context-conditional composition, content-hashed caching" — is a content-addressable store with its own versioning and composition graph, structurally closer to a package registry than to "agent identity." As proposed it has no owner; it will default into `agents.definitions` as an afterthought, which is how composition and hashing logic tends to rot into ad-hoc string concatenation. Give it a name and a table set now, before code exists to retrofit.

**Name "plan" as an explicit entity inside `work`, not just items/dependencies/claims.** Capability 1 requires diffable, re-runnable *work graphs* — that implies a plan/version entity distinct from its items (something to diff *against*). The proposal lists rows, not a graph identity. Without a first-class plan/version row, "diffable and re-runnable" has no anchor, and this recreates the same shape of bug that produced nine-of-nine stale backlog items: there is data describing code, but no explicit link telling you when that data goes stale relative to what it describes. `work` should own that linkage (item → the code/commit state it describes, invalidated on drift), not just item text.

**Add a named orchestration/supervision component — do not let it default into "daemon glue."** Capability 2 (unattended recovery) requires reading claims (`work`) + dispatch history (`execution`) + budgets (`economics`) and acting across all three. Nothing in the proposed structure owns this reconciliation loop. Given the established fact that "a multi-cycle loop exists in code with no callers," an unnamed, unowned orchestration responsibility is precisely how that happens again — it's nobody's table, so it's nobody's job. Name it, give it its own tested state machine, and make it the same mechanism that resolves the divergence in §4.

**Add an operation-composition layer between the five contexts and `runtime/{daemon,cli,mcp}`.** Capability 10 wants one operation surface, multiple transports. As drawn, nothing stops each transport independently importing all five contexts and composing operations itself — which produces N-transport × 5-context coupling and transport drift (cli exposes an op mcp forgets). This needs a named layer (a real operation surface each transport mounts, not three parallel wiring sites), the same discipline this repo already uses for apigen (`extract types → compose schemas → live-mount to CLI/MCP/HTTP with zero codegen`). Reuse that pattern explicitly rather than re-deriving it per transport.

**Reconsider whether five contexts must be five separate physical database files.** For a solo developer with no coordination cost and one deploy target, the team-scale reason for bounded-context *process/storage* isolation (independent ownership, independent blast radius across teams) doesn't apply. The reason that *does* apply here — killing convention-only enforcement — only requires code-level access discipline (only `work`'s module writes `work.*`), not physical file separation. Physical separation is what turns §4 into a real crash-atomicity problem; it should be justified by an actual isolation need, not applied by default at DDD-textbook granularity.

**Praise: `shared/identity` as the *only* shared kernel is the right call.** Constraining shared surface to ID types (not a grab-bag "common" package) is exactly the discipline that prevents the usual bounded-context failure mode of ownership eroding into shared utility soup. Keep it that narrow.

## 2. Primary risks and shortcomings

- **Capability 7 (HITL steering) and 9 (evidence-gated execution) have no enforced call path.** As discussed in §1, relocating session and guard data to new tables doesn't compel the planner to route through them. This is the "Structural enforcement over convention" quality factor's core failure, reproduced: a bounded context is still just a convention until a mandatory operation contract, not a shared naming scheme, sits at the seam. Guards specifically have no owning context at all — they read `execution` observations and write corrections somewhere (a new `work` task? a redirected `agents` session?) with no operation named for either.

- **Capability 6 (cost-aware planning) and the cost-boundedness quality factor are unaddressed by the boundary redraw.** The 90%-assumed-cache-hit bug requires `economics.calibration` to read real signal from `providers` (did the binding actually request caching?) and `execution` (actual token/cache telemetry per attempt). The proposal lists these as three separate contexts with no specified data flow between them. Redrawing table ownership does nothing to stop `economics` from calibrating against a fictional number again unless the dependency `providers → execution → economics` is a named, required operation, not an implicit assumption a future planner author has to rediscover.

- **Capability 3 (mid-session provider swap) crosses `providers` and `agents` with no contract.** Swapping providers mid-conversation without losing context requires translating session/transcript state (owned by `agents`/`execution`) into a new provider's tool format (owned by `providers`). That's a cross-context read-and-transform operation that has to be specified now — "no context touches another's storage" is fine as a rule, but only if the translation operation that *is* allowed is named, otherwise it gets implemented as a direct join the first time someone is in a hurry.

- **Verifiability (quality factor) is not touched by this design at all.** Nine-of-nine stale backlog items is a staleness/lifecycle problem, not an ownership problem; see the "name a plan/version entity" fix in §1. Left as-is, `work` will faithfully own tables full of the same rot it owns today, just with cleaner FKs around it.

## 3. What fails first — as this grows and runs unattended for long periods

The first failure is a **partial cross-context commit during a crash**, producing exactly the class of bug the JSON-file rewrite was meant to retire: `work` durably records a claim; the process is killed before `execution` durably records the corresponding cycle. Now the item is claimed forever with no execution record and no observation trail — permanently stuck work, which is the specific failure capability 2 and capability 8 exist to prevent. This is likely to surface *first*, not eventually, because it only requires ordinary crash timing (unattended systems accumulate crash exposure linearly with uptime), and the brief states plainly that cross-file crash atomicity is unproven in this storage engine.

Close second: a **budget check/claim race** across concurrent transports. Capability 10 puts cli, mcp, and daemon on the same operation surface simultaneously; capability 5 requires budgets to block, not warn. A check-then-act (read remaining budget in `economics`, then claim in `work`) that isn't wrapped in one atomic step will let two concurrent dispatches both pass the check and both spend, exceeding a cap exactly when capability 5 was supposed to prevent it — silently, since nothing in the design flags this as a required atomic pair.

Third, and slower-building: unbounded growth in `agents.transcripts` with no stated retention policy, becoming a query-performance problem on the execution hot path once the system has run unattended for weeks. Real, but not the failure that takes the system down first.

## 4. Cross-context consistency

Capability 8's exclusivity lives in `work`; the record of what actually happened lives in `execution`. Given multi-file mounts enforce FKs and roll back correctly on detected failure, but crash atomicity across separate files is *unproven*, there are three real options:

1. **Co-locate `work` and `execution` in one physical database file** (keep them as separate logical schemas/modules in code, drop the physical file boundary between just these two). Cost: violates the "each context owns its storage file outright" purity for exactly one pair. Buys: real ACID atomicity for the single highest-stakes invariant in the system — a claim and its dispatch record commit together or not at all, with no dependency on an unproven guarantee. This is the cheapest way to get a guarantee you can actually cite instead of hope for, and it costs nothing else the design cares about (FK enforcement, module ownership, and per-context access discipline are all still possible within one file via schema-qualified tables).

2. **Keep them as separate files, wrap every claim+dispatch in one cross-file transaction via the documented mount facility.** Cost: you are shipping your top capability's correctness guarantee on top of a mechanism the brief itself flags as unproven for crash atomicity — rollback-on-detected-failure works, but a kill -9 mid-two-phase-commit is not covered by anything cited. This option is only acceptable after a crash-injection test (repeated kill -9 between the two file commits, verified no split-brain over many iterations) converts "unproven" into "verified for our access pattern" — undocumented, this option is a rebrand of the exact bug being fixed, wearing better tooling.

3. **Keep them separate, and build a reconciler**: on daemon startup and periodically, scan for claims in `work` with no matching live record in `execution` and either resume or release them. This turns "must never diverge" (a transactional guarantee) into "may diverge briefly, always self-heals" (an eventually-consistent guarantee), and it is not extra work — capability 2 (unattended recovery) already requires a reconciliation loop; this reuses it rather than building a second consistency mechanism.

**Recommendation:** do (1) and (3) together, not instead of each other. Merge `work`+`execution` storage for atomic claim/dispatch (cheapest correct answer to the highest-stakes invariant), and build the reconciler anyway as the general-purpose unattended-recovery mechanism capability 2 needs regardless of how atomic the write path is — it's the backstop for every *other* crash window this design has (agent session left open, economics reservation left uncommitted) that a two-table merge doesn't cover.

## 5. The single worst thing about this design

It has an ownership model but no consistency model. "Each context owns its tables outright" answers *who may write*, and never answers *what must commit together* or *what happens when it doesn't* — and the two data flows the brief's own evidence identifies as the system's actual prior failures (claim/dispatch divergence, and cost calibration built on a number nobody produces) are precisely the flows this proposal is silent about. The boundaries are correctly drawn along the ownership axis; the five quality-factor failures that motivated this rebuild all happened along the *transactional* axis, and that axis doesn't appear anywhere in the document.
