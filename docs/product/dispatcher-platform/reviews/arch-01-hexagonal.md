# Hexagonal (ports & adapters) — architectural critique

**Verdict:** Good for the half of the system that is already easy (storage/provider swap-out); structurally silent on the half that is actually hard (sessions, cost enforcement, unattended supervision, one-surface-many-transports), because it names layers instead of the seams where the ten capabilities actually collide.

## 1. Improvements — packages to split/merge/add/remove, boundaries to move, what each buys

- **Add an `app/` (use-case) layer between `core` and `hosts`.** As proposed, `cli`, `mcp-server`, and `daemon` each sit directly on top of `core` + `ports`, meaning each host independently wires: load work, call planning, persist via `work-store`, emit to `observation-sink`, check budget, attach a session. That's the same orchestration logic authored three times. This is structurally the same failure shape as "one subsystem mirrors another's wire types by hand" — parallel implementations of connective logic that drift. Concretely: `app/plan-execution`, `app/session-lifecycle`, `app/supervisor`, `app/cost-ledger`. Hosts become thin: translate transport in/out, call one `app/*` entrypoint. This is what actually delivers capability 10 ("one definition, many transports") — the proposed structure names three hosts but never names the one definition.
- **Add `core/prompt-model`.** Capability 4 (prompts as versioned software: reusable components, context-conditional composition, content-hashed caching) has no package anywhere in the proposal. That's not an oversight to fix later — it's exactly why "prompt composition produces tool grants the runtime discards at the boundary" happens: the thing that computes grants has no home, so nothing owns the contract that grants must survive to the runtime. Pair with `ports/prompt-store` (versioned components/compositions) and `adapters/prompt-cache-content-hash`.
- **Add `ports/budget-ledger`.** Capability 5 says caps must block, not warn. "Planning" (pure, in `core`) can compute a budget-respecting plan, but nothing in the proposed structure stops a `provider-*` adapter from being called directly and spending past the cap — that's exactly "policies rendered as advisory prose," reproduced by this design's omission of an enforcement seam. The ledger must be a port with an atomic reserve/commit/release contract that every provider adapter calls through before a spend commits, not a pure computation that assumes compliance.
- **Add `ports/session`.** Nothing in `core/work-model`, `core/execution-model`, or `core/planning` models "session" — it's implicitly adapter-private state inside `runtime-inprocess`/`runtime-mcp`. That's the direct cause of "HITL, chat injection and streaming are built and working but unreachable from the planner, which fires session-less tasks": the planner has no vocabulary for "this task needs a live session" because sessions aren't a core concept. Model session attach/suspend/resume/redirect as a port, durable independent of any one runtime process.
- **Add `ports/verifier`.** Capability 9 (evidence-gated execution) needs to actually run checks and read `observation-sink` — that's I/O, so it cannot live in the "pure, zero-dependency" `core`. Keep guard *policy* (what counts as pass/fail) in `core/execution-model`; move guard *evaluation* to `ports/verifier` + an adapter. As stated, the proposal has nowhere for this to live without violating its own purity constraint.
- **Specify `ports/work-store.claimTask()` as atomic, not CRUD.** The port's existence is right for capability 8, but "interfaces only" doesn't itself prevent a SQL-backed adapter from doing read-then-write. Name the method as an atomic claim (`Claimed | AlreadyClaimed`), or the double-claim bug returns underneath a clean-looking port.
- **Specify `ports/agent-runtime` lifecycle, not just calls.** The reconnect bug ("client memoizes its connection and never reconnects, so a dead subprocess poisons every subsequent cycle") is the natural default implementation of any bare call-interface. The port must require `healthCheck`/`restart` as first-class operations, or every adapter author reinvents the same wrong default.
- **Un-nest `hosts/daemon`.** A daemon is not a transport peer of `cli`/`mcp-server` — it's a continuously running control loop with its own crash/retry/backoff state and no analog to "handle one request, return." Pull the loop into `app/supervisor`; `hosts/daemon` becomes a five-line process bootstrapper.
- **Make wire types generated, not hand-shared.** "One subsystem mirrors another's wire types by hand, deliberately, to avoid a dependency" is a decision this rebuild must not repeat. Define provider/runtime message contracts once in `core`, and if a genuinely separate process boundary exists, generate the wire schema from that one definition rather than re-authoring it — turns drift into a build-time error instead of a hand-sync duty.

## 2. Primary risks and shortcomings

- **Capability 4 (prompts as versioned software)** is unaddressed — no package owns it, so the exact discarded-tool-grants bug has no structural fix under this proposal, only a new place to keep happening.
- **Capabilities 5 and 6 (cost enforcement / cost-aware planning)** are split between pure `core` computation and untracked adapter-side spend with no ledger port — "blocks, not warns" is not enforceable as specified.
- **Capability 7 (HITL steering)** stays broken by design: session is nowhere in `core`/`ports`, so the planner cannot express session-need, which is the literal bug already observed.
- **Capability 2 (unattended execution/recovery)** and the **structural-enforcement** quality factor are both underserved by folding `daemon` into `hosts`: it treats the system's core reliability property as "one more way to call the domain" instead of a stateful actor with its own model.
- **Capability 10 (one definition, many transports)** is asserted but not delivered — three hosts with no shared use-case layer is three definitions with a shared vocabulary, not one definition with three views.
- **Recoverability** is the one quality factor this design genuinely fixes: `observation-sink-eventlog` as an append-only source of truth, with derived state (token counts, attempt history) recomputed via projection instead of last-writer-wins JSON, directly kills the cited failure. Say so plainly — it's correct.
- **Substitutability** is well served for storage and providers (textbook adapter swap), but undermined for runtime substitutability specifically by the missing lifecycle contract — a new runtime adapter will reproduce the reconnect bug unless the port forces the issue.

## 3. What fails first — as this grows and runs unattended for long periods

The supervision loop is where load concentrates over time (most cycles, most crashes, most retries), and it's the piece this structure defines least — it isn't a domain concept in `core`, isn't a port, and is demoted to a peer of `cli`/`mcp-server` inside `hosts`. It will accrete ad hoc retry/backoff/healing logic with no model constraining it, which is the same shape as today's "multi-cycle loop exists in code with no callers," just relocated. Second: budget-ledger races. Given agent work spawns separate processes that die independently, concurrent spend against an unspecified enforcement point will blow through caps precisely under the heaviest concurrent load — i.e., precisely when the system has been running unattended longest. Third: any HITL session in flight when its runtime process crashes is unrecoverable, because session state lives inside the runtime adapter rather than a durable port — this will happen on a long enough unattended run and there is no resume path.

## 4. What it makes easy / what it makes impossible

Easy: swapping LLM providers (capability 3, textbook fit), swapping the storage backend, and testing `planning`/packing/eligibility with zero mocks as deterministic pure functions — a real win for the verifiability quality factor on that slice of the system.

Impossible, as specified: enforcing cost caps as a blocking transactional invariant (no ledger port); expressing "this task needs a session" in a planner that only knows plain-data tasks (no session concept in core); delivering one true operation surface across CLI/MCP/daemon (no use-case layer, so each host independently reimplements orchestration — the exact class of drift bug already seen with hand-mirrored wire types); and treating structural work exclusivity as store-enforced rather than caller-disciplined, unless the `work-store` port's method signature — not just its presence as a port — is specified as atomic.

## 5. The single worst thing about this design

There is no application/use-case layer between `core` and `hosts` — the proposal jumps from pure domain straight to three independent transport-specific hosts, so "one definition, many transports" (capability 10) is not actually structural, and every named bug in the brief (dropped tool grants, unreachable HITL, hand-mirrored wire types, an orphaned multi-cycle loop) is a variant of the same root cause: connective/orchestration logic with no single authoritative home, free to be implemented differently — or not at all — in each place that needs it.
