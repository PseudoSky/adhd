## 1. Question 3 — is `extract_module()` safe to invoke as a separate process from `flask_server.py`'s own invocation of it?

### 1.1 What `extract_module()` actually does

`extract_module(module_path, namespace=None)` is the real entrypoint (verified — it is the only public extraction function; `_main()` calls it directly)[extractor.py:333-336,548]. Per call it:

1. Resolves the target `.py` file path and derives the namespace/file segments (pure, local — no global state)[extractor.py:353-359].
2. Dynamically loads the target module via `importlib.util.spec_from_file_location("_apigen_target_", str(path))` — **the registered name is a hardcoded literal, `"_apigen_target_"`, not derived from the target path**[extractor.py:362].
3. **Registers the freshly-loaded module object in `sys.modules["_apigen_target_"]` *before* `exec_module()`** — this is the one process-global mutation the function performs, done deliberately so `dataclasses._is_type()` can resolve `cls.__module__` and `typing.get_type_hints()` can resolve stringized (PEP-563) annotations against the module's own globals during extraction[extractor.py:361-380]. On any exec failure the entry is popped again (`sys.modules.pop(spec.name, None)`)[extractor.py:378-379], but **on success it is left in `sys.modules` indefinitely** — this is a genuine (if narrow) module-registry leak under a fixed key, discussed in §1.3 below.
4. Walks the module's public exports (`__all__` or `dir()`-minus-underscore) and, for each, builds a plain-dict `Operation` (`id`, `host`, `namespace`, `path`, `kind`, `async`, `streaming`, `safe`, `input`, `output`, `envelope`, `typeText`)[extractor.py:382-527]. Every value placed into these dicts is a JSON-primitive, list, or nested dict — schema fragments, segment `{raw, words}` structures, booleans, strings. **No live function object, class object, or other non-serializable Python value is ever placed into the returned list.**
5. Returns `operations: list[dict[str, Any]]` — a plain, JSON-serializable data structure[extractor.py:343-344,527].

**Conclusion:** the only process-level side effect `extract_module()` performs is inserting an entry into `sys.modules` under the fixed key `"_apigen_target_"`. Its **output** (the thing a separate process would hand across the process boundary) is pure data with no dependency on any process-local object identity, cache, or global. Running `extract_module()` in a short-lived, separate process and emitting its return value as JSON on stdout (exactly what the proposal's step 1, `--emit-json`, proposes[transport-serve-core-refactor.md:175]) reproduces the return value byte-for-byte in any other process — there is nothing in the function's own side effects that a separate process would need to "carry over" for the JSON to be correct.

### 1.2 What `flask_server.py`'s own invocation (`_build_state`) relies on beyond the returned `ops` list

`ApigenFlaskServer._build_state()` is the real "own invocation" referenced by proposal §8.3[flask_server.py:572-611]. Tracing it exactly:

1. It calls `extract_module(self._module_path, namespace=self._namespace)` itself, to get `ops`[flask_server.py:574]. This is the **same** call proposal §8.3 worried a separate process wouldn't reproduce — but per §1.1 above, `extract_module()`'s only side effect (the `sys.modules["_apigen_target_"]` registration) is never read by `_build_state` or by anything else in `flask_server.py` (grep-confirmed: `"_apigen_target_"` appears nowhere in `flask_server.py`; the string does not occur in the file at all).
2. It then performs **a second, fully independent module load** of the *same* `.py` file, under a **different** hardcoded `sys.modules` key, `"_apigen_flask_module_"`[flask_server.py:585-596] — this is a completely separate `importlib.util.spec_from_file_location`/`module_from_spec`/`exec_module` cycle, producing a **second, distinct module object** with its own fresh globals, independent of the module object `extract_module()` loaded and registered under `"_apigen_target_"` a moment earlier in step 1.
3. It builds `registry: dict[str, Any]` by walking the **returned `ops` list** from step 1 and, for each op, doing `fn = getattr(mod, op["path"][-1]["raw"], None)` against the **second** module object from step 2 — i.e. it re-derives the live callable purely by **name lookup keyed off plain-data (`op["path"][-1]["raw"]`, a string) from the `ops` list**, never by any object reference `extract_module()` produced[flask_server.py:598-604].
4. `Runtime(registry)` and `_ServerState(namespace, runtime, ops)` are built from these two independently-derived pieces (the schema data from step 1's `ops`, the live callables from step 2's fresh module)[flask_server.py:606-611].

**The critical fact this traces out:** `flask_server.py`'s `_build_state` **already, today, in a single process, treats `extract_module()`'s result as pure hand-off data** — it does not reuse the module object `extract_module()` loaded, does not reuse any function reference from it, and does not read the `sys.modules["_apigen_target_"]` entry it left behind. It performs its own, completely separate module load whose only input is the target `.py` file path (not anything produced by `extract_module()`'s internals) and whose only cross-reference to `extract_module()`'s output is the plain-string function names inside the returned `ops` list.

This means the target user module is **already loaded/exec'd twice, independently, in the same process**, under two different `sys.modules` keys, every time `ApigenFlaskServer.start()` runs today. If the target `.py` file had import-time side effects that were unsafe to run twice (opening a socket at module scope, a `print()` at import time, appending to a shared list defined in another already-imported module, etc.), that class of hazard **already exists today**, in-process, independent of any process split. It is not introduced or worsened by moving step 1 into a separate OS process — a separate-process split runs the target module import exactly once *fewer* times in the process that goes on to serve (only step 2's load happens in the server process; step 1's load — and its one-time exec of the target file — happens and finishes in a process that exits immediately after printing JSON).

### 1.3 The one caveat found (not a blocker)

`extract_module()`'s `sys.modules["_apigen_target_"] = mod` registration (§1.1 point 3) is never popped on success[extractor.py:374-380]. This is harmless for the two-phase split (the process that runs extraction exits right after, taking `sys.modules` with it) and harmless for `flask_server.py` today (it doesn't read that key). It **would** matter only if a single long-lived process called `extract_module()` repeatedly for *different* target files without exiting in between (e.g. a hypothetical batch-extraction tool) — each call would silently clobber the previous target's entry under the same fixed key, and if anything else in that process later did `sys.modules.get("_apigen_target_")` expecting a specific target, it would get whichever target was extracted most recently. **No code path in this repository currently does that** (confirmed by reading both `extractor.py`'s own `_main()`, which extracts exactly one file per process invocation[extractor.py:534-552], and `flask_server.py`, which never reads the key). This is a latent, narrow module-registry hygiene issue, not a defect that blocks or complicates the Phase 3 two-phase split — it is called out here for completeness, not filed as a new BACKLOG item (it does not manifest on either the extract-only path or the serve path as currently written or as Phase 3 proposes to change them).

### 1.4 What Phase 3 (`py-flask-serve-split`) still needs to build

Confirming the gap already correctly identified by the proposal's own step 3[transport-serve-core-refactor.md:177] and mirrored in `docs/plan/apigen-serve-core/dag.json`'s `py-flask-serve-split` node: **today, `_build_state()` always calls `extract_module()` itself — there is no existing entry point that accepts a precomputed `ops`/plan instead.** This is not a safety hazard (§1.1–§1.2 show the call is side-effect-neutral either way); it is a straightforward missing feature that Phase 3 already exists to build: `_build_state` (or its replacement) must be changed to accept an externally-supplied plan (e.g. `--plan <path>`) and skip its own internal `extract_module()` call, while **retaining** its second, independent module load (step 2 above) since that load's only job — producing live callables — is inherent to being a server process and cannot be satisfied by data crossing a process boundary (Python function objects are not safely serializable across the process boundary here; nothing about the split changes that).

### DECISION

```
DECISION: SAFE — extract_module() is a side-effect-neutral pure-data producer; its only process-global mutation (sys.modules["_apigen_target_"], extractor.py:374) is read by nothing, including flask_server.py's own _build_state, which already performs its own fully independent second module load (flask_server.py:585-596) and only ever consumes extract_module()'s output as plain-data ops (function names + JSON schema) via getattr()-by-name (flask_server.py:598-604) — never a live reference from extract_module() itself. The two-phase extract-in-one-process / serve-in-another-process split proceeds as designed (proposal §3d steps 1-3); the only real gap is that _build_state currently always calls extract_module() itself rather than accepting a precomputed plan — a missing feature, not a safety defect, and it is already Phase 3's (py-flask-serve-split's) explicit job to add that --plan entry point.
```

## 2. Question 4 — does py-grpc's `plugin.ts` + `grpc_server.py` genuinely mirror py-flask's spawn+re-derivation pattern?

### 2.1 `plugin.ts` layer — genuinely mirrors, near byte-for-byte

Comparing `apigen-plugin-py-grpc/src/lib/plugin.ts`[plugin.ts:1-209] against `apigen-plugin-py-flask/src/lib/plugin.ts`[plugin.ts:1-209] line by line: the two files are structurally identical —

- Same `waitForReady()` helper: a `readline` interface over `proc.stdout`, watching for a `{"ready":true}` JSON line, bounded by a 10 s timeout, settling on either the ready line or premature process exit[py-grpc plugin.ts:58-102; py-flask plugin.ts:58-102].
- Same `run()` shape: resolve `port`/`host` from `input.options`, resolve `namespace`/`modulePath` from `input.packages[0]`, validate the source is a `.py` file, call `ensurePythonEnv(...)`, `spawn()` the managed interpreter with `-m apigen_python.<X>_server --module … --namespace … --host … --port …`, forward `stderr`, `await waitForReady(proc)`, then block on process exit / `input.signal` abort → `SIGTERM`[py-grpc plugin.ts:108-182; py-flask plugin.ts:108-182].
- Same plugin object shape: `id`, `description`, `language: 'py'`, `optionsSchema`, a no-op `generate()` (run-only plugin, `{ files: [] }`), `run`[py-grpc plugin.ts:188-208; py-flask plugin.ts:188-208].

**Differences are exactly the ones you'd expect for a different protocol/port/dependency set**, not structural divergence: default port `50051` vs `8000`; spawned module `apigen_python.grpc_server` vs `apigen_python.flask_server`; `ensurePythonEnv({ extras: ['grpc'] })` vs `ensurePythonEnv({})` (grpcio is an optional extra)[plugin.ts:131 both files]. **Verdict for this layer: mirrors.** py-flask-serve-split's assumption that py-grpc's TS plugin shape is portable holds — a two-phase spawn (extract-only subprocess, then real-`project()`, then spawn-with-plan) can be layered onto `py-grpc/plugin.ts`'s `run()` the same way it will be layered onto `py-flask/plugin.ts`'s `run()`.

### 2.2 Python server layer — the extract/serve shape mirrors; the naming/projection derivation genuinely diverges

**What mirrors:** `grpc_server.py`'s `ApigenGrpcServer._build_state()`[grpc_server.py:599-650] follows the *exact* same pattern as `flask_server.py`'s `_build_state()` (§1.2 above): it calls `extract_module()` itself to get `ops`[grpc_server.py:601], then performs a **second, independent** module load under yet another distinct hardcoded `sys.modules` key, `"_apigen_grpc_module_"`[grpc_server.py:612-623], and builds its `registry: dict[str, Any]` by `getattr(mod, op["path"][-1]["raw"], None)` against that second module, keyed by the same plain-string function names from `ops`[grpc_server.py:625-630]. This is identical in shape to flask_server.py's step 2/3 (§1.2) — the extract/serve split adjustment described in §1.4 (accept a precomputed plan, skip the internal `extract_module()` call, keep the second independent load for live callables) applies to `grpc_server.py` exactly the same way it applies to `flask_server.py`. **No additional hazard here beyond what §1 already resolved.**

One gRPC-specific wrinkle not present in flask_server.py: `_build_state` filters `ops` down to `kind in ("action", "constructor")` before building gRPC methods, dropping `kind="query"` operations entirely (falling back to all ops only if none qualify)[grpc_server.py:634-637]. This is a deliberate, working filter, not a defect — it is called out here only because it means py-grpc's *set* of exposed operations is a strict subset of py-flask's for the same source file, which the plan's parity gate (`py-grpc-serve-split.3`) needs to be aware doesn't map 1:1 onto py-flask's own golden fixture set without accounting for the `kind` filter.

**Where it genuinely diverges — naming/projection derivation:**

`flask_server.py`'s `_route_for_op`/`_http_verb` are a **verified, byte-for-byte port** of `@adhd/apigen-engine-naming`'s `project(op).http`: `_route_for_op` computes `'/' + '/'.join(kebab(s) for s in [namespace, *path])`[flask_server.py:252-262], which is exactly `naming.ts`'s `'/' + allSegs.map(toKebab).join('/')` where `allSegs = [op.namespace, ...op.path]`[naming.ts:147,153]; `_http_verb` computes `safe || isPrimitiveOnlyInputSchema(input) ? GET : POST`[flask_server.py:308-314], exactly matching `naming.ts`'s `op.safe || isPrimitiveOnlyInputSchema(op.input) ? 'GET' : 'POST'`[naming.ts:150-151]. Both use **every** segment (namespace + full multi-segment path), matching `naming.ts`'s `allSegs`.

`grpc_server.py` has **no equivalent port at all**. Its naming is computed inline, in two separate places, using a scheme unrelated to `naming.ts`'s real gRPC projection:

- **Service name:** `namespace.capitalize() + "Service"`, computed independently in `_ServerState.__init__`[grpc_server.py:407] and again in `ApigenGrpcServer.start()`[grpc_server.py:639] (two duplicate inline sites, not one shared function). Python's `str.capitalize()` upper-cases only the first character and **lower-cases the rest** of the string — so for a namespace of, say, `"myApi"`, this produces `"MyapiService"`, not any Pascal-cased-per-word form.
- **Package name:** the raw `namespace` string, unchanged, used directly as `file_proto.package`[grpc_server.py:263] and again in `_ApigenGrpcHandler.__init__`'s `self._full_service = f"{state.namespace}.{state.service_name}"`[grpc_server.py:448].
- **Method name:** the raw, un-transformed function identifier, `op["path"][-1]["raw"]`, used directly as the proto message/service method name with **no case transformation at all**[grpc_server.py:267,272-273,293,297,310-313] and again for gRPC-method routing in `_ApigenGrpcHandler.service()`, which matches the inbound gRPC method string against `fn_name` looked up in `self._state.op_map` (itself keyed by the same raw name)[grpc_server.py:453-465].
- **The file/path segment is silently dropped.** For a multi-segment op (namespace + file-segment + export-segment — the common shape, since `extract_module()` includes the file segment unless the source stem is `index`/`main`[extractor.py:394-395]), `flask_server.py`'s route derivation uses **all** segments, but `grpc_server.py`'s service/method derivation **never looks at `op["path"]` except for `op["path"][-1]`** — the file segment (`op["path"][0]` when there are two path segments) is never incorporated into `package`, `service`, or `method` anywhere in the file.

Compare against the real `project(op).grpc` rule in `naming.ts`: `grpcPackage = snake(allSegs.slice(0,-1)).join('.')`, `grpcService = Pascal(allSegs[allSegs.length-2])`, `grpcMethod = Pascal(allSegs[allSegs.length-1])`[naming.ts:163-166] — i.e. package is dotted-and-snake_cased from **every segment except the last**, service is the **Pascal-cased second-to-last segment** (the file segment, for a 2-path-segment op), and method is the **Pascal-cased last segment**. For a two-path-segment op (namespace=`pkg`, path=[`utils`, `addDecimal`]), `naming.ts` computes `package="pkg.utils"`, `service="Utils"`, `method="AddDecimal"` (full path `pkg.utils.Utils/AddDecimal`), while `grpc_server.py` today computes `package="pkg"`, `service="PkgService"`, `method="add_decimal"` (full path `pkg.PkgService/add_decimal`) — **a different package, a different service name (with a hardcoded `"Service"` suffix `naming.ts` never adds), and a raw-vs-Pascal-cased method name.** These are not equivalent under any renaming; they are two unrelated algorithms.

**This exact divergence was independently confirmed here and cross-checked against an existing BACKLOG entry** (`BACKLOG.md:1318`, `FEAT-APIGEN-SERVE-CORE-009`'s "architect review fold (2026-07-23, F4 — CONFIRMED divergent, resize)") and the `py-grpc-serve-split` plan state's own context doc (`docs/plan/apigen-serve-core/contexts/py-grpc-serve-split.md:59-62`, criterion `py-grpc-serve-split.5`), both already filed/authored before this preflight ran, both asserting the identical finding this document independently re-derives from the primary source. **No new BACKLOG item is filed for this — it is a corroboration of an existing, correctly-scoped entry, not a new discovery** (dedupe-before-filing).

**One refinement this preflight adds beyond what was already filed:** the existing context doc (`py-grpc-serve-split.md:44`) flags that "the exact re-derivation symbol name to delete is confirmed by the preflight findings" and asks the executor to "amend criterion `py-grpc-serve-split.2`'s pattern (executor-class) if it differs from `_route_for`." **It does differ, materially: there is no single, named, deletable function analogous to `_route_for_op`/`_http_verb`.** The divergent naming in `grpc_server.py` is **inline**, duplicated across (at minimum) five call sites: `_ServerState.__init__` line 407 (`service_name` assignment), `ApigenGrpcServer.start()` line 639 (`service_name` re-computed a second time), `_build_file_descriptor_proto()` lines 263/267/272-273/293/297/310-313 (package name + per-op message/method names), `_build_descriptor_pool()` lines 340-351 (looks up messages by the same inline-derived names), and `_ApigenGrpcHandler.service()`/`__init__` lines 448/453-465 (routes inbound gRPC calls by re-deriving `self._full_service` and matching the raw method suffix against `op_map`, itself keyed by raw names). `py-grpc-serve-split` (criterion `.2`) should be read as "**thread the injected plan's `grpc.package`/`grpc.service`/`grpc.method` through all of these call sites**, replacing the inline `namespace.capitalize()+"Service"` / raw-name computations with the plan-supplied precomputed values" — not "delete one function like `flask_server.py`'s `_route_for_op`." This is a strictly larger, more scattered edit than the py-flask equivalent, consistent with the context doc's own "resize" framing but now with the exact call-site inventory needed to scope it precisely.

### py-grpc vs py-flask shape verdict

```
DIVERGES (confirmed, not merely suspected): py-grpc's plugin.ts spawn/waitForReady/subprocess-lifecycle layer mirrors py-flask's byte-for-byte (only port/module-name/pyenv-extras differ, as expected). Its Python server's extract/serve TWO-MODULE-LOAD pattern (extract_module() for schema + a second independent load for live callables) also mirrors py-flask's exactly, so §1's SAFE verdict for the extract/serve split carries over unchanged. BUT py-grpc's service/method/package NAMING is NOT a port of naming.ts's project(op).grpc rule the way py-flask's _route_for_op/_http_verb IS a port of project(op).http — it is an unrelated, inline, five-call-site scheme (namespace.capitalize()+"Service" + raw fn-name, ignoring the file/path segment entirely) that produces different package/service/method values than naming.ts's real algorithm for any multi-segment op. This matches — and is independently corroborated, not newly discovered — the existing BACKLOG.md:1318 (FEAT-APIGEN-SERVE-CORE-009, F4 fold) and docs/plan/apigen-serve-core/contexts/py-grpc-serve-split.md:59-62 (criterion .5) findings.
```

## 3. PLANNER-CLASS escalation assessment

**No new DAG state needs inserting.** The plan already anticipated exactly this outcome: `py-grpc-serve-split`'s context doc already carries an explicit F4 fold and a dedicated acceptance criterion (`py-grpc-serve-split.5`, "py-grpc divergent naming … reconciled to project()'s grpc rule via injected plan (F4)")[py-grpc-serve-split.md:24,59-62], and `BACKLOG.md`'s `FEAT-APIGEN-SERVE-CORE-009` entry already carries the matching architect-review fold[BACKLOG.md:1318] — both dated 2026-07-23, prior to this preflight running. This preflight's Q4 work is a **confirmation with primary-source citations** of a finding the plan's authors had already resized `py-grpc-serve-split` for, not a new problem requiring a new state.

The one actionable refinement (§2.2's last paragraph) is a **precision correction to an existing criterion's guidance**, not a scope change: `py-grpc-serve-split.2`'s note about "the exact re-derivation symbol name" should be read as "five inline call sites across `_ServerState`, `ApigenGrpcServer.start()`, `_build_file_descriptor_proto()`, `_build_descriptor_pool()`, and `_ApigenGrpcHandler`," not a single named function. This does not require editing `dag.json`/`state.json` — it is exactly the kind of detail the context doc already flagged as "to be confirmed by the preflight findings" and can be read directly from this document by whoever executes `py-grpc-serve-split`.

Question 3 (extract-module safety) resolved SAFE with no adjustment beyond what `py-flask-serve-split` was already scoped to build (§1.4) — no escalation from this question either.
