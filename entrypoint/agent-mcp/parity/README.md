# CLI-parity instrument (private, unpublished)

Line 1 of every `parity/*.mjs` is `// PARITY-INSTRUMENT-ONLY`. This directory is not in `tsconfig.lib.json` `include`, not in the build `cp` list, not in `package.json` `files`, and this README sits here (not at the package root) so the build's `cp *.md` skips it. Verification is `no-publish.e2e.test.ts` (walks `dist`, `npm pack --dry-run`, with a negative control).

## Scenario and arms
One scenario ("shopkit", two phases in one session; `fixtures.mjs`). One run per arm per round, ledger cap 3: **A** native `claude -p` (native default toolset only), **B** agent-mcp `claudecli` provider, **C** agent-mcp `anthropic` provider. B and C use only agent-mcp tools or MCP servers as shipped, with the PRODUCT DEFAULT shell allowlist and egress (R6-prep). The task prompt is byte-identical for every arm and names no tool or method (R3). Arm A runs first; B and C alternate order between rounds (`ledger.armOrderFor`). If A is not a genuine success (every content item green, not INVALID, no defect signal) the iteration is VOID: B and C are not run.

## Commands (`node entrypoint/agent-mcp/parity/drive.mjs ...`)
`--self-check` (no model call, no `claude`), `--print-plan`, `--check-oracle`, `--check-lib`, `--rederive-tools [--round R<n>] [--run <id>] [--emit-fixture]` (zero model calls, read-only: canonical per-tool counts of saved runs, see Tool names), `--rederive-duration [--round R<n>] [--rep n]` (zero model calls, read-only: wall and phase-sum durations, overhead split and B/A, C/A under both metrics, see Duration metrics), `preflight` (zero model calls, exit 0/3), `verdict --round R<n>`, `grid --round R<n>`, `--dry-run`, `--live --yes` (refuses, exit 3, unless every gate is green).

## Wire capture (R6B-proxy, opt-in)

Question it answers: what context does each arm actually SEND to the provider? Until now only arm C's request body was logged (`logs/api`); A's and B's were never captured, so contexts could not be diffed.

`capture-proxy.mjs` is ONE local reverse proxy for all three arms and every agent-mcp provider. Clients set their base URL to `http://127.0.0.1:PORT/<arm>/<provider>` (`<arm>` matches `[A-Za-z0-9_-]+`, `<provider>` is `anthropic|openai|deepseek`); the rest of the path (`/v1/messages`, `/v1/chat/completions`, `count_tokens`, ...) is appended and forwarded to that provider's upstream (`https://api.anthropic.com`, `https://api.openai.com`, `https://api.deepseek.com`, overridable with `PARITY_UPSTREAM_ANTHROPIC|OPENAI|DEEPSEEK`). Anything else is a 404 and is never forwarded. `openai.ts` only calls `chat.completions`, so `/v1/responses` is not exercised.

- Transparent (duration is a graded metric): request piped through, response chunks written to the client as they arrive (no SSE buffering), request headers forwarded except `host` (`accept-encoding` is kept), status and response headers unchanged, errors and 429s verbatim, nothing rewritten. The log copy of a compressed body is decoded after the fact from a tee; forwarded bytes are never decoded. Measured added latency against a local mock (p50, logging on): about 0.17 ms per request and per first SSE chunk (`measureOverhead`, recorded in every captured run as `record.capture.proxyOverheadP50Ms`).
- Logs: `<run>/logs/wire/proxy-<arm>-<provider>.jsonl`, events `session_start`, `raw_request` (verbatim body: parsed JSON, else base64), `raw_response` (verbatim body plus parsed final `usage`), `turn` (arm, provider, seq, model, `ms_first_byte`, `ms_total`, status, request/response bytes). Request headers and credentials are never recorded (keys travel in headers); `set-cookie` is dropped from response headers.
- Opt in with `drive.mjs --dry-run|--live --capture` or `PARITY_CAPTURE=1`. Default OFF: the plan, the env builders, `effectiveConfig` and the records are unchanged. When on, `record.capture` and `record.config.capture` say so.
- Wiring per arm (`drive.mjs captureEnv`): A sets `ANTHROPIC_BASE_URL=.../A/anthropic` in the `claude -p` spawn env; B sets it to `.../B/anthropic` in the agent-mcp server env and the claudecli child inherits it (`claudecli.ts buildSubprocessEnv` copies `process.env`); C sets `ANTHROPIC_BASE_URL=.../C/anthropic` in the server env because the Anthropic SDK in `providers/anthropic.ts` reads that variable itself and never receives the resolved `ADHD_AGENT_ANTHROPIC_BASE_URL`. B and C also set `ADHD_AGENT_OPENAI_BASE_URL=.../<arm>/openai/v1` and `ADHD_AGENT_DEEPSEEK_BASE_URL=.../<arm>/deepseek/v1` (the `/v1` is needed: `config.ts normalizeBaseUrl` only adds it to a bare host). Whether the real `claude` CLI under OAuth honours `ANTHROPIC_BASE_URL` is unverified until a live capture run.
- `node wire-diff.mjs <run-dir | logs/wire | proxy-*.jsonl ...> [--json]` (offline) prints per arm the system text, tool names, tool count and tools-JSON bytes, first-request message count and bytes, and per-turn input/cache usage, then a side-by-side delta of the arms' first requests (tools present/absent per arm, system text equal or not). "First request" is the first request that declares tools; the CLI's tool-less side calls are listed under the arm's model counts.
- The post-run secret scan (`scanAndLock`) runs over the whole run dir, so a secret-shaped string inside a logged body is redacted afterwards; the proxy itself records bodies verbatim.
- Tests: `capture-proxy-loopback.e2e.test.ts` (e2e lane: in-process loopback servers, mock upstream for Anthropic and OpenAI SSE, with negative controls) and `capture-proxy.e2e.test.ts` (`--dry-run --capture` against the real built agent-mcp). Tests cite "R6B-proxy AC1..AC6".

## Gate order
Implemented order (`gate.mjs` `GATE_ORDER`): `ledger` (read-only: `approvedBy` non-empty, cap) -> `scope` (scenarioSha vs previous round, LOG headings) -> `models` (the equal-model guard on the resolved experiment configuration, below) -> `judgeCredential` (presence only, no model call: `ANTHROPIC_API_KEY` or `ADHD_AGENT_ANTHROPIC_SECRET` in env or the `.env` cascade) -> `preflight` (zero model calls, never spawns `claude`) -> reservation. Any red or throwing gate exits 3 and leaves the ledger untouched. Nothing in the instrument reads the account usage window or throttles a run on it; the run cap (3 per round unless the ledger documents more), arm-A-first ordering, the scope gate, preflight, ledger accounting and the credential check are the only guards.

## Experiment models are configuration (SCOPE-R9-model-config)
Which model each arm and the judge runs is data, not code: `parity/experiment.json` defines the groups `A` (native `claude -p`, provider `claude-cli`), `B` (agent-mcp, provider `claudecli`), `C` (agent-mcp, provider `anthropic`) and `judge` (provider `anthropic`), each with a provider and a FULL model id. All are Anthropic-backed and share one id by default, `claude-haiku-5-5`. Environment variables override the file, so a different model needs no code change and no question to the owner:

| Variable | Effect |
| --- | --- |
| `PARITY_MODEL_A` / `PARITY_MODEL_B` / `PARITY_MODEL_C` / `PARITY_JUDGE_MODEL` | override ONE group |
| `PARITY_MODEL` | override every group |
| `PARITY_EXPERIMENT_FILE` | read another JSON file of the same shape instead of `parity/experiment.json` |

Precedence, highest first: per-group variable > `PARITY_MODEL` > the JSON file. `--print-plan` shows the resolved id of each planned arm and the judge with its source (`json` or the variable name), how it reaches the arm (A: `claude -p --model <id>`; B and C: the agent definition's `provider.model`) and the equal-model verdict.

Validation is strict and fails fast, naming the offending key, before anything plans, gates, reserves or spends (`drive.mjs` exits 2 with `CONFIG REFUSED`): an unknown top-level, group or per-group key, a group `provider` that is not the arm's provider, a non-string or empty id, an id with whitespace, an alias (`haiku`, `sonnet`, or any id without the `claude-` prefix and a version digit, so also `claude-haiku`), any id containing `opus` (the owner forbids opus; checked case-insensitively on the file, the alternate file and every environment value), a variable that is set but empty, a missing or unreadable `PARITY_EXPERIMENT_FILE`, and an unrecognised `PARITY_MODEL_*` / `PARITY_JUDGE*` name (for example `PARITY_MODEL_D`).

A round opts in with `ledger.profile.modelConfig: "experiment"` (R9 does), which is mutually exclusive with the legacy `model` / `judgeModel` / `armModels` profile fields. Rounds without it (R5-R8) never read the experiment file or the `PARITY_*` variables, keep their original model fields and re-derive exactly as before. The resolved ids are recorded on the run record (`record.modelConfig`, `record.config.modelConfig`, `record.model` as before), the ledger run entries (`runs[].model`, `runs[].modelSource`) and the judge calls (`judgeCalls[].modelId`, `modelSource`); runs are priced by the resolved id's rate card.

Equal-model guard (two layers, both before the first spend that could be wasted): the `models` gate refuses a configured round whose planned arms resolve to different pricing ids (`drive.mjs` `modelsGate`, `experiment.mjs` `modelConsistency`; two ids priced by the same rate card count as equal), unless the ledger profile records `modelDifferenceReason` (a deliberate, owner-approved difference); and the runtime `armModelGuard` starts a later arm only if arm A's response model equals the id that arm is configured with. Tests cite `PARITY-R9-cfg AC1..AC7` (`src/__tests__/parity-instrument/r9-cfg.test.ts`).

## Metrics (R4) and quality (R5)
Cost (billed, authoritative; common-card shown beside it) <= 1.02 x A, duration <= 1.02 x A, quality >= 0.98 x A (mean of 8 judged qualities). Turns, tool calls, peak context are report-only. n=1 per arm: fixed threshold, no significance claim. Billed vs common-card: billed uses the CLI `total_cost_usd` for A and tier-aware cache pricing for B/C; common-card prices all cache writes at the 5m rate. Both card-based numbers use the pinned model's rate card (`lib.RATE_CARDS`); see Model pin (R7-model).
The judge (`claude-haiku-4-5`, `judge.mjs` `JUDGE_MODEL`, a pin separate from the arms' model) is a PAID third-party call; it authenticates with the arm-C credential path (`ANTHROPIC_API_KEY`, else `ADHD_AGENT_ANTHROPIC_SECRET` from env or the `.env` cascade; auth shape chosen by token prefix as `providers/anthropic.ts` does; the secret is never logged). It sends no `temperature` (R8-judge: the model default, so scores are single samples, see below). It runs only from the driver in a live round (or `--rejudge` of a saved judge-failed run), after the oracle passed for A and the judged arm, with no env flag. Owner: the repository owner (skywinstonsk@gmail.com), recorded here, in the driver header and in the experiment LOG; it is deliberately not mentioned in the published `AGENTS.md`.

## Oracle scope change SCOPE-R5-oracle-model-and-leak (applies to every arm)
- `r1_model` scores TURN models only (`init.model` plus every assistant turn, parent and child). Models that appear only as `result.modelUsage` keys with no assistant turn are hidden helper calls (arm A's native WebFetch summariser); they are recorded as informational `observation.sideModels` and never scored, for A, B and C. Arm C's server-side web_fetch is not visible at all, so its `sideModels` is always empty (a measurement asymmetry, not a pass).
- `q_rate` is INVALID only when phase 2 read the leaked file (a parent or worker call naming docs/shipping.md or CHANGELOG.md, or a `docs/` wildcard read; `observation.phase2.workerCalls` carries the workers' calls) or the value is in phase-1 assistant text. A copy of the carrier rate in phase-1 docs/changelog that phase 2 never read leaves the answer judged, with the detail "leaked to <file> in phase 1, not read in phase 2".
- New scored content item `leak_internal_note` (F4): FAILS when docs/shipping.md or CHANGELOG.md contain the ticket's internal carrier rate or handling fee ("Internal finance note, not for customer-facing docs"). `na` for legacy expectations without a carrierRate. The R4 goldens score unchanged on every existing item and pass it.
- Driver exit status: `drive.mjs --live` exits 4 when the iteration is VOID because arm A is not a genuine success (B and C are not run), so a void never looks like success; 1 is a harness failure, abort or invalid run; 3 a red gate; 0 a clean plan. Per the owner rule, a void iteration is not a started iteration: release its run with `ledger.releaseRun` and move its run directory aside before rerunning.
- Tests: `entrypoint/agent-mcp/src/__tests__/parity-instrument/oracle-scope-r5.test.ts` (AC-MODEL-1, AC-QRATE-1, AC-LEAK-1, AC-EXIT-1) and the matching oracle self-test checks and mutants (`drive.mjs --check-oracle`).

## Reply selection (R5-reply, applies to every arm)

The scored reply of a phase is NOT the stream's last `result` frame: on a native run with background subagents the CLI emits a late notification follow-up turn after the real answer, and that turn becomes the final result. `oracle.applyReplySelection` (called at the end of `analyzeA` and `analyzeBC`, identically for A, B and C) picks the LAST assistant text of the phase whose last JSON object carries every required key (phase 1: `root_cause, ticket, owner, web_heading, flat_shipping_total, tests_pass, files_changed`; phase 2: `empty_cart_handled, tests_pass, carrier_rate, first_file_fixed, examples_updated`), falling back to the last non-empty assistant text. `<system-reminder>` blocks are stripped first, so notification-only text (and JSON echoed inside a reminder) is never eligible. The record carries `phaseN.replySource = {index, via: 'json'|'fallback'}` and `phaseN.replyTextRaw` (the stream value). No prompt, threshold or item criterion changed. Tests cite "R5-reply AC1..AC4" (`oracle.mjs` selfTest, `drive.mjs --self-check`).

## Judge reply parsing and `--reparse-judge` (R5-judge)
The judge reply must be exactly one JSON object; it may be wrapped in exactly one markdown code fence (` ```json ` or bare ` ``` `). Prose before/after, a second object or second fence, or an unclosed fence is `TEXT_OUTSIDE_JSON`; schema validation (8 qualities, integers 1-100, string notes) is unchanged.
`node drive.mjs --reparse-judge --round R5` re-parses saved `tmp/agent-mcp/parity/<round>/judge/<arm>.json` records that carry `error` + `rawResponse` with the current parser. ZERO model calls; the ledger (`judgeCalls[]`) is never touched, since the paid call was already logged. A repaired record gains `scores`, `notes`, `reparsedFromRaw: true`, `originalError` (the rejection code) and drops `error`; the arm's `record.json` quality block is updated the same way. It prints per-arm judge means and the C/A ratio against the owner gate (>= 0.98 x A) and never a round verdict.

## Output
Raw output goes to repo-root `tmp/agent-mcp/parity/<round>/` (gitignored). The arm working directory lives under the OS temp dir (`adhd-agent-mcp-parity/<round>/work`) so no repo or agent-instruction file sits above it; only an operator-supplied `--out` moves it under that directory (and `ancestorLeaks` then rejects an in-repo one). Every attempt of a runId gets a fresh, never-used work dir `work/<runId>-a<n>` (n starts at the ledger's runs+releases count for that runId and is bumped past any dir on disk; old dirs are never deleted). `prepare()` then fails closed if the repo holds any file outside the fixture set (a pre-spawn harness fault: nothing reserved, record `aborted`, retryable), and `record.json` carries `workDir` and `preManifest` (path -> sha256 of the repo before phase 1). Proven by the `R5-workdir AC1-AC3` self-checks.

## Ledger releases (R5-harness)
A run is reserved only after fixture preparation succeeds, immediately before the first model-capable spawn. A fault before that point records the arm as `aborted` (retryable) and consumes no run and never records arm A as a void. `ledger.releaseRun(round, runId, reason)` is the audited repair for a run that was reserved but provably never reached a model: it appends to `releases[]` and resets `armA` when A is released.

## Shell allowlist and egress (R6-prep AC2, supersedes the R3 "no curl" rule)
Owner direction: "drop all restrictions until you get the system working". B and C run the PRODUCT DEFAULT shell allowlist: `agentDef` sets `nativeTooling.shell: true` and passes no `allowCommands`/`allowPatterns`, so `DEFAULT_SHELL_ALLOW_COMMANDS` (which includes `curl`) applies. The instrument pre-writes no srt policy and adds no domain (`SRT_EXTRA_DOMAINS` stays empty); `ADHD_AGENT_SRT_SETTINGS` only points the server at an isolated, initially absent per-run file, which agent-mcp provisions with its default OPEN egress (allow-all loopback proxy). After each B/C run the driver reads the server's `Shell egress: open|restricted` startup line and the provisioned policy (`egressFactOf`) and records `record.shellEgress` ({mode, startupLine, policyMode, proxyPort}); a mode other than `open` adds a record warning. `--print-plan` states `Shell egress: open` and `effectiveConfig` carries `shellAllow`/`shellEgress`. The task prompt text is byte-identical for every arm and still names no tool or method; the scenario sha is unchanged (no scope change).

## Peak context (R6-prep AC3)
Peak context = max over phases of `phases[].tokens.total.ctx` (`metrics.peakContextOf`); report-only, never gating; shown in the verdict line and the grid metric line. Arm C per-turn context comes from the `message_start` usage (`lib.turnContextOf`); the billing usage (final `message_delta`, cumulative over server-tool iterations) is kept for cost only. `node entrypoint/agent-mcp/parity/rescore.mjs --round R5 --ctx` re-derives the context for a finished round with zero model calls into `<round>/rescore/ctx/` (new files only).

## Owner-directed retry (R5-retry, R5-resume)
- `ledger.retryPlan` (e.g. `[{"arm":"B","rep":2},{"arm":"C","rep":2}]`) replaces the seeded plan; the CLI still cannot slice it. It is honoured only with a non-empty `extraRunReason` (the owner direction, quoted), never contains arm A (A1 is the native reference and is not rerun), and rejects rep 1, unknown arms and duplicates (`ledger.retryPlanOf`, fail closed). Run ids are `<arm><rep>` (B2, C2); fixtures are seeded by rep, so a rep-2 run is a different (same-shape) instance. `c1_cache` treats C rep 2 as a warm repetition inside the 5 minute TTL: a retry hours later cannot satisfy it (instrument artifact; a process item, not part of genuineness).
- The loop stops at the first aborted or harness-failed retry arm (no loop).
- `ledger.judgeCapExtra` + `ledger.judgeCapReason` raise the judge cap above 3 (`ledger.effectiveJudgeCap`); the extension is bounded, the reason is recorded on each extra call, and the cap is checked before the paid call.
- Retry judge records go to `tmp/.../<round>/judge-rep<N>/<arm>.json`, never into `judge/`.
- `verdict|grid --round R5 --rep 2` reports A1 vs the rep-2 B/C (read-only).
- R5-resume AC1: on an idempotent resume (A skipped) or a plan without A, `state.aGenuine` is seeded from the finished A record AND the ledger `armA.genuine` (`seedAGenuine`); before this the judge was suppressed for later arms.

## Judge request, judge failures and `--rejudge` (R8-judge)
- The judge request carries NO sampling parameters (`judge.JUDGE_SAMPLING`, written as `sampling` into every judge record). Newer judge models (claude-haiku-5-5) reject `temperature` with HTTP 400, which failed the R8 B1 judge call, so it is omitted for every model instead of being retried on a 400 (a retry would spend a second paid call on an error-message match). Judge scores are therefore ONE sample at the model's default sampling: they are not deterministic and a re-judge of the same brief can differ. R5/R7 judge records were produced at `temperature: 0` and are not byte-comparable with a record whose `sampling` says otherwise.
- The judge's output ceiling is `judge.JUDGE_MAX_TOKENS` = 8000. A thinking-by-default judge model (claude-haiku-5-5) spends part of `max_tokens` on thinking blocks before the text, so the previous 1500 cut the R8 B1 re-judge off mid-JSON (`{"scores": {"spec_conformance`, stop_reason `max_tokens`). Every judge record now keeps `stopReason` and the content `blockTypes`, and a reply truncated at the ceiling is named `MAX_TOKENS` (not `NOT_JSON`).
- A failed judge call is never invisible. `quality.status` is `judge-failed` (the request was rejected or errored, or none could be built) or `judge-error` (the reply did not parse). Live, `judgeCalls[]` gets an entry for a `judge-failed` run: `status: "failed"`, `error`, `paidCallAttempted` (true when a request left the harness, false for a failure before one did, such as an alias with no reported id), tokens 0 and `costUsd: null` (unmeasured). A request that went out counts toward the judge cap (a rejected request is not provably free); a `paidCallAttempted: false` entry does not (`ledger.judgeCallsUsed`). The summary line prints the error or code, and the process exits `5` (`JUDGE_FAILED_EXIT`) when any run's judge failed (a harness failure/abort/invalid run still exits `1`, a VOID iteration `4`).
- `node entrypoint/agent-mcp/parity/drive.mjs --rejudge --round R8 --run B1 --yes` judges a SAVED `judge-failed` run once more, without re-running the arm. It rebuilds the brief from `tmp/agent-mcp/parity/<round>/live/out/runs/<run>/record.json` and the run's own final repo (`record.workDir/repo`), and refuses (no call) if that repo no longer equals the recorded `observation.files`, if the credential is missing, or if the record's quality is anything but `judge-failed` or a `judge-error` whose saved reply still cannot be parsed (so it cannot spend twice; a `judge-error` reply that parses under the current parser is repaired offline by `--reparse-judge`, no call). The final-state check compares the five tracked files in `observation.files` (`repoFilesOf`), not the whole tree; the record keeps no post-run tree manifest, so a change elsewhere in the repo is not detected by it (for B1 a one-off mtime check showed no file under the work dir changed after `finishedAt`). The previous `judge/<arm>.json` is kept as `<arm>.prior-<n>.json` before the new call overwrites it (`priorQuality.file` points at the copy). `--rejudge` is a paid call that does not re-check `ledger.approvedBy` (the original live approval stands; the judge cap still applies). It goes through the same `judgeRun` as a live round (cap check first, alias resolved from the id the arm reported, ledger entry for success and failure, the earlier error stored on the entry as `rejudgeOf`). Only `quality` changes in `record.json`; the earlier failure is kept as `priorQuality` (chained when re-judged more than once), and `score`/`observation` are written back unchanged. Exit 0 only when the re-judge scored.

## Scorer fixes and offline rescore (R5-scorefix)
- `x2_parallel` (B/C): the overlap is that of the INTENDED pair, the first group of two or more depth-1 child rows created within 2000 ms of each other (one `tasks_batch` creates its rows ~1 ms apart; `lib.intendedPairOverlap`). Extra model-chosen workers before or after the pair no longer enter an N-way intersection. With no such group the overlap is over all rows (negative for a sequential run). The observation records `pairBasis` and `pairRows`.
- `c1_cache` (C): the warm-repetition requirement applies only when rep 2 starts within the 300 s cache TTL of rep 1 (`oracle.CACHE_TTL_SECONDS`). A later start is `na` with detail "cold repetition by schedule". The gap is seeded from the rep-1 `record.json` on disk, so a separate retry pass has it (it used to be null there). An unknown gap is not excused.
- Judge brief format 2 (`judge.BRIEF_FORMAT`): server-tool results (web_fetch/web_search) are captured from the response stream and rendered in the transcript; an uncaptured result reads `(result not captured)` and a captured blank `(empty result)`. Every judge record carries `briefFormat`; records without it (all of R5 so far) are format 1, whose server-tool results were blank.
- `node entrypoint/agent-mcp/parity/rescore.mjs [--round R5] [--out DIR]`: zero model calls. Re-scores a round's finished records under the corrected scorers into `tmp/agent-mcp/parity/<round>/rescore/` (items, counts, diff, fidelity, verdict and grid per repetition). It first re-scores the stored observation unpatched and exits 3 if that does not reproduce the stored score. Raw records are never written.

## Model pin (R7-model, SCOPE-R7-model-sonnet)
Owner: "the experiment with sonnet instead of haiku". ## Tool names (I-toolname)
The same tool reaches the model under different names, so a raw tool name is NOT comparable across arms. The instrument keys per-tool counts on a canonical identity and keeps the raw spelling visible.

| tool (logical) | A: native `claude -p` | B: agent-mcp `claudecli` (host: claude CLI) | C: agent-mcp `anthropic` (host: engine) | canonical key |
|---|---|---|---|---|
| shell | `Bash` | `mcp__shell__shell_execute` | `shell__shell_execute` (the model sometimes emits bare `shell_execute`) | A `Bash`; B/C `shell__shell_execute` |
| read / edit / write files | `Read`, `Edit`, `Write` | `mcp__fs__read_text_file`, `mcp__fs__edit_file`, `mcp__fs__write_file`, ... | `fs__read_text_file`, `fs__edit_file`, `fs__write_file`, ... | A native name; B/C `fs__<tool>` |
| dispatch a worker | `Agent` (advertised as `Task`) | `mcp__agent-mcp__task` | `agent-mcp__task` | A `Agent`; B/C `agent-mcp__task` |
| collect a worker's result | inline in the `Agent` result | `mcp__agent-mcp__result` | `agent-mcp__result` | B/C `agent-mcp__result` (category `collect`) |
| ticket lookup | `mcp__r2info__get_ticket` | `mcp__r2info__get_ticket` | `r2info__get_ticket` | `r2info__get_ticket` |
| web fetch (differs in KIND) | native `WebFetch` | client-side engine tool `mcp__web__web_fetch` | Anthropic SERVER tool `web_fetch` (`server_tool_use`, executed by the API) | A `WebFetch`; B `web__web_fetch`; C `web__web_fetch` with `serverToolCalls` counting it |

- Canonical form: strip `mcp__`; a native built-in (PascalCase, no `__`) keeps its name; a bare name that matches exactly one advertised `server__tool` resolves to it (`lib.canonicalToolName`, `lib.toolNameFacts`); an ambiguous or unadvertised bare name is left bare, never guessed. The advertised list is the arm's own: A/B the CLI `init.tools`, C the request `tools`.
- Nothing is normalised away: `metrics.phases[].calls` carries `byTool` (canonical), `rawNames` (raw spelling -> count), `bareNameCalls` and `bareNameByTool` (calls where the model dropped the server prefix of an advertised tool; the product defect stays measurable), `serverToolCalls` (Anthropic server tools), `unresolvedBare`. A server tool's own bare name (`web_fetch`) and native tools are never counted as bare.
- Comparability: per-tool counts compare across arms at the canonical-tool level (the same logical tool, e.g. shell) or at the category level (`byCategory`) ONLY, never by raw name. Arms use different tool surfaces by design (A: Claude Code built-ins; B/C: agent-mcp `fs`/`shell`/`agent-mcp`/`web` servers), so even canonical keys differ for read/edit/dispatch/web; compare those by category. Categories (`lib.TOOL_CATEGORIES`): dispatch, collect, shell, edit, write, read, search, mcp, web, control (administration, scheduling, session and harness tools nobody dispatches work through); `other` means a tool the taxonomy does not know. The judge keeps its own transcript taxonomy (`judge.toolCategory`), unchanged so the judge brief sha does not move.
- Counting scope: `record.json` phase counts are the PARENT task only (A: parent turns; B/C: the root task of the phase). `drive.mjs --rederive-tools --round R8` re-derives counts over parent plus workers, and parent-only, from the saved logs (A stream files, B `spawn.stdout`, C `http.*` bodies) without writing anything. The committed fixture `golden/r8/tool-names.json` (names, kinds and advertised sets only) is its output for R8 and backs `--check-lib` and `src/__tests__/parity-instrument/tool-names.test.ts`.
- R8 reading: C1 shell = one key, 13 calls, 9 of them bare (parent 8 of 9); A1 and B1 have no bare calls. Existing records are not rewritten: their `byTool` keep the raw-name keys they were written with; use `--rederive-tools` for canonical numbers.

## Duration metrics and paired fixtures (R9-meas, SCOPE-R9-duration-metric, SCOPE-R9-paired-fixtures)
Owner decision on the duration metric (2026-10-12): **"Report both (Recommended)"**. The pre-registered rule stands: the new metric is NEVER the sole pass bar, and both are printed in every round.
- **Wall (graded, unchanged).** `record.wallMs` = the whole run, from the driver's start of the run to the end of analysis. It is still what `variantVerdict` gates on (`duration <= 1.02 x A`), and every verdict, grid line and SUMMARY column labels it `wall (graded)`. It includes harness work: fixture preparation, reservation, capture start, server start and `agent_create`, the submit calls, the hidden-suite runs between phases, the fixed 1500 ms pause before the usage queries, the usage queries, server/capture close and analysis. Arms B/C also include the driver's 2500 ms client poll lag (`waitTask` is unchanged, so R9 wall stays comparable to R8 wall).
- **Phase-sum (added, report-only).** `phaseSumMs` = the sum of `metrics.phases[].wallMs`: arm A the spawn -> exit of each `claude -p` turn, arms B/C the first poll after the task is submitted -> the poll that saw a terminal status, so the harness setup, teardown, submit calls, hidden-suite runs and the fixed pause are excluded and the server-side wait of the task is what remains. It is `null` unless every phase has a finite wallMs (never a partial sum). It is reported as `phase-sum (report-only)` next to the wall, in `formatVerdict` (`variantVerdict.durationPhaseSum`, `gating:false`, no `result`), in the grid metric line and in the SUMMARY.md `phase-sum s (report-only)` column. It never gates: wall over 1.02 with a phase-sum under it is a duration FAIL, and the converse is a PASS (tested).
- **Harness overhead, broken out.** Every record written from R9 carries `record.duration` = `{graded:'wallMs', wallMs, phaseSumMs, overheadMs, overhead}` (`metrics.durationBreakdown`, stamped by `drive.recordDuration`; `wallMs` itself is not touched). `overheadMs = wallMs - phaseSumMs`. For B/C the split comes from the run dir's `mcp-calls.json` call log: `setupMs` (run start -> first submit), `submitMs`, `betweenPhasesMs` (hidden suite + file reads), `accountingWaitMs` (= `fixedSleepMs` 1500 + `hiddenAndReadsMs`), `queriesMs`, `teardownMs` (server close, capture close, analysis), `residualMs` (clock disagreement, ~0). Also reported: `serverSumMs` (sum of the root tasks' `completedAt - createdAt` from `task_list`) and `pollLagMs` = phase-sum - serverSum, the client poll lag that is INSIDE the phase sum. Arm A has no call log, so its overhead is `{attributed:false, unattributedMs}`: nothing is invented.
- **`drive.mjs --rederive-duration --round R8`** recomputes all of this from the saved records and call logs and prints B/A and C/A under both metrics; it writes nothing (no record, ledger, summary or judge file; asserted by a directory snapshot test). Saved records are never rewritten. R8, verified from the saved records: A1 wall 85322 / phase-sum 84737 ms, B1 81144 / 77632, C1 121117 / 117756; **C/A 1.420 wall, 1.390 phase-sum; B/A 0.951 wall, 0.916 phase-sum**. (The earlier planning figure 1.391 came from dividing the rounded seconds 117.8 / 84.7; the unrounded ratio is 1.3896.) Poll lag inside the R8 phase sums: B1 3.96 s, C1 2.04 s; the server-side task intervals sum to 73.67 s (B1) and 115.71 s (C1).
- **Basis caveat.** The phase-sum of A (client-side process spawn -> exit) and of B/C (client-side poll interval) are different clocks, and the B/C figure carries the poll lag; the server-side sum is shown beside it for that reason. Do not read the phase-sum as a measurement of the model alone.

**Paired fixtures (`ledger.profile.pairedFixtures: true`, default off).** The per-run fixture values (package name, tax rate, free-shipping threshold, shipping rate, handling fee, ticket id, owner handle) and the seeded visible/hidden test cases are drawn from a PRNG keyed `seed|run|arm|rep` (and `seed|cases|arm|rep`, `seed|hidden|arm|rep`), so in R5-R8 A1, B1 and C1 got different thresholds (80/50/110), tax and ticket ids: a flagged confound. With the profile switch the streams are keyed by the pairing index n (= `rep`) only (`fixtures.makeSpec({paired:true})`, `valueStreamKey`): A_n, B_n and C_n then share every value, ticket text, repo, visible cases and hidden suite. Details:
- The system-prompt nonce stays PER ARM (`seed|sys|arm`): identical prompts across arms must not share a prompt-cache prefix. `runId` is still `<arm><n>`.
- Off by default and absent from `profileOf` unless true; a non-boolean value fails closed (`LedgerError`). The `paired` key is on a spec only when true, so every existing round (R5-R8) re-derives byte-identically (the whole unpaired fixture is hashed against the pre-change generator in `r9-meas.test.ts`) and stays re-scorable.
- Scenario sha: `currentScenarioSha()` identifies the scenario TEMPLATE (prompts, ticket structure, expectations of the canonical unpaired seed-20261011 A1 spec), not the per-run seeded values, so switching pairing on does not move it and R8's recorded sha stays valid for R8 (asserted). The pairing is recorded in the tracked ledger profile, on every record as `record.fixtures = {paired, valueStream}`, and in the scope log (SCOPE-R9-paired-fixtures). `specFor({seed, arm, rep, profile})` is the one place the profile reaches the spec: `makeCtx` and `--rejudge` both use it.
- Limitation: `rescore.mjs` regenerates `expected` with the unpaired derivation and would throw (fail closed, "regenerated expected.* differs") on a paired record; teach it `record.fixtures.paired` before rescoring an R9 round.

## Fair timing, evidence and analysis (SCOPE-R10-prep, PARITY-R10-prep)

Enabled per round by `ledger.profile.fairTiming: true` and `traceEvidence: true` (`ledger/R10.json`, which is **not an approval**: `approvedBy` is empty, so `--live` is refused by the ledger gate). Every record written before R10 is untouched; R5-R9 re-derive byte-identically (`--rederive-duration`, `--rederive-tools`, `verdict`, `grid` compared with `cmp`).

**Fair timing (`timing.mjs`).** The graded wall is the sum of the product windows: A = the `claude -p` turn is spawned and the prompt written -> the `result` stream event; B/C = the `task` call is issued -> the server's own `completedAt`. C waits with `result {wait_ms}` long-polls (no poll interval), and the accounting step is a bounded condition wait (`waitUntilStable`: two identical consecutive `usage_query` reads, 50 ms apart, 5 s deadline), never a fixed sleep. Everything else is split into the same named segments for every arm: `setup | lag | verification | handoff | accounting | teardown`, residual 0 by construction (marks `run.start, p<i>.start/engineEnd/observed/hiddenDone, accounting.done, run.end`). Boot is reported beside the split (A `p<i>.initMs`, C `serverConnectMs`) and not subtracted: it is product time.

**Evidence (`evidence.mjs`, schema `parity-evidence/1`).** Each run directory gets `evidence.json` (redacted, deterministic) and `evidence/threads.jsonl` (full per-thread output, gitignored with `tmp/`). Sources: the wire capture (arms A and C), the API log (joined by body sha256 to task/agent), the agent-mcp tracing plugin output (arm C; the instrument pins `ADHD_AGENT_TRACING_LOG_SINK=file` and `ADHD_AGENT_TRACING_LOG_DIR=<run>/logs/trace`; `captureArgs` stays off) and `mcp-calls.json`. Recorded: threads (keyed by the TEXT of the first message), tools offered per request, thinking per block as `{chars, signaturePresent, state}`, delegation mode (`sync` unless `background`/`run_in_background`), tool timings and same-turn overlap, RT1-RT6 facts. **The Anthropic API returns thinking blocks with a signature and no text** (`state: omitted`); the absence of text is not evidence about the model, and the harness never says otherwise. The bundle holds no page text, prompt text, tool-result text, thinking text or signature; `leakScan` fails on key shapes, 120+ char opaque runs, `FAKESIGNATURE` and the page heading.

**Analysis commands (read-only, zero model calls).**
`node drive.mjs analyze <round> <runA> <runC> [--section gap|threads|blocking|surplus|tools|contamination|rt|evidence|wall|all]` where a run is a run id or an `evidence.json` / golden bundle path; `node drive.mjs analyze --emit-bundle <runDir> [--arm X] [--out F] [--redact-spans]`. Sections: wall-gap reconciliation (gap = per-phase delta + poll lag + harness overhead, residual 0), per-thread counts, parent blocking on sync delegation, worker-request surplus by purpose, tools-offered diff, contamination matches (q_rate style probe, minimal span, phase and channel), RT1-RT6. The R9 numbers reproduced from the saved records: gap 17.780 s = +9.246 +3.549 +2.208 +2.777; C parent blocked 19.167 s and 13.537 s (tracing spans 19.128 / 13.524 s) on SYNC delegation while A launched its workers in the background; worker requests C 18 vs A 10; tools offered parent 34 vs 25, worker 33 vs 4. Tests use `golden/r10/r9-{A1,C1}.bundle.json` (made with `analyze --emit-bundle <R9 run dir> --redact-spans`; regenerate the same way); they never read gitignored data.

**Wall attribution (`--section wall`, R10 M1).** Reads the R10 trace signals (tracing README, "Wall-time attribution signals") from the evidence bundle's `trace` and prints, for arm C, one line per task thread and one line per dispatched child, then the model-call table. Nothing is hand-joined and nothing is guessed: a quantity the trace does not carry prints `n/a (...)` or `unmeasurable (...)`, never `0`.
- Task thread: `wall_ms`; startup `tools_ready_ms` with `connect_ms` per MCP server and `queue_wait_ms` / `session_ms` (stamped by the product on dispatched children since R10 M2; `n/a (not recorded)` on a task with no dispatching parent or from an older build); `queued_ms_sum` over the thread's barrier waits (`n/a` when no call recorded `queued_ms`); `model_ms`, `tool_ms`, and `idle_ms = startup <tools_ready_ms> + unexplained <rest>`. The unexplained remainder is idle_ms minus the startup span and is printed as is (a negative value means an inconsistent record and is not clamped).
- Dispatch: `kind`, `mode` (sync | background), `children`, `parent_blocked_ms`, `wait_ms`, `call_id`, and per child `child_prestart_ms` = the child's `agent.task` start minus the start of the parent's `agent.tool_call` whose call id equals `agent.dispatch.call_id` (the child is found through `agent.dispatch.child_task_ids`; starts are the `.start` records' timestamps, never end minus duration when a start record exists). Missing `call_id`, missing `child_task_ids`, a missing tool_call or child task record, or a child that would start before its dispatching call prints `child_prestart_ms=unmeasurable (<reason>)`. A `result` wait (`kind: result`) starts no child and prints its `wait_ms` only. When the child's `queue_wait_ms` and `session_ms` were both recorded, the span is printed split: `child_prestart_ms=5 (queue_wait_ms=0 + session_ms=2 + remainder 3)` (the remainder is unclamped, so an inconsistent record shows as negative). A `tasks_batch` dispatch prints one line per child, each against the same dispatching call.
- Model calls: `thinking_config` and `thinking_blocks` are always printed on the same line. `none` is spelled `none (no thinking field sent (API default; may still think))`, because the R9 finding is that omitting the field does not stop the model emitting thinking blocks; a count line reports how many calls were `none` AND returned thinking blocks. A provider that does not report them (OpenAI-compatible, claudecli) prints `n/a (not reported by this provider)`.
- Arm A: `n/a (native arm has no trace)` (the native CLI has no tracing plugin; A's numbers are never derived). Arm C with an empty `logs/trace`: `n/a (no tracing-plugin output was captured ...)`. A bundle made before R10 (the committed r9 goldens): `n/a (the trace holds none of the R10 wall-attribution attributes ...)`.
- Output compatibility: `wall` is appended last, so `--section all` is the pre-M1 output followed by the two wall sections, and every pre-existing section is byte-identical (cmp against `golden/r10/m1-baseline/`, captured before the change).
- Fixtures: `golden/r10/r10-m1-dryrun-C1.trace.jsonl` is the real tracing-plugin output of a mock-provider run through the built server, captured before R10 M2 so the children carry no `queue_wait_ms` / `session_ms` (filtered to the records the reader uses); `golden/r10/r10-m1-synthetic-C1.trace.jsonl` is hand-built in the sink's record shape and carries what the real run does not emit (a background dispatch, a `result` wait, `queued_ms`, `wait_ms`, startup `queue_wait_ms` / `session_ms`, two dispatch calls in one parent turn). Tests: `src/__tests__/parity-instrument/r10-m1-wall.test.ts` (unit) and `r10-m1-wall.e2e.test.ts` (fresh dry run through the real server, `analyze` as a subprocess), citing `R10 M1 AC1-AC7`.

**Product changes are out of scope.** If the evidence points at agent-mcp behaviour (for example C sending no `thinking` field, or 33 tools offered to a worker), the harness reports it; it does not change product code.

## Thinking parity (SCOPE-R10-thinking-parity, R10 launch prep)

Why: the R9 wire capture showed arms A and B sending `thinking: {"type":"adaptive"}` while arm C (the anthropic provider) sent no thinking field, so the arms were not asking the model the same thing. The product can now send it (R10 S1 P7: agent definition `provider.thinking` = `{type:'adaptive'|'disabled', display?:'summarized'|'omitted'}`, anthropic provider only, spread next to `output_config.effort` only when set). This is an instrument / experiment-configuration change; it is **not** a product default change.

- **Configuration.** `experiment.json` group `C` carries `"thinking": {"type": "adaptive"}`; groups `A`, `B` and `judge` carry none. `experiment.mjs` validates the key strictly (the product's `anthropicThinkingSchema`: `adaptive` with an optional `display`, or `disabled`; the legacy `enabled` / `budget_tokens` form and any unknown key are refused with the offending key named). Precedence, highest first: `PARITY_THINKING_C` (a JSON object, or the literal `none` to remove it; set-but-empty or malformed is refused naming the variable) > the JSON file. `PARITY_THINKING_A|B|JUDGE` and `PARITY_THINKING` are refused as unknown variables.
- **Anthropic-backed arm only.** Thinking parity applies to arm C (the agent-mcp anthropic provider). Arms A and B run the `claude` binary, which decides its own thinking (live: `adaptive`), and the judge is a direct call the driver passes no `provider.thinking`; the per-group schema therefore **rejects** a `thinking` key on `A`, `B` and `judge` with a clear error. The OpenAI / DeepSeek adapters are not arms of this experiment, so there is nothing to configure for them (their handling of the option is the product's, recorded in the S1 correction-by-adapter table).
- **Opt-in per round.** The resolved thinking reaches arm C only for a round whose tracked ledger lists `SCOPE-R10-thinking-parity` in `scopeChanges` (R10 does). Rounds R5-R9 keep sending no thinking field, so their plans, records and re-derivations are unchanged by editing `experiment.json`. A round listing the scope needs a dated `### ... SCOPE-R10-thinking-parity` heading in the LOG before the round starts (the scope gate).
- **Both definitions.** `drive.mjs providerFor` sets `provider.thinking` on arm C's agent definition exactly where it sets `provider.effort`; the parent and the worker definition both come through it.
- **Verification.** Every gated record carries `record.thinkingFacts` (`thinkingFacts` in `drive.mjs`, wire side `wire-diff.wireThinkingFor`): per arm, the requested option versus the full `thinking` object of every main (tool-declaring, workers included) request on the wire, with a one-line verdict printed per run. An existing path or branch is refused before anything is reserved; the harness never removes a worktree or branch, never checks out in the repo root and never touches main. The preflight checks only arms that hold no ledger run, so a resumed round (B ran, C pending) is not wedged by B's own worktree.

**Sandbox write widening (read this before spending).** The sandboxed shell can write its cwd, but a linked worktree keeps its git state in the MAIN checkout's `.git`; measured in the dry run, the default policy refuses `git commit` there (`Unable to create '.../.git/worktrees/<name>/index.lock': Operation not permitted`, then `packed-refs.lock`). The set is printed in `--print-plan` and recorded in `record.config.sandboxWriteExtras`.

**Pre-commit hook hazard.** `core.hooksPath` is `.githooks`; its pre-commit runs in the group worktree on every commit and a fresh linked worktree has no `node_modules`. The harness never passes `--no-verify`, never edits hooks and does not link `node_modules`; `record.worktree.hooksPath` / `nodeModulesPresent` / `uncommitted` say what happened, and a refused commit shows as a gap or a named failing step.

The harness itself only reads: `makeBacklogReader` refuses every verb except query/get/search/report/lookup and never passes `--allow-production-write`. The picked item is taken from the backlog-operator's own tool calls (a before/after diff of a shared store would include other writers).

No judge, no oracle, no verdict or grid (those modes refuse on a design round). A harness failure stops the round (exit 1); an agent that fails is a result. ## R12: the backlog-operator design with CLI access (SCOPE-R12-schema-and-scope, SCOPE-R12-backlog-cli, owner-directed)

The same design as R11 (groups B and C only, one manual run per group, no retry, the same `TASK_PROMPT`, the same roster bodies, the same stop condition), with one change of mechanism, selected by the ledger ROOT key `backlogAccess: "cli"` in `ledger/R12.json` (absent or `"mcp"` is the R11 shape, byte for byte; any other value is refused). Owner direction (verbatim): "you could easily just give that agent the cli instead". R11 is spent (`ledger/R11.json` records B1 and C1) and is never edited; R12 has its own ledger (cap 2, no runs yet), worktrees `.worktrees/r12-B` / `.worktrees/r12-C` on `parity/r12-B` / `parity/r12-C`, and its own `--round R12` commands.

**Commands.** `drive.mjs --print-plan --round R12`, `drive.mjs --round R12` (the offline dry run: fakes, a throwaway repository and a stand-in `adhd-backlog`; exit 0, prints the flow section), `drive.mjs analyze R12 B1 C1 [--section ...]`, and the paid path `node entrypoint/agent-mcp/parity/drive.mjs --live --yes --round R12` (owned by nix; the same gates as R11).

**CLI, not MCP.** The `backlog-operator` definition carries NO backlog MCP server. It runs `adhd-backlog <verb> --input '<json>'` (`entrypoint/backlog/skill/SKILL.md`) through its shell tool. Writes need the typed `--allow-production-write` switch, which the CLI itself requires on the production store (the refusal text names it); the harness reader never passes it and refuses every write verb. The shell tool is a `mcp-shell-server` argv allowlist behind the exit-status shim; a supplied `allowCommands` REPLACES the product default in full, so the operator's list is the product default (`DEFAULT_SHELL_ALLOW_COMMANDS`, read from this checkout's built `agent-core-native-tooling`, else its source) plus EXACTLY `adhd-backlog`, identical in B and C. It is recorded in `record.config.shellAllowCommands` (list + sha256), `shellAllowAddedToProductDefault` and `shellAllowProductDefaultSha256`, compared across the groups by `identicalGroupsCheck`, and hashed into the scenario sha. The sandbox write set reuses the `sandboxWriteEnv` `keepDefaults` (`~/.adhd/backlog/production/data`, which holds the SQLite store); nothing else is widened for the backlog. Measured (read verbs only, against the production store, both arms, through the real built server): the CLI runs under the shell guard and the srt policy, finds its data dir with the shell child's PATH-only environment, and returns its envelope; `env` and `which` are rejected by the shell server, so the operator cannot inspect its environment.

**Project scope is not cwd-derived.** Measured on `adhd-backlog` 1.0.16: the CLI is not scoped by the shell cwd and has no project option or environment variable (`ADHD_BACKLOG_SCOPE` selects the store/namespace, not a project). The project is a per-call `filter.project` (uid or name) inside `--input`, and the production store holds every project of the machine (the `adhd` project alone has on the order of a thousand non-terminal items). The harness therefore resolves this repository's project from the registry at run time (the project whose registered path is the main checkout, else the one named like its directory, else UNRESOLVED; never a hard-coded uid) and records it in `record.config.backlogScope` (`cwdDerived: false`, the resolved project and how). The roster prompt is not changed, so the only guard against an out-of-repo pick is the S1 verdict below.

**Selection stage S1 (redefined).** PASS only when backlog-operator was dispatched through agent-mcp AND a specific item uid was selected, where the uid appears in a SUCCESSFUL `adhd-backlog` get / claim / transition shell call in the operator's task record (never in a query result: a query lists many uids and selects none), the item is non-terminal and unblocked in the before-snapshot, and it belongs to this repository's project. FAIL with a named reason otherwise: `out-of-repo-pick` (names uid, project and component), `operator-died` (the task failed / was cancelled / timed out before selecting; names the failing step and the last tool error), `operator-stopped` (completed without selecting), `operator-not-dispatched`, `terminal-before`, `blocked-before`; `unknown` (never pass) when the project or the before-snapshot cannot confirm it (`project-unresolved`, `before-unconfirmed`). S2-S5 are as in R11; S5 matches the operator's successful `transition` CLI call (a unique uid prefix, which the CLI accepts, is matched to the full uid) plus the read-back status change.

**Snapshot.** The ready view cannot be paged (measured: it ignores `offset` and `after`, `has_more` stays true, `limit` is capped at 1000; R11's before-snapshot recorded 20 duplicate pages). `record.backlog.before` is therefore the repository project's non-terminal items from the `list` view (`filter.status: "open"` = every non-terminal status), paged by offset until the reported total is read, each with `project`, `component` (uids; names from the registry views in `record.backlog.registry`) and its blockers; `complete` is true only when every reported item was read once without an error. The ready view's first page is kept as a membership probe (`readyUids`, `readyTruncated`). `record.backlog.item` classifies the picked item `in-repo` / `out-of-repo` / `unknown` from state and reports non-terminal / unblocked before and the before -> after status.

**Record.** Every call in `record.toolCalls` has a task-unique `id` (`<taskId>:<call id>`, because the claudecli bridge restarts `bridge-N` per task) and a `ts` with its source (the agent-mcp trace `tool.call` event; arm B pairs by order only when the counts and tool names agree, otherwise `ts` is null, never invented); long results keep head and tail (the `[exit status: N]` sentinel survives); `record.failure.detail` is whole (the R11 record cut it at 300 characters). `record.failure.toolErrorGroups` classifies repeated failures as `tool-error` (the engine rejected the call), `refusal` (ran and was refused) or `nonzero-exit` (an ordinary probe); only the first two are bug candidates. R11's matcher counted isError OR error-like text under one (task, tool) key, which is why B1's 3 `Unexpected shell operator` rejections plus one `ls` that exited 1 read as 4. `record.failure.bugCandidate` is `{operatorDied, operatorStopped, repeatedToolErrors, any}`. `record.worktree` adds `uncommittedChanges` (status + path per group worktree), `uncommittedCount` and `backlogMdHandEdited` (a `BACKLOG.md` edit, committed or not; the graph is the source of truth); the harness only reports and never reverts, restores or deletes anything.

**Dry run.** The operator calls a stand-in `adhd-backlog` (`dryrun/fake-backlog-cli.mjs`, a `#!/usr/bin/env node` executable first on the server PATH, state and log in the throwaway repo) from the REAL sandboxed shell, so allowlist, PATH, interpreter and sandbox-write failures show up offline. The stand-in mimics the measured real CLI contract (one envelope line, `--input`, the typed production-write refusal, an unpageable ready view, project / component uids, prefix uids). Scripted operator modes for the negative controls (`PARITY_FAKE_BO_MODE`): `ok`, `other-project`, `stop`, `die`, `noflag`. Proof: `r12-cli.test.ts` (unit) and `r12-design.e2e.test.ts` (e2e), every test citing its `R12 AC`.

**Not verified offline.** A real `claim` / `transition` under the srt policy needs a write to the production store, which no offline test may do. The policy allows `~/.adhd/backlog/production/data`; `config.yaml` and `backups` are denied. If the first live write fails with an EPERM the failure is named in the record (S1/S5 failing step), not hidden.

## What this harness may signal (PARITY-R10-prep AC4)

The live driver spawns `claude -p` (arm A) and an agent-mcp server (arms B/C). It may send a signal to a process **only** when all of these hold at the moment of the call (again before any SIGKILL that follows a SIGTERM):

1. the pid is an integer greater than 1, is not the driver itself and is not an ancestor of the driver (the interactive claude session that launched it is one);
2. it is a **root the driver spawned itself** (`OwnedRegistry.add` right after `spawn`, which requires the child's ppid to be the driver) whose `ps` start time still equals the one recorded then (a recycled pid is not ours), or a **descendant** of such a root computed from the live process table at that moment;
3. a process-GROUP signal (`kill(-pgid)`) needs more: the registered root created the group (`pgid === pid`), the pgid is not the driver's group or any ancestor's group, and every member of the group is the root or one of its descendants.

There is no signal by name or pattern anywhere (`pkill`, `killall`, `kill -`; the static audit in `r10-killsafety.test.ts` fails if one appears), and with no registry nothing is signalled. Sites: `lib.mjs` `sweepPids` (TERM then identity-checked KILL), `killOwnedGroup` (the timed-out `claude -p` turn), `alive` (signal 0 probes existence only); `drive.mjs` calls them through `sweepOwned` and the turn timer. Proof: `r10-killsafety.test.ts` (each guard by its refusal code over synthetic process tables) and `r10-killsafety.e2e.test.ts` (real processes: a bystander and an ancestor are attacked five ways and stay alive; five in-test mutants of `lib.mjs`, each with one guard removed, DO kill them).

**What the spawned `claude -p` shares with the user's `~/.claude`.** `HOME` and `CLAUDE_CONFIG_DIR` pass the env allowlist, so arm A uses the user's own login and appends its session transcripts to `~/.claude/projects/<slug of the run's temp work dir>/` (one directory per run work dir, never cleaned by the harness). `--setting-sources project` keeps user settings, hooks and CLAUDE.md out of the run. The harness never reads, edits or signals the user's other sessions. Other machine effects: temp work dirs under the OS temp dir and `tmp/agent-mcp/parity/<round>/`, the pinned tracing sink under the run dir, the production backlog store directory being on the default `extraAllowWrite` of the agent-mcp sandbox (the harness does not write to it).
