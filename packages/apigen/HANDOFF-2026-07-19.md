# HANDOFF — apigen re-export/OOM/v1-retirement work (2026-07-19)

**Written:** 2026-07-19 · **Status: IN PROGRESS. Nothing published. Nothing externally verified. Do not publish from this state without the follow-up work below.**

---

## TL;DR

A real, user-triggered bug (`@adhd/apigen-cli` silently extracting only 2 of ~140+ operations from a re-export-heavy TypeScript file) turned out to have **three layered root causes**, discovered progressively across this session, each one hiding behind the previous "fix" looking complete. The first two layers are genuinely fixed, merged to `main`, and pushed. The third layer — the one that actually explains why real CLI usage was still broken even after the first two fixes — is **currently being fixed by a dispatched agent, in an isolated worktree, not yet merged.**

**Nothing in this entire effort has been verified outside this monorepo's own workspace.** No real `npm install`, no real publish, no code review by anyone other than the author (me, reading my own and a dispatched agent's diffs). That is the single most important thing for whoever picks this up next to internalize before doing anything with `nx release`/`npm publish` again.

---

## What's actually done, merged to `main`, and pushed to `origin/main`

All on the `adhd` repo, `main` branch, most recent relevant commit `908d843b` (as of this writing; the in-progress work below will add more on top once it lands).

1. **BUG-APIGEN-CORE-002** — `extract()`/`extractClasses()` in `packages/apigen/apigen-core-client/src/lib/extract.ts` / `extract-classes.ts` never followed `export { x } from './other.js'` re-exports. Rearchitected around `sf.getExportedDeclarations()`. **Verified**: 236/240 → 240/240 unit tests, plus a direct scratch-script call of the raw function against `~/dev/ai/sox-ecosystem/libs/memory-core/src/index.ts` returning the correct 146 operations (140 function/const + 6 class-derived). This verification called the extractor function directly — not through the CLI.

2. **BUG-APIGEN-CORE-003** — `buildSchema()`'s session cache stored resolved values, not in-flight promises, so concurrent identical type-resolution requests (e.g. many properties independently needing `SharedArrayBuffer`) all missed the cache simultaneously and each redundantly recomputed — a genuine cache stampede, and each redundant computation forced a full ts-morph `Program` rebuild that never got released, causing an OOM. Fixed by caching in-flight promises. A second bug (a real deadlock, not present before the first fix) was found live during verification — self-referential/recursive types would join their own ancestor's pending promise and hang forever — fixed with an explicit ancestor-tracking guard. **Verified**: real, unstubbed `extract()`+`extractClasses()` against the same fixture completes in ~6.6-10.9s at a memory cap that previously OOM'd, 146/146 operations. Again — direct function call, not through the CLI.

3. **BUG-APIGEN-CORE-004** — `isSerializableType()`'s textual heuristic doesn't recognize `Record<K,V>` as serializable, so two legitimately-serializable consts get silently skipped. **Filed only, not fixed.** Low severity, narrow scope.

4. **BUG-APIGEN-018** — `apigen-cli/vite.config.ts`'s `copyDefaultTsconfig` plugin wrote to `dist/apigen-cli` instead of `dist/entrypoint/apigen-cli` (missing a path segment), so a shipped-asset optimization silently never worked (self-mitigated by a fallback, no functional break, just always-slow-path + build litter). **Fixed and verified.**

5. **Release-tooling fix**: `apigen-cli`'s own test suite ships fake npm-registry fixtures with real `package.json` files. Nx's inferred-project detection registered them as real projects, and `nx release version` hung indefinitely (16 minutes, near-zero CPU) trying to interactively prompt for a version bump on a fake test package with no stdin available. **Fixed** via `.nxignore` + a follow-on eslint `ignorePatterns` fix (excluding the fixtures broke `apigen-cli`'s own lint scope in a different way; also fixed).

6. **`decimal.js` dependency declarations** — fixed correctly and differently for two packages: `apigen-core-client` (genuinely test-fixture-only → `ignoredDependencies`) and `apigen-cli` (a real runtime optional-peer probe in `run.ts` → real `peerDependencies`/`peerDependenciesMeta.optional`).

7. **FEAT-APIGEN-019** — filed as HIGH: the CLI has no way to list available `--type` plugins, `--help` text is stale/hardcoded (missing 2 real plugin ids) or empty (for `run`/`run-registry`), and the error on an unknown `--type` is inconsistent — `generate` lists options correctly, `run` gives a misleading "doesn't support run mode" message even for a typo'd, nonexistent type (confirmed live: the user hit exactly this with `--type express` instead of `api-express`). **Filed only, not implemented** — got superseded in priority by the discovery below.

## The bigger problem, discovered after all of the above looked "done"

Even with BUG-APIGEN-CORE-002/003 fixed and verified in isolation, **running the actual shipped CLI** (`apigen run --type api-express --source <file>`) **still only exposed 2 endpoints.** This is because:

8. **The CLI's default path never called the fixed extractor at all.** `generate`/`run` call `runPipeline()` → `generateSchemas()` — an entirely separate, older ("v1") extraction implementation (`extractors/named.ts` etc.) with the *identical* re-export bug, independently implemented, never patched. The fixed v2 `extract()` was only reachable via an opt-in `--v2` flag. `generate-registry`/`run-registry` had **no** `--v2` escape hatch at all — always v1, unconditionally. `serve` spawns child `run` processes without ever passing `--v2`, so it inherited the same default-broken behavior transitively.

   Root cause of *why* this happened (not a mystery, well-documented): a single large commit (`556d02ee`, "apigen v2 — 18-package TS→API toolchain") built a whole new v2 system and integrated it via a cautious `--v2` opt-in rather than a hard cutover — reasonable for an 18-package rollout — but the follow-up step of flipping the default or retiring v1 was never done, and nothing in that plan's own completion doc (`docs/plan/apigen-client-generation/RESUME.md`, "PLAN COMPLETE... NOT committed") tracked it as remaining work.

9. **Even `--v2` doesn't actually fix it.** This is the layer that fooled me initially. The "v2 orchestrator" (`entrypoint/apigen-cli/src/lib/orchestrator.ts`) does Steps 1-4 (detect→extract→merge→collision-check) using the genuinely-fixed v2 `extract()`, and correctly logs `"merged 140 total operations"`. **But Step 5**, which builds the actual schema object every output plugin (`api-express`, `api-fastify`, `mcp`, `cli`, `jsonschema` — all of them) consumes to register routes/tools, calls `generateSchemas()` **again**, independently, from scratch — the same buggy v1 function. The code's own comment says why: *"the v1 OutputPlugin interface speaks ComposedSchemas, not Operation[]... ComposedSchemas is a derived v1-compat projection."* The 140-operation count from Steps 1-4 never flows downstream; it's used only for logging and collision-checking. **Confirmed empirically, not just by reading code**: after a `--v2 run`, curling routes beyond the first two (e.g. `/namespace/memoryCurate`) returned a 404 HTML page, and `grep -c '"method":' <full server log>` returned `2`, not 140, even after 12 seconds of runtime — ruling out truncation.

## Currently in progress — not yet merged

A dispatched agent (isolated worktree, branch not yet identified in this doc since it hasn't reported back) is:
- Rewriting orchestrator.ts's Step 5 to derive the plugin-facing schema shape directly from the already-correctly-extracted `operations` (Steps 1-4's output), instead of calling `generateSchemas()` a second time. Reuses the existing `composeSchemas()` (confirmed to be a pure function, not part of the v1 bug).
- Adding a `hasCtx?: boolean` field to the `Operation` type (v2), which v1's shape carried and which the ctx-first-param dispatch re-injection logic (BUG-APIGEN-001) depends on.
- Deleting the v1 pipeline entirely once nothing calls it (`pipeline.ts`/`runPipeline`, `generate-schemas.ts`/`generateSchemas`, the three v1 extractor files) rather than leaving two parallel implementations that can drift again.
- Wiring `generate`/`run`/`generate-registry`/`run-registry` to unconditionally use the fixed path (removing or deprecating the `--v2` flag).
- **Told explicitly, mid-task, to re-verify with curl against multiple non-first routes** — not log-line counts — after I caught myself trusting a misleading log line earlier in this exact session.
- Separately flagged (not fixing, correctly scoped as out-of-task): v1's `--export` flag let you scope extraction to exactly one export shape (named/default/named-object); v2's `extract()` always extracts every shape unconditionally. This is a real behavior change from v1, not a regression in the fix — will be documented, not fixed, as part of this task.

## What is explicitly NOT verified — read this before touching `nx release` again

1. **No integration test outside this monorepo, at all.** Every test above ran against source or `dist/` *inside* this workspace, where every `@adhd/apigen-*` package resolves via Nx workspace linking. Nothing has been tested the way a real consumer experiences it.
2. **No successful publish has happened.** The one `nx release` attempt hung on the fake-fixture-project bug (now fixed) and was never carried through to an actual `npm publish`.
3. **Confirmed, independently, via `npm pack` + install in an isolated scratch directory (not just theorized): even a fully correct, fully fixed `apigen-cli` would be uninstallable by a real consumer right now.** Six internal dependencies it declares — `@adhd/apigen-base-logical`, `@adhd/apigen-engine-runtime`, `@adhd/apigen-engine-naming`, `@adhd/apigen-python-env`, `@adhd/apigen-plugin-py-flask`, `@adhd/apigen-plugin-py-grpc` — 404 on the real npm registry (confirmed via `npm view` on each). This is a completely separate, unresolved blocker from everything else in this document, discovered while attempting the original publish and never addressed. **Do not attempt a real publish until this is resolved one way or another** (publish those six too, in dependency order, after auditing each one's own readiness — or fall back `apigen-cli`'s dependencies to the older, still-published names, which carry none of today's fixes and are known to have their own problems, e.g. `apigen-runtime` crashing on import).
4. **Only `api-express`'s `run` mode was curl-tested, against one fixture file.** `api-fastify`, `mcp`, `cli`, `jsonschema`, `py-flask`, `py-grpc` have not been exercised end-to-end with the fixed pipeline at all. Since the newly-discovered Step 5 bug is shared infrastructure feeding *every* plugin, and the in-progress fix touches that shared layer, **every plugin needs its own independent verification** once the fix lands — a fix that makes `api-express` work is not evidence the others work.
5. **`generate` mode (writes files to disk instead of running a live server) was not curl/output-tested this round** — only inferred from a log line, which is exactly the mistake this document exists to prevent repeating.
6. **`serve` (multi-source, multi-language front server) was not tested at all.**
7. **`generate-registry`/`run-registry` (multi-package discovery) were not tested at all** with any real fixture.
8. **No code review has happened, by anyone other than the author, on any change made today.** I read my own and the dispatched agent's diffs before merging the first two rounds — that is not independent review.
9. **The in-progress Step 5 fix is not yet merged to `main`** — it's sitting in an isolated worktree as of this writing.

## Explicit ask for whoever picks this up (including future-me)

- **Code review across all plugins is needed before any merge or publish** — specifically because the Step 5 rewrite touches shared infrastructure that every `OutputPlugin` depends on, and only one plugin (`api-express`) has been exercised at all.
- **Before any real `npm publish`**: resolve the six-missing-package install-chain problem. This is independent of code correctness — even a perfect fix here doesn't produce an installable package until that's addressed.
- **Before trusting any "N operations found" or "N routes registered" log line as proof of correctness**: this session demonstrated, twice, that such log lines can be accurate at the layer that produced them while being completely disconnected from what actually gets dispatched to at runtime. The only trustworthy verification is hitting a real endpoint and checking the real response.
