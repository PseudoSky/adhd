### Added — `version` is now a per-project nx task: registry-driven, tag-free auto-bump (2026-07-21)

Versioning is no longer manual. `@adhd/nx-build:version` (target `version`, `dependsOn:[build]`, not cached) bumps a package's SOURCE `version` **iff it needs a new release**, using the npm registry as the baseline — no git tags, no diff base:
- current version **not** on npm → a release is already *pending* → leave it;
- current version **is** on npm → compare the built `dist` against the **published tarball** (`tools/nx-plugins/build/executors/version/compare-published.js`, which ignores the `version` field and internal `@adhd/*` dep ranges) → **changed → bump** (patch default; `--bump=minor|major` to override), **identical → leave**.

Ignoring internal `@adhd/*` ranges in the comparison is deliberate: `dist-manifest` resolves them to concrete versions, so a *dependency's* version moving would otherwise make every dependent's manifest differ and cascade a bump graph-wide. Caret ranges already absorb a dependency's patch/minor bump at install time, so a package bumps only when its **own** code/external-deps/metadata changed. The task writes the bump but does not commit (review `git diff`).

`pnpm release` is now `build → nx run-many -t version → nx run-many -t publish` (added `pnpm release:dry` for a no-write preview — needed because a chained `--dryRun` would only reach the last command). Publish rebuilds anything `version` bumped (a version change invalidates its build cache) and re-stamps the dist manifest before publishing.

Pure `compare-published`/`bumpVersion` logic covered by 8 `node:test` teeth tests (`pnpm test:build-tools`, now 20 total): identical→no-bump, code-diff→bump, version-only→no-bump, internal-range-only→no-bump (no cascade churn), external-dep→bump, added/removed files→bump.

**Verified (`nx run-many -t version --dryRun`, live registry):** EXIT 0 — **41 packages "release pending, no bump"** (not yet on npm), **11 "changed → would bump"** (already-published packages whose new dist-model artifact differs from their old published tarball, e.g. `agent-base-types 2.1.0 → 2.1.1`), 0 unchanged.

### Changed — `publish` is now a per-project nx task; `nx release` retired; registry is the published-reference (2026-07-21)

`nx release` proved unfit for this workspace at every layer — even after the dist-versioning fix it *still* broke: the `skipLockFileUpdate` flag silently did nothing because it sat at `release.version.skipLockFileUpdate` when `@nx/js`'s `updateLockFile` only reads `release.version.generatorOptions.skipLockFileUpdate` (`update-lock-file.js:11`), so a real `nx release` ran `pnpm install --lockfile-only` and 404'd on unpublished internal deps; and its non-topological version pass left source interdependency ranges stale, which then failed the build via `@nx/dependency-checks`.

Replaced `nx release` with a first-class nx **task**: `@adhd/nx-build:publish` is attached to every publishable project (`dependsOn: [dist-manifest, verify-dist-load, publish-hygiene]`, `cache:false`), so releasing the workspace is just `nx run-many -t publish` (wrapped as `pnpm release` = `pnpm run build && npx nx run-many -t publish`). Each task:
1. is **gated** by nx's real targets (`build → dist-manifest → verify-dist-load → publish-hygiene`); `dist-manifest` makes each `dist/package.json` self-consistent (internal ranges resolved from a live workspace snapshot), so publishing never depends on source-range correctness.
2. **publishes** the built `dist/` via `npm publish` only if that `name@version` isn't already on the registry. **The npm registry is the source of truth** for what's released (`npm view name@version`) — already-published versions are a no-op skip, and there are **no git tags** to create or keep in sync.

Versioning model: the source `package.json` version is the release version (no auto-bump; bump source to cut a release). No git-config XOR, no lockfile step, no non-topological versioning, no dependency-checks-on-stale-source, no tag bookkeeping — every `nx release` failure mode is gone, and the release now composes with nx's graph/`run-many`/`affected`/`dependsOn` like any other task. The former `nx release` workflow is marked retired in PUBLISHING.md. `nx.json`'s `skipLockFileUpdate` was also moved into `generatorOptions` so the retired path, if ever run, no longer 404s.

**Verified (`nx run-many -t publish --dryRun`, warm build):** EXIT 0 — target ran for all 52 projects (+260 gate tasks); **41 packages would publish** from their versioned dist, **11 skipped** (already on npm), **0 failed**.

### Fixed — pnpm real `node_modules` linking exposed a cross-bundle `instanceof ApiError` identity mismatch: validate-Layer 400s became 500s in api-express/api-fastify, MCP stream error codes collapsed to `internal` (2026-07-21)

**BUG-APIGEN-PLUGIN-IN-PROCESS-VALIDATE-500-001 — `apigen-plugin-api-express`/`apigen-plugin-api-fastify`'s `run()` error-mapping middleware did `err instanceof ApiError` against an `ApiError` thrown from a *different* bundled copy of the class, so the check silently returned `false` and every validation failure fell through to a generic 500 instead of its real status (400 `invalid_argument`, etc). Same root cause as the sibling `BUG-APIGEN-STREAM-ERROR-CODE-MISCLASSIFY-001` (apigen-plugin-mcp streaming), fixed together.**

Captured the real thrown error directly (temporary `console.error` in the express error handler, reverted after capture — see method below) instead of reasoning from the masked `pino-http` "failed with status code 500" wrapper log. It showed: `err.constructor.name: "A"`, `err instanceof ApiError: false`, stack rooted at `packages/apigen/apigen-engine-runtime/dist/index.js:1:16578` — i.e. the validate-Layer genuinely threw a correctly-populated `ApiError{code:'invalid_argument',...}`, just not one `instanceof` the `ApiError` class `run.ts` imports.

Root cause chain: (1) `apigen-engine-runtime`'s (and every other `platform:node`/`platform:shared` apigen package's) `vite.config.ts` deliberately does **not** externalize `@adhd/*` workspace deps — `tools/vite-plugins/externalize.mjs`'s own doc-comment records why: with no real yarn workspace linking, `@adhd/apigen-base-errors` had to be bundled/inlined into every consumer's `dist` to be resolvable at runtime at all. Inspecting the built bundle confirmed this: `packages/apigen/apigen-engine-runtime/dist/index.js` contains its own private, minified `class A extends Error{constructor(t,r,n){...,this.name="ApiError"...}}` — a structurally-identical but object-distinct copy of `apigen-base-errors`'s own `class _ extends Error{...}` in *its* dist. (2) On `main`/yarn, this never mattered for tests: `node_modules/@adhd/*` had no real symlinks at all, so Vitest's `nxViteTsPaths()` plugin was the *only* way `@adhd/apigen-engine-runtime` could resolve, forcing it (and its transitive `@adhd/apigen-base-errors` import) to SOURCE — one single `ApiError` class shared by the whole test's module graph, so `instanceof` always succeeded. (3) This worktree's yarn→pnpm + in-source-dist migration (`apigen-engine-runtime/package.json` `main` repointed `./index.js` → `./dist/index.js`, `project.json` `outputPath` moved to `packages/apigen/apigen-engine-runtime/dist`) gave pnpm's real `node_modules/@adhd/apigen-engine-runtime` symlink a genuinely valid, resolvable `dist` entry point for the first time. Vite/Node's default resolver now succeeds on that real entry, loading the pre-built `dist/index.js` — with its own inlined `ApiError` — instead of source. `run.ts`'s own directly-imported `ApiError` (from `@adhd/apigen-base-errors`) is a separate module instantiation either way, so `instanceof` was structurally guaranteed to fail the moment `apigen-engine-runtime` resolved to `dist` under test. `apigen-plugin-mcp/src/lib/stream.ts`'s `err instanceof ApiError` check on a pre-first-chunk streaming error hit the identical mismatch, collapsing a `not_found` code to the generic `internal` fallback.

Fix (surgical, no build-system/bundling-strategy change): added `isApiError(err): err is ApiError` to `@adhd/apigen-base-errors` (`packages/apigen/apigen-base-errors/src/lib/errors.ts`, exported from `src/index.ts`) — a structural/duck-type guard (`err instanceof Error && typeof err.code === 'string' && ERROR_CODES.includes(err.code)`) that is immune to cross-bundle class-identity mismatches because it only inspects plain properties every `ApiError` instance carries, not the class reference. Replaced `err instanceof ApiError` with `isApiError(err)` at both call sites in `apigen-plugin-api-express/src/lib/run.ts` (`toHttpStatus`, the Express error-handling middleware) and `apigen-plugin-api-fastify/src/lib/run.ts` (`toHttpStatus`, the Fastify `setErrorHandler`), and in `apigen-plugin-mcp/src/lib/stream.ts`'s streaming error carrier. `HTTP_STATUS`'s `Record<ApiErrorCode, number>` typing continues to enforce the code stays a valid `ApiErrorCode` after the guard narrows.

### Fixed — pnpm migration made `decimal.js` resolvable, exposing a Decimal-scalar regression in `apigen-core-client`'s schema extraction (2026-07-21)

**BUG-APIGEN-CORE-PNPM-DECIMAL-001 — imported `Decimal` (decimal.js) inside array/tuple/Set elements and top-level parameters structurally expanded to the real class shape (`{d,e,s}`) instead of collapsing to the logical `{type:'string',format:'decimal'}` scalar, once pnpm's hoisted `node_modules` made `decimal.js` resolvable from the extractor's ts-morph program.**

4 tests in `ts-json-schema.spec.ts` failed under pnpm that passed under yarn — but for the wrong reason: they passed on yarn only because `decimal.js` was unresolvable there, so the bare type name `"Decimal"` never got expanded. Root cause: whenever ts-morph's `Type.getText()` is called WITHOUT an enclosing-node context (array/tuple element types via `elem.getText()` in `morph-walk.ts`'s `walkType`; top-level parameter types via `getTypeAtLocation(...).getText()` in `extract.ts`'s `rawParams*` helpers), the TypeChecker's default printer emits a fully-qualified import expression for any resolvable externally-imported class — `import("/abs/path/decimal.js/decimal").Decimal` — regardless of the alias the user actually wrote (`Decimal`, `D2`, default or named import all collapse to the same qualified form). `ts-json-schema.ts`'s `normalizeTypeText`/`QUALIFIED_IMPORT_PATTERNS` only recognized the `.default` suffix (the form previously observed when the module was unresolvable and ts-morph fell back to a synthetic default binding), so the `.Decimal` suffix fell through the SCALAR_SCHEMAS lookup, through Path 1 (ts-json-schema-generator, `No root type` on the array/composite form), and into Path 2's structural walk, which expanded the real decimal.js class because `walkType` has no concept of scalar formats — that's owned entirely by the text-based lookup this fix repairs.

Fix: `packages/apigen/apigen-core-client/src/lib/schema-builders/ts-json-schema.ts` — widened the `QUALIFIED_IMPORT_PATTERNS` regex (used by `rewriteQualifiedImports`) from a `.default`-anchored suffix to `\.\w+` (any export-member name), and changed `normalizeTypeText`'s step 1 from a `.default`-only whole-string check to `t = rewriteQualifiedImports(t)`, which is unanchored and therefore also normalizes qualified fragments embedded inside composite type strings, not just whole-string matches. No changes to `morph-walk.ts` or `extract.ts` were needed — the fix operates purely at the text-normalization layer both paths already recurse back through.

### Fixed — 10 apigen packages shipped broken dist bundles (`__filename`/`timeOrigin` crash on load); generator enforcement added (2026-07-20)

`verify-dist-load` caught this independently on `apigen-plugin-mcp`/`apigen-plugin-openapi` (a publish-preview dry-run session) and, via a full `npx nx run-many -t verify-dist-load --all` audit, on 8 more packages that all shared the same root cause: `@adhd/apigen-core-client` (imported by nearly every apigen package) declares real `ts-morph`/`typescript`/`ts-json-schema-generator` dependencies, and every downstream `@nx/vite:build` package with `rollupOptions.external: []` bundled its SOURCE (not its dist — Nx's `tsconfig.base.json` path mapping resolves `@adhd/*` straight to source at build time) directly in. Bundling `@adhd/*` source via `@nx/vite:build` + `nxViteTsPaths()` is the only mechanism in this repo that currently makes cross-`@adhd/*`-package runtime imports work, so it has to stay — only the real npm dependencies needed externalizing.

The transitive walk was necessary: externalizing only a package's OWN direct deps left `ts-morph` bundled anyway for e.g. `apigen-plugin-api-express`, which doesn't depend on it directly but bundles `apigen-core-client` source, which does.
