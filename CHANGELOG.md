### Added — Batch/bulk fan-out operations for apigen: generic N-way parallelizable call orchestration (FEAT-APIGEN-BULK-OPS-001) (2026-07-28)

Apigen now supports generic batch/bulk fan-out of any single-item operation via a new `_batch/<kind>` synthetic mount, enabling concurrent execution of N identical operations with configurable parallelism, backpressure, and per-item failure handling — without requiring authors to hand-write batch functions. **Scope and limits:** Portable across all apigen hosts (TypeScript, Python/Flask, CLI live-dispatch). Spec: `docs/spec/apigen/BATCH_0.0.1.md` (0.0.1 finalized 2026-07-27, closed all architect-review findings F1–F5). **Implementation:** `@adhd/apigen-core-client`'s `batch.ts` (host-agnostic schema derivation: `groupBatchableOperationsByKind()`, `buildBatchKindSchema()`, `buildBatchMountedOperations()`, `syntheticOp()` → one `_batch/<kind>` mount per distinct operation kind, discriminated-union input/output as inline JSON-Schema branches, no hardcoded envelope). **Runtime execution (TS-only):** `@adhd/apigen-engine-runtime`'s `batch.ts` — `MountHostBridge`, `invokeBatch()` fan-out via `createPackageInvoker`, concurrency modes: `'parallel'` (bounded by `concurrency` param), `'serial'`, `'chained'` (serial with cancellation propagation). `itemTimeoutMs` is **rejected upfront** in Python — deliberate design choice (threads cannot be forcibly killed), not a missing feature. **Known limitation:** Cross-host fan-out via `apigen-engine-gateway` remains unaddressed (separate mechanism, scope for future work). **Plugin adoption:** `apigen-plugin-py-flask` (ThreadPoolExecutor for parallel, loop for serial/chained), `apigen-plugin-cli-output` (live-dispatch mount via `projectMountInputSchema()` discriminator flag-projection). **End-to-end verified:** Fastify, Express, CLI live-dispatch, Python/Flask real spawned processes; `entrypoint/backlog` now mounts batch plugin alongside openapi (`proof: entrypoint/backlog/src/batch-adoption.spec.ts`). Teeth: 47 new tests across batch, plugin, and consumer adoption specs; all live-dispatch + real subprocess integration. Commits `0133976d`–`6095a48f` (batch-ops wave). **Files:** `packages/apigen/apigen-core-client/src/lib/batch.ts`, `packages/apigen/apigen-engine-runtime/src/lib/batch.ts`, `packages/apigen/apigen-plugin-py-flask/src/lib/plugin.ts`, `packages/apigen/python/apigen_python/flask_server.py`, `packages/apigen/apigen-plugin-cli-output/src/lib/mount-cli-flags.ts`, `entrypoint/backlog/src/{server.ts,batch-adoption.spec.ts}`, `docs/spec/apigen/BATCH_0.0.1.md`.

### Fixed — MIGRATION.md §3.3 20-writer concurrency scale test surfaced two new `@adhd/backlog` bugs; both fixed in the same session (2026-07-24)

Building the plan's own required 20-real-worker scale DoD (`store/concurrency-scale.spec.ts`, extending `claim.spec.ts`/`busy-retry.spec.ts` from 2 to 20 genuine `worker_threads`) surfaced two previously-unreported, real correctness gaps — not the ones the test set out to prove, but the exact kind of thing driving the real path through real components at real scale is supposed to catch.

**`BUG-BACKLOG-CONCURRENT-ID-ALLOCATION-RACE-001` — 20 concurrent `createItem` calls for the same `(repo, family)` produced only 11–13 unique human ids, not 20.** `store/ids.ts`'s `allocateHumanId` computed `max(existing) + 1` inside its own `BEGIN IMMEDIATE` transaction, correctly serialized against other `.immediate()` callers — but then COMMITTED and returned, and the caller (`crud.ts`'s `createItemNode`, `structure.ts`'s `supersedeItemNode`) inserted the actual node in a SEPARATE, later, unguarded `store.graph.writeNode()`/`store.graph.supersede()` call. This left a genuine TOCTOU window: two concurrent callers could each compute the identical "next" id before either one's node existed yet, and both mint a node claiming it — a silent violation of "humanId is unique within (repo, family)" (SPEC.md §4.1) that a 2-writer test would rarely catch but 20 real writers reproduced on nearly every run. **Fix:** `ids.ts` gains `allocateHumanIdAndInsert(store, repo, family, idOverride, insert)`, which runs id-resolution (or the `idOverride` existence re-check) AND the caller's `insert` callback inside ONE retried `.immediate()` transaction — no other `.immediate()`-wrapped write can interleave. `createItemNode` and `supersedeItemNode` both now route through it (the bare `allocateHumanId` is kept, deprecated, for a caller that never needs an atomic insert alongside it). **Teeth:** `store/concurrency-scale.spec.ts`'s no-contention case (20 workers, 20 distinct items, asserts `new Set(ids).size === 20` and the store's own node count is 20) — negative control confirmed red (11/20 and 13/20 unique ids across two reverted runs) before the fix, green (20/20, stable across repeated runs) after.

**`BUG-BACKLOG-FTS-SANITIZE-TOO-NARROW-001` — `sanitizeFtsQuery` (the `BUG-BACKLOG-DEDUPE-FTS-SYNTAX-CRASH-001` fix, above) only stripped the five characters found in that report (`"():^*-`); a title/grep term containing `#`, `.`, `{`, `}`, `~`, `[`, `]`, `@`, `!`, `$`, `%`, `&`, `=`, `<`, `>`, `?`, `/`, `\`, `;`, or `,` still crashed `searchNodes` the same way — found while writing the scale test's own `createItem` fixture titles (`"... #7"` crashed `dedupeScan` outright).** Probed FTS5's actual query grammar directly (not guessed) to find the complete list — `{` is the most dangerous of these (`no such column: create`, i.e. parsed as column-filter syntax rather than merely erroring). **Fix:** widened `sanitizeFtsQuery` (`store/mapping.ts`) from an enumerated denylist to a Unicode-aware allowlist (`/[^\p{L}\p{N}_\s]/gu` — keep letters/numbers/underscore/whitespace, space out everything else), closing the whack-a-mole gap for good instead of adding one more character to a list that will keep growing. Behavior-preserving for every previously-working case (verified: `"off-by-one"` still sanitizes to `"off by one"` and still matches). **Teeth:** extended `client.spec.ts`'s existing FTS-syntax-crash regression test with `#`-containing and all-newly-found-characters titles.

### Added — committed `published-state.json` cache makes `@adhd/nx-build:version`'s change-detection zero-network on the happy path (PUBLISHED-STATE-CACHE-001); closes `DEBT-BUILD-VERSION-NO-AUTOCOMMIT-001` via a new opt-in `pnpm release:commit` step (2026-07-23)

**The problem:** `version`'s pre-existing change-detector fetched + extracted a full npm tarball for EVERY publishable package on EVERY run just to decide bump/no-bump (`npm view` + `npm pack` + `tar`, real network, 54 publishable packages in this workspace). **The fix — a committed cache, not a live fetch:**
- **`published-state.json`** (workspace root, source-controlled) stores `{ version, normalizedHash, publishedIntegrity }` per package — the "published-reference".
- **`compare-published.js`** gained `normalizedHash(dir)`: a `sha256` over the exact same `normalizeManifest`/`listFiles`/`stableStringify` primitives `comparePublishedToLocal` already used, so a cache-hash compare is provably equivalent to the legacy per-file diff (proven both directions, incl. the internal-`@adhd/*`-range-moves-but-hashes-equal and real-code-change-hashes-different cases — `compare-published.spec.mjs`).
- **`version`** now reads the cache first (zero network); a cache MISS triggers a single-package, in-process backfill (never a graph-wide re-fetch) via the new **`reconcile-core.js`**, shared by the new **`@adhd/nx-build:reconcile`** task. `reconcile` uses an **integrity gate** — pack the local dist OFFLINE, compare its hash against just the packument's `dist.integrity` metadata (~KB, never the tarball) — and pulls the full tarball ONLY when that comparison actually diverges.
- **`publish`**'s existence-check reads the cache first too (zero network on a hit); on a real publish (or npm's "cannot publish over previously published version", treated as success — the read-lag case) it writes the package's entry back from the dist it just packed **locally** (never a re-fetch, immune to registry propagation lag).

### Fixed — `apigen serve`'s front proxy 404'd every canonical route; closes `BUG-APIGEN-CLI-SERVE-FRONT-PROXY-DOUBLE-SEGMENT-001` (2026-07-23)

`apigen serve`'s front proxy (`entrypoint/apigen-cli/src/lib/commands/serve.ts`) forwards every HTTP/1.1 request path-preserving (byte-identical, no rewriting) to the owning child, and uses only the URL's leading segment to pick which child that is. Post route-canonicalization (`BUG-APIGEN-OPENAPI-ROUTE-PATH-MISMATCH-001`), every operation's real route is `/<ns>/<file-or-class-segment(s)>/<op>` — `@adhd/apigen-naming`'s `project(op).http.route` for TS (`api-fastify`), byte-identically re-derived by `apigen_python/flask_server.py`'s `_route_for_op()` for Python (`py-flask`) — never the flat `/<ns>/<op>` the front's own tests/docs still assumed. Live reproduction confirmed both defects against a real spawned server:

1. **Missing file segment (the reported regression).** `serve`'s own fixtures use single-file namespaces where `ns == file-stem` (e.g. `a.ts` mounted at namespace `a`), so the real route is `/a/a/add-numbers`, not `/a/addNumbers` — every serve-mounted op 404'd. **Decision:** kept the front path-preserving/canonical-everywhere (consistent with openapi/mcp/grpc, and the only generically-correct option — a real op's route can be 2 or 3+ segments deep depending on export shape, so there's no flat client-facing form the front could reconstruct without descriptor introspection). No proxy forwarding logic changed; `serve.spec.ts`'s live assertions were updated to the real canonical routes (verified against a real spawned `api-fastify`/`py-flask` server, not guessed), and the module/function JSDoc now states the contract explicitly.
2. **A second, deeper latent bug found while implementing the fix, in the same routing logic:** the front's `byNamespace` lookup table was keyed by a host's RAW namespace string (e.g. `myUserAccounts`), but the real wire-level namespace segment every HTTP-emitting plugin actually serves at is the KEBAB-CASED, tokenized form (`my-user-accounts`) — so any namespace that wasn't already a single lowercase word (every existing test fixture used `a`/`b`) 404'd with "no host mounted", live-reproduced (`GET /my-user-accounts/my-user-accounts/list-all` → 404 pre-fix, `→ 200` post-fix). Fixed by adding `httpNamespaceSegment()` (mirrors `toKebab(makeSeg(ns))`) and splitting the front's single lookup map into two: `byNamespaceHttp` (kebab-keyed, for `api-fastify`/`py-flask`) and `byNamespaceRaw` (raw-keyed, for `py-grpc`, which uses the namespace verbatim as its own gRPC package name — a separate, simpler convention unrelated to `@adhd/apigen-naming`). Also fixed `resolveHosts()`'s duplicate-namespace detection to compare the same canonical form, so two differently-spelled namespaces that kebab to the same wire segment (e.g. `myApi` / `my-api`) are now caught as a collision instead of silently shadowing one host.

**Verification with teeth:** added `[serve.httpNamespaceSegment]` unit tests, a `resolveHosts` canonical-collision test, and extended the live `[serve.live]` suite with a third, multi-word-namespace TS host (`myUserAccounts.ts`) whose canonical route is asserted to 200 and whose pre-fix raw-cased route is asserted to 404 — negative-control-proven by temporarily reverting `httpNamespaceSegment()` to identity, confirming 3 tests correctly go red, then restoring the fix. ### Added — `version` topological dependent-range sync + `lint` self-healing dependency-checks; RESOLVES `BUILD-TOOLING-VERSION-SYNC-DEPS-001` (2026-07-22)

**Change 1 — `version`'s `dependsOn` gained `^version` (topological ordering) plus a final reconciliation step.** `tools/nx-plugins/build/plugin.js`'s inferred `version` target is now `dependsOn: ["build", "^version"]` (was `["build"]`). `^version` versions a package's internal `@adhd/*` dependencies FIRST, so by the time a package's own `version` task runs, every dependency it declares has already settled its version for this run. After deciding its own bump (unchanged logic — registry-as-baseline, no git tags), `tools/nx-plugins/build/executors/version/impl.js`'s `run()` now ALWAYS runs a final step, `reconcileOwnInternalRanges()`, that reconciles the package's own declared internal `@adhd/*` dependency ranges to that now-settled state — by calling `tools/nx-plugins/deps/executors/{sync,check}/impl.js` **directly** (`require(...)`, real function calls, not a subprocess re-implementation): `sync` (fix) for a real run, `check` (read-only) for `--dryRun`, so a dry run never writes. It writes ONLY that package's own `package.json`, never a sibling's — both reused executors scope to `context.projectName`'s root, and `impl.js` never touches any other project's manifest itself.

**Why this can never trigger a spurious own bump (verified, not assumed):** `compare-published.js`'s `normalizeManifest` already strips the `version` field AND every internal `@adhd/*` dependency range from both sides before diffing (pre-existing code, unchanged) — proven by the pre-existing `compare-published.spec.mjs` test `"only an internal @adhd/* dep RANGE differs -> NOT changed"`. So the reconciliation step's range-only edit is invisible to the next run's change-detector: a package's own version bumps only when its code/external-deps/metadata actually changed. No cascade re-bump of dependents is introduced — `^version` only keeps SOURCE ranges consistent.

**Change 2 — every project's `lint` now `dependsOn: ["sync-deps"]`, wired globally via `nx.json` `targetDefaults.lint` (not either plugin's `createNodes`, to avoid an unspecified two-plugin target-merge order — see `tools/nx-plugins/deps/README.md`).** The effective chain is `version → build → lint → sync-deps`: a stale/undeclared internal `@adhd/*` dependency range gets fixed on disk automatically, BEFORE `@nx/dependency-checks` ever inspects the file. **Deliberate, accepted gate-semantics change:** the dependency-check portion of `lint` moves from a hard gate to self-healing for this specific, fixable class of drift — `@nx/dependency-checks` still hard-fails on anything it can't auto-fix.

1. **Port selection with fallback** (`config.ts`'s new `resolveInitialSsePort()`): tries the user's pinned port only when `env.provenance['sse.port'].source !== 'default'` (i.e. `ADHD_AGENT_SSE_PORT`, or a config-file layer, actually set it — not just left at the code default); otherwise derives a stable-per-process candidate port from `env.instanceId` (`deriveInstancePort()`, mirroring `@adhd/environment-builder`'s `dirs.ts` per-instance path-suffixing intent — same idea applied to a port) so concurrent instances naturally spread across ports instead of all racing for 3001. `sse-server.ts`'s `startSseServer()` now returns `Promise<{server, port}>` (was a bare `http.Server`); on `EADDRINUSE` it retries **exactly once** with `listen(0, host)` (OS-assigned ephemeral) and always succeeds unless even that fails (rare permission/sandbox edge case — still non-fatal, logs and resolves `port: undefined`).
2. **Opt-in skippable** (evaluated and rejected true lazy bind-on-first-use): both the gateway (`/v1/chat/completions`) and SSE streaming are PULL-style — a client must already have a working URL before it can ever connect, so there is no "first use" signal to defer binding to; the port must be live (and `stream_url` correct) before any request can arrive. Default stays on — no existing consumer regresses.
3. **Correct discovery**: `config.ts` now records the actual bound port via `setSseBoundPort()` (called once, from `main()`, immediately after `startSseServer()` resolves — before any consumer reads `toEngineConfig()`). `toEngineConfig()`'s `sse.baseUrl` now goes through a new, directly-testable pure function `computeSseBaseUrl(override, boundPort, configuredPort)`: an explicit `ADHD_AGENT_SSE_BASE_URL`/`sse.baseUrl` override always wins (unchanged precedence); otherwise the actual bound port beats the originally-configured one. ### Added — `version` is now a per-project nx task: registry-driven, tag-free auto-bump (2026-07-21)

Versioning is no longer manual. `@adhd/nx-build:version` (target `version`, `dependsOn:[build]`, not cached) bumps a package's SOURCE `version` **iff it needs a new release**, using the npm registry as the baseline — no git tags, no diff base:
- current version **not** on npm → a release is already *pending* → leave it;
- current version **is** on npm → compare the built `dist` against the **published tarball** (`tools/nx-plugins/build/executors/version/compare-published.js`, which ignores the `version` field and internal `@adhd/*` dep ranges) → **changed → bump** (patch default; `--bump=minor|major` to override), **identical → leave**.

Ignoring internal `@adhd/*` ranges in the comparison is deliberate: `dist-manifest` resolves them to concrete versions, so a *dependency's* version moving would otherwise make every dependent's manifest differ and cascade a bump graph-wide. Caret ranges already absorb a dependency's patch/minor bump at install time, so a package bumps only when its **own** code/external-deps/metadata changed. The task writes the bump but does not commit (review `git diff`).

`pnpm release` is now `build → nx run-many -t version → nx run-many -t publish` (added `pnpm release:dry` for a no-write preview — needed because a chained `--dryRun` would only reach the last command). Publish rebuilds anything `version` bumped (a version change invalidates its build cache) and re-stamps the dist manifest before publishing.

Pure `compare-published`/`bumpVersion` logic covered by 8 `node:test` teeth tests (`pnpm test:build-tools`, now 20 total): identical→no-bump, code-diff→bump, version-only→no-bump, internal-range-only→no-bump (no cascade churn), external-dep→bump, added/removed files→bump.

#### BUG-APIGEN-015 — api-fastify host returns logical SCALAR results as `text/plain`, not canonical JSON-string wire → cross-language drift with py-flask
**Discovered:** 2026-06-26, while building the logical-types human demo (driving the REAL hosts, not the codec layer — the conformance suite is green because it tests encode/decode functions, not each host's HTTP response serialization).
**Symptom (exact bytes, same function, same input `123.456` / `2024-01-15T12:00:00.000Z`):**
- TS `api-fastify`: `Content-Type: text/plain` · body `123.456` (bare) · Date body `2024-01-15T12:00:00.000Z` (bare — **not valid JSON**; `JSON.parse` throws).
- PY `py-flask`: `Content-Type: application/json` · body `"123.456"` · `"2024-01-15T12:00:00.000Z"` (canonical decimal/date → JSON string).
So a `Decimal`/`bigint`/`Date` **return** value comes off the two hosts in different shapes. This breaks the headline promise ("one wire, every language") on the RESPONSE path: a polyglot client can't consume both uniformly, and a client that `JSON.parse`s the TS response gets a precision-losing float for `bigint`/`Decimal` (`9007199254740993` → 9007199254740992) or a throw for `Date`. Container returns (Map→entry-array, Set→array) are JSON arrays on both, so no drift there — the gap is specifically **scalar logical returns**.
**Root cause (unverified):** the api-fastify host's reply path sends the encoded scalar (already a string like `"123.456"`) via a path that fastify serializes as a raw text body (`reply.send(string)` → text/plain) instead of JSON-encoding it. The canonical contract (DESIGN §3) is decimal/int64/date → JSON **string**; py-flask honors it, api-fastify does not.
**Why green tests missed it:** the cross-host conformance gate drives the shared codec functions (which agree); it never asserts the full HTTP response envelope of each host. The seam that breaks in real use (host → reply serialization) is exactly the one no test covered.
**Fix direction:** make the api-fastify (and audit api-express/mcp likewise) host JSON-encode the encoded result so a scalar logical return is sent as a JSON string with `application/json`, byte-identical to py-flask. Add a cross-host RESPONSE-envelope conformance assertion (drive both real servers, compare raw bytes) so this can't regress.
**Status: RESOLVED + orchestrator-VERIFIED (2026-06-26).** Added `sendJson(reply, result)` in `packages/apigen/plugins/api-fastify/src/lib/run.ts` — both the GET and POST handlers now `reply.type('application/json')` + `JSON.stringify(result)` (void → `null`), so every result is canonical JSON wire. **api-express was already correct** (`res.json()` always JSON-serializes); MCP is a separate protocol envelope (out of scope). **Verified by use:** rebuilt CLI, drove the real TS + Python hosts — `price 123.456` → `"123.456"` byte-identical on both (`22 31 32 33 2e 34 35 36 22`), `when` → `"2024-01-15T12:00:00.000Z"` on both, `echoBig` → `"9007199254740993"` (quoted, no precision loss), TS content-type now `application/json`. **Regression teeth:** `plugin.spec.ts [v2-fastify.run.verb.1]` tightened to assert `application/json` + body exactly `"pong"` + `JSON.parse` round-trip (reverting the fix → text/plain `pong` turns it red). api-fastify 37/37 + apigen-cli 107/107 EXIT=0.
**Cross-host guard added (2026-06-26):** `packages/apigen/cli/src/test/integration/cross-host-response-envelope.spec.ts` — drives BOTH real servers (api-fastify via built CLI + py-flask via `python3 -m apigen_python.flask_server`) and asserts byte-identical canonical JSON wire for a scalar Decimal return (the response-envelope seam the codec conformance suite missed). Default-running, no env gate. **Teeth PROVEN by orchestrator negative control:** reverting `sendJson` → both guard tests went RED (`expected 'text/plain; charset=utf-8' to contain 'application/json'`); restoring → 2/2 green. #### BUG-PY-FLASK-001 — `from __future__ import annotations` (PEP 563) prevents per-param JSON schema inference in Python extractor

#### BUG-ORCH-008 — the context limiter DESTROYS the provider prefix cache, making token spend dramatically WORSE (measured: +154K full-price tokens in one run)
- **Where:** `windowMessages` (published `src/store/session-store.js:174`; repo equivalent in `agent-engine-orchestrator`), active whenever `ADHD_AGENT_CONTEXT_LIMIT > 0`.
- **Mechanism:** the Chat Completions API is stateless, so the full history is re-sent every model call. Providers make this affordable with **prefix caching** — an unchanged leading prefix is billed at a steep discount (DeepSeek reports `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` on every response). `windowMessages` enforces the limit by **dropping the OLDEST messages**, which mutates the shared prefix. The cache then misses on everything after the system prompt, and the entire context is re-billed at full price.
- **Measured on the wire** (raw request bodies + provider usage captured via a forwarding proxy, 24-call run, `ADHD_AGENT_CONTEXT_LIMIT=30000`):
  - Steady state, prefix intact: **93-100% cache hit**.
  - Exactly the 4 calls where the window trimmed the front (shared prefix collapsed from 28-34 messages to 1): **cache hit fell to 5-6%**.
  - Correlation is 1:1 — every prefix break is a cache bust, and no other call missed.
  - **Full-price tokens burned by those 4 busts: 154,224** (of 190,260 total miss tokens in the run — i.e. the limiter caused ~81% of all full-price input).
- **Net effect:** the mechanism deployed to *reduce* token spend after the 710K incident is responsible for the large majority of the expensive (uncached) tokens. Turning `ADHD_AGENT_CONTEXT_LIMIT` off would very likely have *lowered* cost in this run.
- **Fix direction:** never evict from the front while a prefix cache is in play. Options, best first:
  1. **Don't trim at all** until the real context (from the previous response's `prompt_tokens`, which is exact) approaches the model's actual window — then trim ONCE, in a large step, so the cost is amortized rather than paid every few calls.
  2. Evict by **summarizing/collapsing the middle** while keeping the leading prefix byte-identical.
  3. Cap the *inputs* (tool-result size, tool-call count), which is where the growth actually comes from — see `FINDING-ORCH-007`.
- **Interaction:** this compounds `BUG-ORCH-006` (the estimator undercounts, so trims fire at unpredictable points) and `BUG-ORCH-003` (a trim can orphan a tool message → hard 400).
- **Design landed:** `docs/ideas/context-and-cache-strategy.md` — verifies all of the above independently against the raw wire capture (recomputed, not copied) and specifies a concrete replacement strategy (cap tool-result size at the source; trigger trimming off the provider's own `prompt_tokens` instead of the undercounting local estimator; when a trim is unavoidable, collapse the middle into one synthetic summary turn exactly once instead of evicting repeatedly from the front; per-model window config instead of one global scalar). Also shows the repo's already-landed pairing-aware `windowMessages` fix (§4 of that doc) does **not** resolve this bug — it still evicts from the front, so it still busts the cache; it only fixes `BUG-ORCH-003`/`004`, not `BUG-ORCH-008`.

- **Status:** ✅ SHIPPED in 2.1.1 (published 2026-07-12; live-confirm evidence under BUG-ORCH-009). Was: FIXED IN REPO (unpublished). Replaced front-eviction with cache-preserving compaction (`engine/context-window.ts`): history grows append-only; only when the PROVIDER-reported context (`usage.inputTokens`) crosses 75% of the model's TRUE window (`contextWindowFor`) does the loop compact the middle into ONE summary message via the provider, preserving the stable system head + recent tail. Rare + prefix-stable, so the cache survives between compactions. Wired into `orchestrator.ts` loop; `decideCompaction`/`compactMessages` fully unit-tested (`context-window.test.ts`, 12) incl. no-orphan tail selection and best-effort fallback when the summariser throws. CAVEAT: the end-to-end trigger against a live model at 75%-of-window is not exercised by an automated test (would need a multi-hundred-K real context); the compaction logic itself is deterministically tested via an injected summariser.

- **Discovered:** 2026-07-15/16, while verifying BUG-AGENTMCP-003's "main/exports target must be inside `files`" requirement for this package — the `generators` field (`./generators.json`) referenced a `factory` path (`./src/generators/registry-package/generator`) that did not exist ANYWHERE in `dist/packages/agent/agent-generator-plugin`, built or not.

- **Verified end-to-end (exit 0), not just file-presence:** resolved `generators.json`'s `factory`/`schema` fields exactly as Nx's own generator loader does (`require()` relative to the built package root), then invoked `registryPackageGenerator(tree, {name:'smoke-test'})` against a real `@nx/devkit` `createTreeWithEmptyWorkspace()` `Tree` — confirmed it writes `project.json`, `package.json`, and `drizzle.config.ts` into the in-memory tree. This drives the real artifact through the exact resolution path a consumer's `nx generate` would use, not a bypass.
- **Status:** FIXED. Not yet published (package is at `0.0.1`, never released) — this blocks nothing live, but would have blocked the FIRST publish from ever producing a working generator.

#### BUG-AGENTMCP-008 — `@adhd/agent-plugin-budget` and `@adhd/agent-plugin-sanitize` declared a `module`/`exports.import` target (`./index.mjs`) that their own build NEVER PRODUCES, and an `exports.require` target (`./index.js`) that is actually the ESM build
- **Discovered:** 2026-07-15/16, verifying BUG-AGENTMCP-003's "confirm the package's own main/exports target is actually included in files" requirement — went one level deeper and checked whether the declared targets are even the RIGHT files, not just present-or-absent.
- **Root cause:** both packages set `"type": "module"` in `package.json`. Under Vite library-build's format-naming convention, `"type":"module"` flips the default extensions: the `es` format emits `.js` (not `.mjs`) and the `cjs` format emits `.cjs` (not `.js`) — confirmed by inspecting the actual build output (`index.js` + `index.cjs`, no `index.mjs` ever produced) against `vite.config.ts` (`formats: ['es','cjs']`, no explicit `fileName` override per format). The `package.json` `module`/`exports.import` fields were apparently copy-pasted from a template written for the OPPOSITE convention (no `type:module`), so: (1) `module`/`exports.import: "./index.mjs"` pointed at a file that never exists — any ESM-aware bundler/Node `exports` resolution would hard-fail; (2) `exports.require: "./index.js"` pointed at the file that is actually ESM source — `require()` on it would throw `ERR_REQUIRE_ESM`. Both packages were fully broken for BOTH import styles, despite `main`/`typings` looking superficially fine.
- **Fix (2026-07-16):** `main: "./index.cjs"`, `module`/`exports.import: "./index.js"`, `exports.require: "./index.cjs"`, `exports.types` unchanged (`./index.d.ts`) — matches the files Vite actually emits. Verified via the `check-publish-hygiene.mjs` gate: all 3 `exports.*` targets + `main` + `module` now physically present in the packed tarball for both packages.
- **Impact assessment:** neither package is published (`0.0.1`/`0.0.2`), and nothing in-repo imports them via the npm-resolved `exports` map (internal consumers resolve via `tsconfig.base.json` `paths` straight to `src/index.ts`, unaffected) — so this was caught before it could break a real consumer, but would have on first publish.
- **Status:** FIXED.

#### BUG-REPO-PRECOMMIT-PARTIAL-STAGE-001 — the pre-commit hook's `nx affected -t lint --fix` re-stages a FULL file, defeating deliberate partial/cached-patch staging and sweeping in concurrent agents' unrelated uncommitted work
- **Discovered:** 2026-07-20, in `.worktrees/apigen-v1-retirement` while landing BUG-APIGEN-033, alongside a concurrent agent (BUG-APIGEN-029) mid-editing the SAME file (`packages/apigen/apigen-core-client/src/lib/extract.ts`).
- **Detail:** to avoid sweeping another agent's in-flight, non-overlapping hunks into an unrelated commit, `git apply --cached <patch-with-only-my-hunks>` was used to stage exactly the intended 4 hunks in a 7-hunk working-tree file, leaving the other 3 hunks (a different agent's `hoistNestedDefs` WIP) correctly unstaged. `git commit -m "..." -- <exact files>` was then used per the repo's own explicit-pathspec convention. The pre-commit hook still ran `nx affected -t lint --fix` against the project containing the staged file; ESLint's `--fix` operates on the **working-tree** copy (which still had all 7 hunks, since only the index had been partially staged) and the hook's own "auto-fixed and re-staging" step then `git add`'d the file wholesale — silently re-staging the FULL working-tree content (all 7 hunks) right before the commit was created, overwriting the deliberately-partial index. The resulting commit (`56c2e118`) contained an unrelated agent's untested, in-progress code under the wrong commit message. Caught immediately by inspecting `git show --stat HEAD` / `git diff HEAD~1 HEAD` before reporting done, and corrected with a same-session follow-up commit (`851e0a9b`) that reverse-applied just the swept-in hunks and reapplied them to the working tree only (uncommitted), restoring the other agent's WIP byte-for-byte with zero data loss.
- **Why it matters:** the repo's own explicit-pathspec / no-`git add -A` convention (this file's own guidance, repeated in multiple agent-facing docs) is specifically meant to prevent exactly this class of incident when several agents share a worktree — but a pre-commit hook that unconditionally re-stages whatever `eslint --fix` touches on disk bypasses that protection entirely, regardless of how carefully the caller staged the index beforehand. Any agent using a cached/partial patch to avoid sweeping a concurrently-edited shared file is silently defeated by this hook, with no warning at commit time (the hook reports success, not "note: this file had more staged than you asked for").
- **Fix direction:** the hook's auto-fix/re-stage step should diff `eslint --fix`'s post-fix file content against the ORIGINALLY-staged (pre-hook) index blob and only re-add the delta introduced by the fix itself (or refuse to auto-stage a file whose pre-hook staged content didn't already match the full working-tree content) — never blindly `git add` the whole file. At minimum, the hook should warn loudly when a file it's about to re-stage has staged content that differs from its working-tree content BEFORE the fix step runs, since that's precisely the partial-staging signal it's currently destroying.
- **Status:** FIXED on main 2026-07-20 (commit `8e6fd54b`) — root-fix, not the delta-patch above: `.githooks/pre-commit` gate 2 no longer runs `--fix` or `git add`s anything (verify-only; a lint failure prints the standalone `npx nx affected -t sync-deps` fix for the user to run/review/stage). Since the hook never mutates or re-stages a file, this failure class is structurally eliminated. (Note: the shared-index sweep from a *concurrent agent's* non-pathspec `git commit` is a distinct, still-live hazard — mitigation is `git commit -- <paths>`, documented for agents; not a hook issue.)

#### BUG-NX-RUNMANY-DRYRUN-NOT-PROPAGATED-TO-DEPENDENCY-TASKS-001 — `nx run-many -t version --projects=A,B --dryRun` (and even a single `nx run A:version --dryRun`) does NOT propagate `--dryRun` to the dependency tasks `^version` pulls in — they run with the schema default and really write
- **Discovered:** 2026-07-22, live, while proving `^version`'s real topological ordering for `BUILD-TOOLING-VERSION-SYNC-DEPS-001` below. Ran `npx nx run-many -t version --projects=agent-store-runtime,agent-engine-orchestrator --dryRun --parallel=2` expecting a fully read-only proof.
- **Detail:** Nx's `--dryRun` CLI override only applies to the tasks matching the explicitly requested `--projects`/`--target` selector. The 46 dependency tasks `^version` auto-included in the same run (every internal `@adhd/*` package agent-store-runtime/agent-engine-orchestrator transitively depend on) did **not** receive the override and ran the executor's schema default (`dryRun: false`) — confirmed by the log: the 2 explicitly-named projects' lines carried `[dry-run]`, the other 46 did not. 10 of those (`agent-base-types`, `agent-core-env`, `agent-core-policy`, `agent-core-provider`, `agent-engine-compiler`, `agent-store-prompts`, `agent-store-tools`, `environment-base-spec`, `environment-builder`, `environment-core-node`) had a real change to bump and were **actually written to disk** — including a real internal-`@adhd/*`-range sync (`environment-builder`/`environment-core-node`'s `@adhd/environment-base-spec` range, `agent-core-env`'s `@adhd/environment` range) from the new Change-1 reconciliation step. Caught immediately via `git status --porcelain` (these 10 files were clean at session start per the task's own baseline) and reverted with `git restore -- <path>` per file (verified byte-identical to the pre-run `git diff` afterward) — no lasting effect, but a real near-miss: an invocation that *looks* fully read-only silently was not, for anything not in the explicit `--projects` list.
- **Impact:** any scoped or single-project `--dryRun` version invocation is unsafe for anything beyond the exact named project(s) — a real risk for anyone (human or agent) who reasonably expects `--dryRun` to make the WHOLE invocation read-only. The unscoped `pnpm run build && npx nx run-many -t version --dryRun` (no `--projects` filter — every project is already explicitly targeted, nothing is dependency-pulled) is NOT affected.
- **Fix applied (mitigation, not an Nx core fix):** `tools/nx-plugins/build/executors/version/impl.js`'s `run()` now treats dry-run as `!!options.dryRun || process.env.ADHD_NX_VERSION_DRY_RUN === '1'` — the env var is honored uniformly by every task in a single nx invocation (nx's task workers inherit the parent process's env, unlike CLI-override propagation) and is a true belt-and-braces guarantee regardless of how the task got included. `package.json`'s `release:dry` script now sets it. `PUBLISHING.md` and `tools/nx-plugins/build/README.md` document the gap and the required env var for any scoped/single-project dry run. Regression test: `tools/nx-plugins/build/executors/version/impl.spec.mjs` — `"ADHD_NX_VERSION_DRY_RUN=1 env var forces dry-run behavior even when options.dryRun is NOT set"` — proves the env var alone (with `options.dryRun` deliberately omitted, simulating a task Nx failed to propagate the flag to) still blocks the write and routes reconciliation through `sync-deps-check`, not `sync-deps`. Re-verified live afterward: the SAME `--projects=agent-store-runtime,agent-engine-orchestrator --dryRun` invocation, now with `ADHD_NX_VERSION_DRY_RUN=1` set, showed `[dry-run]` on all 48 tasks and left every file byte-identical (`md5` before/after matched).
- **Not fixed (upstream/out of scope):** Nx's own CLI-override-to-dependency-task propagation behavior itself is unchanged (would require an Nx core change or a different task-graph API); the env var is a robust workaround specific to this repo's custom executor, not a general Nx fix.
