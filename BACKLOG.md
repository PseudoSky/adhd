### DEBT-BUILD-COMPOSITE-TSC-PARALLEL-001 — composite tsc project-reference builds can race under nx parallelism on a cold cache (transient TS2307)
**Discovered:** 2026-07-21, full `nx release --dry-run` (build/dist-versioning-plugin). `agent-engine-orchestrator:build` failed `TS2307: Cannot find module '@adhd/agent-store-prompts'` during the parallel publish-phase build — yet the **same build passes in isolation** (`npx nx build agent-engine-orchestrator` → EXIT 0) and after a full ordered `npx nx run-many -t build` (→ EXIT 0, all 54 projects). So it is a build-ORDER race, not a real resolution break (the tsconfig path `@adhd/agent-store-prompts → src/index.ts`, the package name, and the import specifier all match).
**Where:** agent tsc packages build with `tsconfig.lib.json` `"composite": true` project references; under high nx parallelism on a cold cache a consumer's `tsc` can begin before a referenced project's declaration output is visible. Same composite-tsc family as the external-`tsc --build` stray-`.js`/`TS6307` incident recorded later in this file.
**Impact:** a cold-cache one-shot `nx release` (no build-first) can transiently fail. **Mitigated:** the `pnpm release` script is `pnpm run build && pnpm exec nx release` — building first (proper dependency order, warm cache) sidesteps the race; the publish phase then gets cache hits.
**Fix direction:** `composite:true` is NOT trivially removable — each package's root `tsconfig.json` declares `references:[{path:"./tsconfig.lib.json"}]`, and TS requires a referenced project to be composite, so dropping it breaks the project-reference topology + `tsc -b` + IDE typecheck (verified 2026-07-21). Options that remain: (a) add explicit cross-package `references` from each consumer's `tsconfig.lib.json` to its `@adhd/*` deps' tsconfigs so `tsc` itself enforces build order (larger topology change); (b) constrain the tsc build's nx parallelism; (c) keep the build-first mitigation as the accepted answer. **Blocked on a deterministic reproduction:** the race is intermittent (warm/isolated builds always pass), so per the repo verification standard no fix can be teeth-proven until it can be reliably reproduced — a speculative edit here would be unprovable and risk regressing 6 packages. Do NOT change composite without a repro.
**Citations:** [build/dist-versioning-plugin, claude (opus), 1: `agent-engine-orchestrator:build` TS2307 in the parallel release dry-run; 2: terminal `npx nx build agent-engine-orchestrator` → EXIT 0 (isolated); 3: terminal `npx nx run-many -t build` → EXIT 0 (54 projects, ordered); 4: packages/agent/agent-engine-orchestrator/tsconfig.json (`references:[{path:./tsconfig.lib.json}]`) + tsconfig.lib.json (`composite:true`) — composite is load-bearing for the reference]
**Status:** OPEN — non-blocking (build-first mitigates); real fix blocked on a deterministic repro (see fix direction). 6 packages carry `composite:true`.

### DEBT-BUILD-VERSION-SYNCDEPS-REDUNDANT-001 — `sync-deps` (`@nx/dependency-checks` via ESLint) is uncached and re-invoked 2-3x per project per release, dominating `version`'s wall-clock
**Discovered:** 2026-07-23, BUILD-TOOLING-METRICS-001 (centralized `tools/nx-plugins/lib/metrics.js` performance-metrics facility) profiling of the `version` task's subprocess overhead, following up on `published-state.json`'s zero-network cache work (which cut `version` from ~74s to ~51s but left it dominated by non-network overhead per that work's own follow-up note).
**Where:** `nx.json` `targetDefaults`: `build` → `dependsOn:["^build","lint"]`, `lint` → `dependsOn:["sync-deps"]`. `sync-deps`/`sync-deps-check` (`tools/nx-plugins/deps/executors/{sync,check}/impl.js`) have **no `cache` setting at all** (neither in `tools/nx-plugins/deps/plugin.js` nor `nx.json`), so every time `sync-deps` is part of a requested task graph it unconditionally re-executes for real — Nx's caching only ever SKIPS a task that is itself configured cacheable; it never infers "this ran moments ago in a sibling invocation." Separately, `version`'s own `dependsOn:["build","assets","^version"]` (`tools/nx-plugins/build/plugin.js`) means `version` ALSO pulls in `build`'s full dependency chain (`^build`→`lint`→`sync-deps`) on every invocation, AND `version/impl.js`'s own `reconcileOwnInternalRanges` step calls `sync-deps`/`sync-deps-check` a SECOND time in-process (to reconcile internal `@adhd/*` ranges) — reusing the exact same executor, which runs the FULL `@nx/dependency-checks` rule (missing/obsolete/version-mismatch, not just internal ranges) both times.
**Measured (real `pnpm release:dry`-equivalent run, all 61 projects, `CI=true ADHD_NX_VERSION_DRY_RUN=1 npx nx run-many -t version --dryRun`, metrics.json from `tools/nx-plugins/lib/metrics.js`):** a single `nx run-many -t version` invocation triggers `sync-deps` (via the build→lint chain) **54 times** (37.6s cumulative real work) **and** `sync-deps-check` (via `version`'s own reconciliation) **54 more times** (38.3s cumulative) — ~76s of ESLint dependency-check work per `version` run alone, BEFORE counting the SEPARATE `sync-deps` pass `pnpm run build` already paid for moments earlier in the same `pnpm release`/`pnpm release:dry` pipeline (confirmed: a subsequent `publish --dryRun` run's dependency chain re-triggered `sync-deps` yet again for a subset of projects). Isolated micro-benchmark: each real `eslint-check.mjs` invocation costs ~550-580ms, of which the actual `execFileSync(eslint, ...)` (loading ESLint's rule engine + `@nx/eslint-plugin`/`@typescript-eslint/*` + resolving `.eslintrc.json` to check ONE `package.json`) is ~96% of that — i.e. this is NOT wasted subprocess-boot overhead (already eliminated, see CHANGELOG BUILD-TOOLING-METRICS-001), it's the inherent cost of the ESLint CLI engine paid 2-3x redundantly per project per release.
**Why not fixed in BUILD-TOOLING-METRICS-001:** two real fix directions exist — (a) make `sync-deps`/`sync-deps-check` genuinely `cache:true` Nx targets (deterministic given package.json + the Nx project graph, a textbook caching candidate) so the 2nd/3rd redundant invocation per release becomes a free cache hit; or (b) have `version`'s `reconcileOwnInternalRanges` skip its own explicit sync-deps/check call when the build-phase `lint`→`sync-deps` pass already ran against unchanged inputs in the same pipeline. Both touch the **`@nx/dependency-checks`/`sync-deps` subsystem**, which has ALREADY shipped one severe, hard-to-detect regression in this exact area (`BUG-REPO-PRECOMMIT-DEPCHECK-STRIPS-USED-DEPS-001` — real, statically-imported deps silently stripped from `package.json`) and is guarded by extensive, hard-won defensive logic (`tools/nx-plugins/deps/eslint-check.mjs`'s `isRealInstall` guard). A caching or dependency-graph change here has repo-WIDE blast radius (every project's `build`/`lint`, not just `version`) and needs its own dedicated verification pass (real installs, worktrees, CI), not a rushed addition to an unrelated profiling task.
**Fix direction:** prototype (a) first — declare `sync-deps`/`sync-deps-check` `cache:true` with `inputs` covering the project's own `package.json` + the Nx project graph's dependency-version hash (NOT the full `production` fileset, to avoid false invalidation), and prove: (1) a real dependency-drift case is still caught after a cache hit is cleared by a real input change, (2) the `--fix` (write) mode's cache semantics don't create a self-referential-input problem (package.json is both input and output when `--fix` mutates it). If (a) proves unsound, fall back to (b) with a `client_request_id`-style provenance flag so `version`'s call only runs when nothing already validated this project's deps in the current pipeline invocation.
**Citations:** [BUILD-TOOLING-METRICS-001, claude (sonnet), 1: nx.json targetDefaults (build/lint dependsOn); 2: tools/nx-plugins/deps/plugin.js (no cache config); 3: tools/nx-plugins/build/plugin.js:62 (version dependsOn); 4: tools/nx-plugins/build/executors/version/impl.js reconcileOwnInternalRanges; 5: live metrics.json from `nx run-many -t version --dryRun` across 61 projects, 2026-07-23; 6: isolated micro-benchmark, node -e spawnSync/import timing of tools/nx-plugins/deps/eslint-check.mjs against packages/agent/agent-base-types/package.json]
**Status:** OPEN — non-blocking (correctness unaffected; this is a pure performance/redundant-work finding). Real numbers above should anchor whoever picks this up; do not re-guess.

### INVESTIGATION-WORKTREE-PNPM-MIGRATION-001 — pnpm migration for worktree deps: spike complete with real numbers, next steps defined, migration NOT started

- Cold install (empty store, empty `node_modules`): **31.7s** real wall-clock.

### BUG-APIGEN-GENERATOR-STALE-LOCALBIN-001 — `apigen-generator-nx`'s `generate` executor hardcodes the pre-migration repo-root dist path, so the in-source-dist move makes it silently fall back to the STALE PUBLISHED `npm` package instead of the local, fixed build

### BUG-AGENTMCP-001 — the built `dist` agent-mcp server cannot resolve its own `@adhd/*` workspace deps at runtime (`.mcp.json`'s dev entry is dead)

3. A `dist/node_modules/@adhd/<name> -> ../../packages/<group>/<name>` link step in the build (contained, but a workaround).

### DEBT-APIGEN-007 — `lt-dep-manifest` dep-collection is end-to-end blocked by missing `lt-extract-scalars`
**Discovered:** 2026-06-25, during `lt-dep-manifest` state execution.

**Status:** OPEN — `lt-dep-manifest` infrastructure is green; activation gate is `lt-extract-scalars`. **tracked-by: `docs/plan/apigen-logical-types` → state `lt-extract-scalars`.**

### BUG-ORCH-010 — `inputTokens` means DIFFERENT THINGS per provider, so all cross-provider usage aggregation is summing incompatible units
- **Where:** `src/providers/anthropic.js:229` vs `src/providers/openai.js:138`; consumed by `src/plugins/usage-plugin.js` and `src/tools/usage.js` (`usage_query`, incl. `group_by: 'provider' | 'model' | 'agent'`), and by the budget plugin's `tokens` / `inputTokens` caps.
- **The divergence** (confirmed against primary provider docs — see `docs/ideas/provider-caching-research.md`):
  - **Anthropic**: `input_tokens` **EXCLUDES** cached tokens. True total input = `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`.
  - **OpenAI / DeepSeek / Gemini**: the headline count **INCLUDES** cached tokens (DeepSeek documents the equation explicitly: `prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens`).
  - agent-mcp stores the raw headline field from each provider into the same `inputTokens` column.
- **Consequences:**
  1. **Anthropic spend is systematically under-counted** — on a cache-heavy Anthropic run, most input tokens live in `cache_read_input_tokens` and are invisible to `inputTokens`.
  2. **Budget caps behave differently per provider.** A `tokens`/`inputTokens` cap bites an openai-provider agent much sooner than an anthropic-provider agent for identical real usage.
  3. **`usage_query --group_by provider` is not comparable across rows** — it is adding two different quantities.
- **Fix:** normalize at the provider boundary into an explicit, provider-neutral shape — `{uncached_input_tokens, cache_read_tokens, cache_write_tokens, output_tokens, total_input_tokens_processed}` where `total_input_tokens_processed` is computed uniformly as the sum of the first three regardless of each provider's own convention. Drive budget caps and window arithmetic off `total_input_tokens_processed`, and compute cost with each provider's own multiplier table (cache-write is 1.25x/2x on Anthropic, 1.25x on OpenAI GPT-5.6+, and **free** on DeepSeek/Gemini — one shared constant is wrong for half the providers).
- **Also:** `inputTokens` is a CUMULATIVE SUM across model calls, not a context size (see `FINDING-ORCH-007`). Peak-context and cumulative-billed must be recorded as separate metrics; only peak may drive window enforcement.
- **Status:** FIXED IN REPO (unpublished). `TokenUsage` now carries a provider-neutral shape (`agent-base-types/src/domain.ts`); Anthropic's exclusive headline is reconstructed to the true total (`normaliseAnthropicUsage` sums input+read+creation), OpenAI/DeepSeek pass their inclusive headline through with cache split recorded. `inputTokens` now means the same thing on every provider. Cross-provider comparability proven by `usage-normalisation.test.ts`. Budget-cap re-keying onto `total_input_tokens_processed` and cost-per-provider multipliers remain TODO. Needs a published release.

### DEBT-PROCESS-AFFECTED-TEST-001 — agents must use `nx affected -t test` (not targeted `nx test <project>`) when changing shared packages; worktrees amplify the blind spot

**Discovered:** 2026-07-20, triaging FEAT-APIGEN-022 test-gap (commit `a82ec947` changed `apigen-engine-naming` but the author only ran `nx test apigen-cli` + `nx test apigen-engine-naming` — three downstream test suites were missed and landed broken).

**Problem:** When a change touches a package that has downstream consumers, running targeted `nx test <project>` on the changed package and the one you're actively developing misses all other consumers. The dependency graph may include consumers you don't know exist:
- `apigen-engine-naming` → `apigen-codegen-openapi` → `apigen-plugin-openapi`
- `apigen-engine-naming` → `apigen-engine-conformance`

The author of `a82ec947` updated four test files in `apigen-cli` but never ran the `codegen-openapi`, `plugin-openapi`, or `engine-conformance` suites. All three landed broken and stayed broken until discovered by a downstream triage pass.

**Rule:** Any change to a package that has dependents MUST be validated with `nx affected -t test` (not `nx test <project>`), or equivalently `nx run-many -t test -p <project>,<dep1>,<dep2>,...` listing the project AND all transitive consumers explicitly. The targeted `nx test <project>` form is only safe for leaf packages with zero dependents.

**Worktree amplification:** The repo uses parallel worktrees for concurrent agent development. `nx affected -t test` within a single worktree only detects consumers in that worktree's branch and the base branch. It does NOT detect consumers being modified in other worktrees' branches. This means:
- An agent in worktree A changes `apigen-engine-naming` and runs `nx affected -t test` — passes (consumers in worktree A's branch are covered).
- An agent in worktree B is actively modifying `apigen-plugin-openapi` (a consumer) on a branch that hasn't merged to the shared base yet.
- The worktree A agent's `nx affected` has no visibility into worktree B's branch.
- When worktree B merges, they inherit the breaking change without warning.

The worktree context also means Nx cache is not shared (`DEBT-NX-WORKTREE-CACHE-001`), so each worktree independently rebuilds and retests — but this is a performance issue, not a correctness one. The real correctness gap is the invisible cross-worktree consumer.

**Fix direction (multiple options, pick at least one):**

1. **CI gate** — The least-ambiguous mitigation. Add a CI workflow that runs `nx affected -t test` against the merge target for any PR that changes a `packages/apigen/` (or other shared-domain) package, with explicit error on failure. This catches the cross-worktree gap at PR time regardless of what the author tested locally.

2. **Pre-commit hook expansion** — The existing pre-commit hook already runs `nx affected -t lint --fix`. Extending it to also run `nx affected -t test` would catch missing downstream tests at commit time within a single worktree. (Trade-off: significantly slower commits; may need a `--no-verify` escape hatch for docs-only changes.)

3. **Agent instruction update** — Amend `AGENTS.md` §Development & Nx Commands to mandate `nx affected -t test` (not `nx test <project>`) when changing packages with dependents. Weakest mitigation (relies on agent compliance, no mechanical enforcement).

4. **Cross-worktree awareness** — Long-term: adopt a "merge contract" pattern where each worktree publishes a lightweight dependency-change manifest on a well-known branch or shared file, and `nx affected`-like tooling can read it. This is speculative and would need a design spike.

**Immediate recommendation:** Option 1 (CI gate) + Option 3 (AGENTS.md update) — mechanical enforcement at merge time plus agent-level guidance for day-to-day work. Option 2 (pre-commit expansion) is worth evaluating but likely too slow for local commit latency.

**Cross-references:** `DEBT-NX-WORKTREE-CACHE-001` (Nx cache not shared between worktrees), `FEAT-APIGEN-022` (the feature whose commit triggered the gap, commit `a82ec947`), `DEBT-WORKTREE-DIRTY-MAIN-MERGE-001`, `DEBT-WORKTREE-MERGE-CHECK-001`.

**Status:** OPEN.

### BUG-APIGEN-ENGINE-RUNTIME-DISPATCH-REF-UNSUPPORTED-001 — `@adhd/apigen-engine-runtime`'s run-mode `dispatch()` cannot handle ANY JSON-Schema `$ref`, regardless of where `definitions` live
- **Discovered:** 2026-07-22, implementing `entrypoint/backlog/src/server.ts` (apigen MOUNT wiring — extract → composeSchemas → `plugin.run()`). `client.ts`'s return types (`CreateItemResult`, `BacklogItem[]`, ...) reference named exported types (`BacklogStatus`, `Priority`, `Citation`, `Note`) heavily enough that `@adhd/apigen-core-client`'s extraction resolves them via ts-json-schema-generator's named-type ($ref + `definitions`) path rather than fully inlining every occurrence. Calling a real mounted tool (`createItem`, both via MCP `callTool` and via HTTP) crashed with `[apigen-logical] $ref "#/definitions/BacklogStatus" cannot be resolved in run-mode without a descriptor root. Supply a resolve() in the ctx override to handle $ref.`
- **Root cause:** `packages/apigen/apigen-base-logical/src/lib/runmode.ts`'s `buildCtx()` hard-codes `resolve: (ref) => { throw new Error(...) }` — a permanent stub, never a real dereferencer — and `packages/apigen/apigen-engine-runtime/src/lib/dispatch.ts`'s `encodeResult`/`decodeArg` call `_transcoder.encode/decode` via a MODULE-LEVEL frozen transcoder with NO way for a caller (a plugin, a host like `apigen-plugin-mcp`/`apigen-plugin-api-fastify`) to supply a working `resolve()` override. Verified directly: even after hoisting a schema's nested `definitions` up to its own top level (where AJV, a *different* consumer, would resolve it fine), `dispatch()`'s transcoder still throws — the resolver is unconditionally the throwing stub regardless of where `definitions` lives. **Run-mode dispatch (as opposed to codegen-mode, which has a real "descriptor root") cannot handle `$ref` in ANY composed schema today.**
- **Impact:** any `@adhd/apigen-core-client`-mounted (not code-generated) function whose input/output schema ends up `$ref`-based (which happens automatically whenever a named type is referenced by ≥2+ call sites within one extraction pass — an easy, common case for any real domain model, not an edge case) crashes at dispatch time over BOTH the MCP and HTTP transports. This silently affects every "mount, don't codegen" consumer of `apigen-plugin-mcp`/`apigen-plugin-api-fastify`, not just `@adhd/backlog`.
- **Workaround shipped in `@adhd/backlog`:** `entrypoint/backlog/src/server.ts`'s `dereferenceSchema()` fully inlines every `$ref` (collecting `definitions`/`$defs` from any depth, substituting recursively, dropping the now-unused dicts) BEFORE `composeSchemas()` ever sees the schema — client.ts has no self-referential/recursive types, so this always terminates. This is a workaround, not a fix — the underlying `apigen-engine-runtime`/`apigen-base-logical` limitation remains.
- **Fix direction (upstream, out of `@adhd/backlog`'s scope):** either (a) give `dispatch()`/`RunInput` a way to supply a real `resolve()` override backed by the composed schema's own `definitions`/`$defs` (the "descriptor root" the error message alludes to), or (b) have `composeSchemas()`/the extraction pipeline guarantee every composed schema is fully dereferenced before it ever reaches a plugin, so run-mode `dispatch()` never needs to resolve a `$ref` at all.
- **Status:** OPEN (upstream `@adhd/apigen-engine-runtime`/`@adhd/apigen-base-logical`) — mitigated locally in `@adhd/backlog`.
- Citations: [main, claude (sonnet-5), backlog-implementation, 1: packages/apigen/apigen-base-logical/src/lib/runmode.ts:36-53; 2: packages/apigen/apigen-engine-runtime/src/lib/dispatch.ts:93-102; 3: entrypoint/backlog/src/server.ts (dereferenceSchema); 4: live repro — real MCP `callTool createItem` + real HTTP `POST /backlog/createItem` both threw this exact error before the workaround, both green after]

### BUG-APIGEN-LOGICAL-NULL-OBJECT-RESULT-INT64-001 — `apigen-base-logical`'s run-mode transcoder wraps a legitimate `null` result (for an object-typed output schema) in a nonsensical `{"$apigen":"int64","v":"null"}` envelope
- **Discovered:** 2026-07-23, adding `@adhd/backlog`'s CLI transport (`entrypoint/backlog/src/cli.ts`) and manually smoke-testing `get-item` against a non-existent id. `client.ts`'s `getItem` returns `BacklogItem | null`, and ts-json-schema-generator (this repo's tsconfig has no `strictNullChecks`) emits the OUTPUT schema as a plain `{type:'object', properties:{...}}` with no `null`/`oneOf` branch at all — the `| null` half of the TS type is silently dropped from the generated schema. Reproduced identically over BOTH the CLI (`backlog get-item --repo … --human-id <missing>`) and a live HTTP `GET /backlog/client-d/get-item?...` for a non-existent item: both return **HTTP 200 / exit 0** with body `{"$apigen":"int64","v":"null"}` instead of a bare JSON `null`.
- **Root cause (traced to exact lines, not guessed):** `packages/apigen/apigen-base-logical/src/lib/runmode.ts`'s `encodeNode()`, the `type:'object'` branch (`runmode.ts:122-124`): `if (value === null || typeof value !== 'object' || Array.isArray(value)) { return encodeSchemaless(value, schema, ctx); }` — a `null` result against an object-typed schema is treated as a "schema-less / any position" value rather than passed through as a literal JSON `null`. `encodeSchemaless()` (`runmode.ts:297-319`) then does `for (const id of ctx.registry.ids()) { try { codec.encode(value, ...) } catch { /* next */ } }` — "first codec whose `encode()` call does not throw, wins" — and the `int64` codec's encoder is `String($)` (`hints.spec.ts:371`, confirmed: `TEMPLATE_CELLS.typescript['int64'].encode === 'String($)'`), which is `String(null) === 'null'` — a valid string, so it NEVER throws for ANY input including `null`. Whichever codec with an unconditionally-non-throwing encoder happens to be registered first (here, `int64`) wins by construction, regardless of whether it has any real relationship to the value.
- **Impact:** any apigen-mounted function whose return type is `T | null` (or any other case where the generated schema's "any position" fallback receives `null`) returns a wrong, self-describing-envelope-wrapped result on every transport (HTTP, MCP, CLI — all three share this one `dispatch()`/transcoder). A consumer expecting a bare `null` (the overwhelmingly common "not found" contract) instead gets `{"$apigen":"int64","v":"null"}` and must special-case it, or worse, silently misinterprets it. Not merely cosmetic: any generic JSON client (including this repo's own `apigen-plugin-openapi`-advertised contract) is actively lied to about the response shape.
- **Fix direction (upstream, out of `@adhd/backlog`'s scope):** two independent, complementary fixes: (a) `encodeNode`'s `type:'object'` branch should pass a literal `null` straight through as `null` (never route it into the schema-less envelope heuristic at all — a missing/absent value is never a codec's responsibility); (b) separately, `encodeSchemaless`'s "first non-throwing codec wins" heuristic is unsound in general (a permissive `String($)`-style encoder will always mask a genuinely-unmatched value) — it should require every candidate codec to also pass a matching *decode-that-round-trips* check, or better, never be reached for `null`/`undefined` at all. No `@adhd/backlog`-side workaround was applied (this only reproduces on a NOT-FOUND result — every DoD test seeds the item first, so it isn't blocking, but `cli.spec.ts` deliberately does not assert the null-return shape, to avoid encoding this bug's wrong shape as expected behavior).
- **Status:** OPEN (upstream `@adhd/apigen-base-logical`) — not mitigated in `@adhd/backlog`; low real-world impact today since every currently-shipped `@adhd/backlog` DoD test only exercises the found-item path, but worth fixing before any consumer relies on a bare `null` not-found contract.

### DEBT-BACKLOG-CONCURRENCY-BUSY-RETRY-001 — no bounded retry/backoff on `SQLITE_BUSY`, and `busy_timeout` is hardcoded/unconfigurable, for the global-scope store's many-one-shot-CLI-writer design
- **Discovered:** 2026-07-23, architecture review of `docs/plan/backlog-adoption/MIGRATION.md`'s new "concurrency at 20+ agents" section.
- **Detail:** `graph-backlog-store.ts:19-32` opens WAL and hardcodes `db.pragma('busy_timeout = 5000')` with no config knob — `BacklogConfig`/`backlogEnvironmentSpec` (`env.ts:10-40`) exposes only `db.path` and `logging.level`; there is no `db.busyTimeoutMs` field or env-var override. Every metadata-mutating write funnels through `mutateMetadata` (`store/mutate-metadata.ts:30-45`), which wraps `db.transaction(fn).immediate()` with **no try/catch and no retry** — if a `BEGIN IMMEDIATE`'s wait exceeds `busy_timeout`, `better-sqlite3` throws a `SQLITE_BUSY`/`SQLITE_BUSY_TIMEOUT` exception straight to the caller (a one-shot CLI process crashing, or an MCP/HTTP request 500ing) instead of a clean, distinguishable "contended, retry" outcome. `claimItemNode`/`renewClaimNode`/`releaseClaimNode` (`store/claim.ts:1-98`) and every other lifecycle/structure op inherit this because they all funnel through the same primitive. `DESIGN.md` §12 (lines 619-624) explicitly notes "single-writer-per-scope is NOT enforced at the DB layer" and calls WAL+CAS "sufficient correctness-wise" for the `global`-scope store's documented many-concurrent-processes reality (`graph-backlog-store.ts:22-23`'s own comment) — but that is a claim about the LOCKING protocol's correctness, not about the FAILURE MODE when the fixed 5s `busy_timeout` window is exhausted under real load. At 20+ concurrent one-shot CLI writers, a worst-case pileup contending for the same hot item can plausibly exceed 5s of queued `BEGIN IMMEDIATE` waits, and today that surfaces as an unhandled thrown error with zero automatic recovery.
- **Plan:** `backlog-adoption` — this is a **Phase-3 (write-path cut-over) blocker** per `docs/plan/backlog-adoption/MIGRATION.md` §5[E6]. Cross-filed at `docs/plan/backlog-adoption/BACKLOG.md`.
- **Scope (verified by reading the source 2026-07-24):** this item is ONLY about the missing bounded-retry/backoff and the unconfigurable `busy_timeout` — it is NOT a transaction-isolation defect. Every write path already uses `BEGIN IMMEDIATE` (`mutate-metadata.ts:35-44` closes its `db.transaction(...)` with `.immediate()`[E1]; `ids.ts:11-27` does the identical thing for id allocation[E2]), and `mutate-metadata.ts:12-18` documents why deferred mode is unsafe[E1]. The deferred-vs-immediate choice is guarded by a MANUAL, one-time negative control performed during implementation, explicitly **NOT part of the automated suite** (`claim.spec.ts:11-18`[E3]) — so a regression from `.immediate()` back to deferred would NOT be caught by CI today; it is documented and was hand-verified, not automatically protected. Do not re-open the isolation angle as a defect; the only work here is the retry wrapper + config knob (and, separately, an automated guard for the isolation choice would be a defensible add — but that is not this item).
- **Fix direction:** (1) add `db.busyTimeoutMs` to `BacklogConfig`/`backlogEnvironmentSpec.config` (mirroring the existing `db.path` shape), env-overridable via `ADHD_BACKLOG_DATABASE_BUSY_TIMEOUT_MS`, default 5000, so an operator scaling toward more concurrent agents can raise it without a code change[E4]; (2) wrap the `.immediate()` call in a bounded, jittered exponential-backoff retry (e.g. 3-5 attempts) that retries ONLY on the specific `SQLITE_BUSY`/`SQLITE_BUSY_TIMEOUT` error code (`better-sqlite3` sets `.code`) — never on any other thrown error, and never conflated with the semantic `'held'` claim-contention result (a correct, non-error outcome that must never be silently retried into a false claim). The retry wrapper must cover ALL write paths that funnel through `.immediate()`, not just `mutateMetadata`: `ids.ts:11-27`'s id-allocation transaction has the identical unguarded shape and would still crash under the same contention[E2].
- **See also (forward pointer, not a dependency):** the proposed `@adhd/sox-executor` `DbAdapter` (sox-ecosystem `docs/spec/sox-executor.md` §2.5[E5]) exposes exactly this — `transaction<T>(fn, { immediate: true })` mapping to `BEGIN IMMEDIATE` where supported[E5] — at the adapter layer. If that library ships and is adopted here, this item's retry wrapper is naturally satisfied by adopting the adapter rather than hand-rolling the backoff. That spec is authored, not yet a shipped package; do not block this item on it.
- **Status:** OPEN.
